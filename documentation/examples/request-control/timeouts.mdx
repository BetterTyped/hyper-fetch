A product card behind a slow server. Pick how long the server takes and how long the request may wait. When the server
is slower than the timeout, the request is aborted and the card offers to retry, or to retry with a longer limit.

:::tip What it shows

1. **`setAdapterDefaults`** sets one timeout for every request of the client.
2. **`options: { timeout }`** and **`setOptions`** set it for one request.
3. **`TimeoutError`** tells a timeout apart from other failures with `instanceof`.
4. **`refetch()`** retries after a timeout.

:::

## How it works

1. The fetch adapter aborts every request after 5 seconds by default. `api.ts` changes that for the whole client with
   `client.adapter.setAdapterDefaults(() => ({ timeout: 4000 }))`.
2. `getProduct` sets its own limit in `options`, which holds the adapter options of a request:

   ```ts
   // highlight-next-line
   options: { timeout: 2000 },
   ```

3. `App.tsx` builds the request from the chosen values with `setQueryParams({ delay })` and `setOptions({ timeout })`.
   DummyJSON's `delay` query param makes the server answer slowly.
4. When the time runs out, the adapter aborts the call and the response has status `0` and a `TimeoutError` as `error`.
   `send()` and the hooks resolve with it, they don't throw. `error instanceof TimeoutError` picks the message.
5. **Retry** calls `refetch()`. **Allow 5 s and retry** raises the limit. The timeout is not part of the cache key, so
   `useFetch` lists it in `dependencies` and sends the request again when it changes.
6. While the request runs, a progress bar compares the elapsed time with the limit.

Requests with `retry` set are retried after a timeout too, since it is a failed response like any other.

:::note When to use it

- Slow or unreliable APIs where a stuck request is worse than a quick error.
- Search and autocomplete, where an old answer is not worth waiting for.
- Long reports or exports, which need a longer limit than the client default.

:::
