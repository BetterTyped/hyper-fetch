A project list that keeps working without a connection. Switch to **Offline**, create a project with its first task and
check off a few tasks: every change shows at once and waits in the outbox. Reload the page and it is all still there.
Switch back to **Online** and the outbox sends the writes in the order you made them.

<Example files={{ "src/db.ts": dbFile, "src/App.tsx": app, "src/server.ts": server }} />

:::tip What it shows

1. **An outbox**: `createDb(collections, { offline: true })` sends every write through a queue that waits for the
   network and replays in order.
2. **Persistence**: `persistence: { storage: localStorage, scope, version }` keeps the rows and the outbox, so a reload
   keeps offline writes on screen and in the queue.
3. **Idempotency keys**: `map` sends the write's id from `context.id`, and the fake server ignores an id it has seen.
4. **Dependent writes**: the first task is inserted with `{ dependsOn: [project] }`, so a rejected project drops its
   task without sending it.
5. **Rejected and retried writes**: a 422 drops the write and reports it to `db.onError`. A 503 keeps it in the outbox
   and retries it.

:::

---

## How it works

1. `db.ts` creates the db with `offline: true` and `persistence`. Every write goes through the outbox, online or not, so
   there is one path for every write.
2. Each `mutate` mapping adds `idempotencyKey: id` to the payload. The outbox marks a write as sent before its request
   goes out and sends it again after a reload, so the server needs the key to apply it once.
3. `App.tsx` turns the network off with `setOnline(false)` from `useAppManager(client)`. The outbox waits for the
   client to come back online, then sends the writes one at a time.
4. The outbox panel reads `db.inspect().outbox` and re-renders on `db.onChange`. Each record shows whether it was sent
   and which write it depends on.
5. Creating a project makes two writes. The task names the project's `Transaction` in `dependsOn`. When the server
   rejects the project with a 422, the db reverts both rows and reports both writes to `db.onError`.
6. `server.ts` keeps its rows and log in `localStorage` too. Reload the page while a write is in flight: the server
   already applied it, the outbox sends it again with the same key, and the log shows it was ignored.

:::note When to use it

- Apps used where the connection drops: field work, travel, mobile.
- Forms and notes where a lost write is expensive.
- Writes that depend on each other, like a project and its tasks, and must reach the server in order.

:::
