Your GraphQL documents already know their result and variable types. HyperFetch 10 reads them from the document, sends
hashes instead of full queries, keeps partial data when you ask for it, and listens to subscriptions over `graphql-ws`.
Upgrading means installing two peer dependencies.

## Highlights

- **[Typed documents](#typed-documents)**: A `TypedDocumentNode` or gql.tada document types the request without generics.
- **[Error policy](#error-policy)**: `errorPolicy: "all"` keeps partial data as a success, with the errors beside it.
- **[Persisted queries](#automatic-persisted-queries)**: Requests send the SHA-256 hash of the query, so CDNs can cache `GET` responses.
- **[Operation refetch](#refetch-every-variant-of-an-operation)**: `matchGqlOperation` invalidates every cached variant of an operation at once.
- **[Subscriptions](#subscriptions-over-graphql-ws)**: `GraphqlWsAdapter` speaks `graphql-transport-ws` on the shared reconnection engine.
- **[Spec alignment](#what-goes-over-the-wire)**: `operationName`, the GraphQL over HTTP `Accept` header and the right content type.

## Typed documents

`createRequest` reads the result and variable types from the `__apiType` decoration that graphql-codegen and gql.tada
put on a document, so you no longer repeat them as generics.

```ts title="requests.ts"
import { GraphqlAdapter, type GraphqlErrorType } from "@hyper-fetch/graphql";
import { GetUserDocument } from "./gql/graphql"; // generated

const client = createClient<{ error: GraphqlErrorType }>({ url }).setAdapter(
  GraphqlAdapter(),
);

// highlight-next-line
export const getUser = client.createRequest()({ endpoint: GetUserDocument });

// data and payload are typed by the document
const { data } = await getUser.send({ payload: { id: "1" } });
```

- Generics you declare win over the document. `createRequest<{ response: UserView }>()` keeps the document's variables
  and uses your response type.
- A document without variables needs no payload.
- Core reads the decoration structurally and has no GraphQL dependency, so any adapter whose endpoint carries
  `__apiType` gets the same inference.
- An untyped `DocumentNode` or string keeps the `undefined` response and payload, so declare them with generics.

When the document goes in the `document` option and the `endpoint` is a URL path, read the types with
`GraphqlDocumentTypes`:

```ts
const getUserByPath = client.createRequest<
  // highlight-next-line
  GraphqlDocumentTypes<typeof GetUserDocument>
>()({ endpoint: "/User", document: GetUserDocument });
```

## Error policy

A response can hold both `data` and `errors` when only some fields failed, and a dashboard with one broken widget should
still show the others. The `errorPolicy` adapter option decides what such a response resolves to.

```ts
const getDashboard = client.createRequest()({
  endpoint: GetDashboardDocument,
  // highlight-next-line
  options: { errorPolicy: "all" },
});

const { data, extra } = await getDashboard.send();
// Show data, and mark the fields in extra.errors[].path as unavailable
```

| `errorPolicy`      | A response with `data` and `errors`                                             |
| ------------------ | ------------------------------------------------------------------------------- |
| `"none"` (default) | Fails: `data` is `null` and `error` holds the errors, as in 9                   |
| `"all"`            | Succeeds with the partial `data`. No `data`, or a 4xx or 5xx status, still fails |

The server errors are in `extra.errors` with both policies. Set a default for every request with
`GraphqlAdapter().setAdapterDefaults(() => ({ errorPolicy: "all" }))`, and the request `options` still win.

## Automatic persisted queries

With `persistedQueries`, a request sends the SHA-256 hash of the query in `extensions.persistedQuery` instead of the
text. Requests get lighter, and hashed `GET` URLs are short enough for a CDN to cache.

```ts
const getUser = client.createRequest()({
  endpoint: GetUserDocument,
  method: GraphqlMethod.GET,
  // highlight-next-line
  options: { persistedQueries: true },
});
```

| The server answers           | The adapter                                                                 |
| ---------------------------- | --------------------------------------------------------------------------- |
| `PersistedQueryNotFound`     | sends the request again with the query, so the server stores it, and returns that response |
| `PersistedQueryNotSupported` | sends the request again with the query, and full queries from then on       |

- Without Web Crypto (`crypto.subtle` is missing on insecure origins) the full query is sent.
- One `timeout` covers the hashed request and the one that registers the query.
- Turn it on for every request with `GraphqlAdapter().setAdapterDefaults(() => ({ persistedQueries: true }))`.
  Without the option, nothing changes.

## Refetch every variant of an operation

After `UpdateUser`, every `GetUser` in the cache may be stale, whatever its `id`. `matchGqlOperation` returns a RegExp
that matches the cache keys of every request of a document, like `refetchQueries` in Apollo.

```ts
const { success } = await updateUser.send({ payload: { id: "1", name: "Ann" } });

if (success) {
  // highlight-next-line
  client.cache.invalidate(matchGqlOperation(GetUserDocument));
}
```

- It matches any variables, params, query params and method. A document matches its requests on every URL path of the
  `document` option, a request only on its own path.
- Documents with the same operation name but other selections are other operations, so they do not match.
- `invalidate` takes a list, so one mutation can refetch several operations.

## Subscriptions over graphql-ws

`GraphqlWsAdapter` connects a `Socket` to GraphQL subscriptions over WebSocket. It speaks `graphql-transport-ws`, the
protocol of the `graphql-ws` library that Apollo Server, GraphQL Yoga, Mercurius, Hot Chocolate and Hasura support.

```ts title="subscriptions.ts"
const socket = new Socket({
  url: "wss://api.example.com/graphql",
  // highlight-next-line
  adapter: GraphqlWsAdapter(),
  // Runs on every connection attempt, so a reconnect sends a fresh token
  adapterOptions: {
    connectionParams: async () => ({ token: await auth.getFreshToken() }),
  },
});

export const onMessage = socket.createListener()({
  topic: "OnMessage",
  // highlight-next-line
  options: { document: OnMessageDocument },
});

onMessage
  .setPayload({ room: "general" })
  .listen(({ data }) => console.log(data.onMessage.text));
```

The typed document types the data and makes the variables a required payload. In React,
`useListener(onMessage.setPayload({ room }))` subscribes again when the room changes and reports `status` and `error`.

- Listeners with the same document and variables share one subscription. The last one to stop sends `complete`.
- The connection counts as open once the server acknowledged `connection_init`, so `connectionTimeout` covers the whole
  handshake. Subscriptions started earlier wait for it.
- After a reconnect, every running subscription is sent again with a new id. Close codes a retry cannot fix, like
  `4400` or `4401`, stay closed, as in the `graphql-ws` client. `shouldReconnectGraphqlWs` keeps those rules in a custom
  `shouldReconnect`.
- Errors of one event arrive in `extra.errors` and the subscription goes on. An `error` message ends the listener with a
  `GraphqlSubscriptionError` in `onEnd`.
- The adapter answers the server's `ping`. `keepAlive` pings a quiet connection to notice one that died behind a proxy,
  and `lazy` holds a connection only while there are subscriptions.

Typed payloads, the listener lifecycle, delivery strategies and the reconnection engine come from the
[sockets post](/blog/hyper-fetch-10-sockets), so `batch` delivers arrays of the document's data.

## What goes over the wire

Each operation follows the [GraphQL over HTTP](https://graphql.github.io/graphql-over-http/) format more closely:

- The body, or the query string for `GET`, holds `operationName`, the name of the first operation in the document.
- The `Accept` header asks for `application/graphql-response+json` with `application/json` as the fallback, so servers
  that follow the spec answer invalid requests with a 4xx status.
- `POST` requests always send `Content-Type: application/json`, also without variables. `GET` requests send none, since
  the header only triggered a CORS preflight.
- Headers you set win over both defaults.
- Cache and query keys contain the operation name, a fingerprint of the document and the variables.

## Reliability fixes

- `GetUser(id: 1)` and `GetUser(id: 2)` no longer share a cache entry or get deduplicated into one request.
- Two documents with one operation name but other selections no longer share a cache entry. A deduplicated request
  used to hand the second caller the data of the first.
- Queries without variables are sent as JSON. They went out as `text/plain`, and servers answered 415.
- A string document like `mutation DeleteUser($id: ID!) { ... }` no longer asks for a URL param named after the text
  after the colon, so `send({ payload })` compiles.
- An empty `errors` list is no longer a failure.
- Network, abort and timeout failures arrive as a list with one `Error`, like every other GraphQL error, so
  `GraphqlErrorType` covers them all.
- The upload of a request is reported as finished only once the body was sent.

## Upgrading

`graphql` is now a peer dependency, and so is `@hyper-fetch/sockets`, for `GraphqlWsAdapter`. Install both next to
`@hyper-fetch/graphql`:

```bash npm2yarn2pnpm
npm install @hyper-fetch/core @hyper-fetch/sockets @hyper-fetch/graphql graphql
```

- Cache keys now contain the document fingerprint and the variables. Data persisted under the keys of earlier versions
  is not read again, so the first requests after the upgrade go to the network.
- Generics written only to mirror a typed document can go. Keeping them still works, since declared generics win.
