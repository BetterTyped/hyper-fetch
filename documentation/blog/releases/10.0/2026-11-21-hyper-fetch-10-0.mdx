HyperFetch 10 is out, and this one is about your backend. Its biggest addition is `@hyper-fetch/db`, a normalized
cache that stays live: each record is stored once and every view of it updates when a write or a socket event changes
it. The client now takes its types straight from tRPC, oRPC, Hono and Elysia, sockets recover from a lost connection
the same way on every transport, and GraphQL gets persisted queries and `graphql-ws`. Before tagging it we audited
every package and landed more than 80 fixes, each with a regression test. Core, React and Firebase upgrade with no code
changes.

{/* truncate */}

```bash npm2yarn2pnpm
npm install @hyper-fetch/core@10 @hyper-fetch/react@10
```

Every package now ships under one version, so `@10` everywhere is a set that was released and tested together. Sockets
and GraphQL have a few breaking changes, listed in [Upgrading from 9](#upgrading-from-9).

## Highlights

- **[HyperFetch DB](#hyperfetch-db)**: a normalized cache that stays live, with live queries, optimistic writes and an
  offline outbox. _Beta._
- **[Typed clients from your backend](#typed-clients-from-your-backend)**: tRPC, oRPC, Hono and Elysia types go
  straight into `createSdk`, with no schema to write.
- **[Optimistic updates](#optimistic-updates)**: describe the change, and core applies it, rolls it back on failure
  and refetches.
- **[Infinite lists](#infinite-lists)**: `useInfiniteFetch` pages by page number, offset or cursor.
- **[Sockets that recover](#sockets-that-recover)**: one reconnection engine and typed subscription payloads for every
  adapter. _Breaking._
- **[GraphQL, typed end to end](#graphql-typed-end-to-end)**: typed documents, automatic persisted queries and a
  `graphql-ws` adapter. _Breaking._
- **[Typed Firebase queries](#typed-firebase-queries)**: constraints are checked against the fields of your documents.
- **[Devtools for sockets](#devtools-for-sockets)**: HyperFlow shows your sockets, also from Node.js servers.
- **[Hardened everywhere](#hardened-everywhere)**: an audit of every package, with a failing test before each fix.

## HyperFetch DB

The same record usually sits in several cached responses, and keeping every copy current with a socket is code each
app writes by hand. `@hyper-fetch/db` stores each record once, in a typed collection that your requests and socket
listeners fill, and components query the collection instead of an endpoint:

```tsx title="posts.tsx"
const Post = collection(PostSchema, { key: "id", version: "updatedAt" })
  .load(getTeamPosts, {
    where: {
      teamId: { eq: (teamId) => ({ params: { teamId } }), required: true },
    },
  })
  .sync(onPostChanged, { type: "update" });

const db = createDb({ post: Post });
// highlight-next-line
const { data } = useLiveQuery(db.post.where((p) => eq(p.teamId, 1)));
```

A write shows at once in every view and reverts on failure, and a slow response cannot overwrite a newer socket event.
Writes made offline replay in order after a restart. The [HyperFetch DB post](/blog/hyper-fetch-db) explains how the
live part works and how we tested it.

## Typed clients from your backend

If your server is tRPC, oRPC, Hono or Elysia, its types already describe every endpoint. HyperFetch 10 reads them, so
the client needs no schema, codegen step or hand-written request:

```ts title="api.ts"
import { TrpcAdapter, type TrpcSchema } from "@hyper-fetch/trpc";
import type { AppRouter } from "./server";

const client = createClient({ url: "/trpc" }).setAdapter(TrpcAdapter());

// highlight-start
const api = createSdk<typeof client, TrpcSchema<AppRouter>>(client, {
  camelCaseToKebabCase: false, // keep procedure names as written
});
// highlight-end

const { data } = await api.user.byId.$query.setPayload({ id: 1 }).send();
```

`OrpcSchema`, `HonoSchema` and `ElysiaSchema` work the same way. tRPC subscriptions and oRPC event iterators become
typed socket listeners. The [backend packages post](/blog/hyper-fetch-10-backends) sets up each server, end to end.

## Optimistic updates

Optimistic UI usually means a snapshot, a cache write and a rollback written by hand for every mutation. Now you
describe the change and core does the rest:

```ts title="todos.ts"
import { optimistic } from "@hyper-fetch/core";

const toggleTodo = updateTodo.setOptimistic(({ params, payload }) => [
  // highlight-next-line
  optimistic(getTodos).patch(params.todoId, payload),
]);
```

The patch shows before the request is sent. If the request fails it is rolled back, and once it settles `getTodos`
is refetched. `useSubmit` takes the same helpers, so one component can override the change.

## Infinite lists

`useInfiniteFetch` keeps the pages, the next cursor and the end of the list in sync from one `pagination`
description. Each page stays a normal request under its own cache key:

```tsx title="feed.tsx"
const { items, hasNextPage, fetchNextPage } = useInfiniteFetch(getFeed, {
  // highlight-next-line
  pagination: { cursor: "cursor", next: "nextCursor", items: "data" },
});
```

Page numbers and offsets work too, and `fetchInfinite` does the same outside React. Core and React also gain `Hydrate`
for server rendering, retry backoff, offline queues that survive a reload and binary downloads. The
[core and React post](/blog/hyper-fetch-10-core-react) walks through each of them.

## Sockets that recover

Every socket adapter now runs on one reconnection engine: jittered backoff, a connection timeout, and a reset once the
connection stays up. Listeners also learned subscriptions. A listener can carry a typed payload, and it tells you when
the server starts and ends the subscription:

```ts title="jobs.ts"
const onJobProgress = socket.createListener<JobProgress, { jobId: string }>()({
  topic: "jobs.onProgress",
});

onJobProgress.listen(({ data }) => render(data), {
  // highlight-start
  payload: { jobId: "1" },
  onEnd: ({ error }) => (error ? showError(error) : showDone()),
  // highlight-end
});
```

Sockets also run in Node.js, Bun and Deno, and server-sent events read named events. The
[sockets post](/blog/hyper-fetch-10-sockets) covers delivery strategies, the reconnection options and the upgrade steps.

## GraphQL, typed end to end

Pass a typed document from graphql-codegen or gql.tada as the endpoint, and the response and variables are typed with
no generics. One option turns on automatic persisted queries:

```ts title="users.ts"
const getUser = client.createRequest()({
  endpoint: GetUserDocument,
  // highlight-next-line
  options: { persistedQueries: true },
});

const { data } = await getUser.send({ payload: { id: "1" } });
```

Subscriptions get their own `GraphqlWsAdapter` for the `graphql-transport-ws` protocol, and `errorPolicy: "all"` keeps
partial data next to its errors. See the [GraphQL post](/blog/hyper-fetch-10-graphql) for the details.

## Typed Firebase queries

Firestore and Realtime Database constraints moved into `queryParams`, as an array or as a typed callback that only
accepts the fields and values of your document:

```ts title="teas.ts"
const { data } = await getTeas.send({
  // highlight-next-line
  queryParams: (c) => c.where("type", "==", "Green").orderBy("year", "desc"),
});
```

Writes send their payload again, and listeners deliver each snapshot once. The
[Firebase post](/blog/hyper-fetch-10-firebase) has the full list.

## Hardened everywhere

Before this release we audited every package and wrote a failing test for each problem before fixing it. Among the
fixes:

- Out-of-order responses no longer overwrite newer data.
- Falsy payloads and response data are kept.
- Removed requests stop retrying.
- A failing response mapper resolves `send()` with a failed response instead of rejecting.
- Scopes stay isolated in hooks and Suspense.
- SSE sockets no longer reconnect after a manual disconnect.

Flaky specs were fixed at the cause instead of retried, so timing-dependent tests now run on fake clocks. Each area
post lists the fixes for its package.

## Upgrading from 9

Core, React, Firebase and the HTTP adapters need no code changes. The breaking changes are in `@hyper-fetch/sockets`
and `@hyper-fetch/graphql`:

| Change                                                                     | What to do                                                        |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Sockets connect wherever a global `WebSocket` exists, Node.js included     | Set `adapterOptions: { autoConnect: typeof window !== "undefined" }` |
| `connectionTimeout` (5s) limits an attempt, `reconnectTime` is the minimum delay (1s) | Set `connectionTimeout` if you relied on `reconnectTime` for it |
| `onMessage` interceptors receive `{ event, topic, extra }`                 | Nothing, unless you need the topic or the adapter extra           |
| Listener generics make room for subscription payloads                      | Update hand-written `Listener`, `ListenType` or `ListenerOfAdapter` types |
| `graphql` and `@hyper-fetch/sockets` are peer dependencies of `@hyper-fetch/graphql` | Install both                                            |
| GraphQL cache keys changed                                                 | Nothing: data persisted by earlier versions is fetched again once |

The [sockets](/blog/hyper-fetch-10-sockets#upgrading) and [GraphQL](/blog/hyper-fetch-10-graphql#upgrading) posts show
each change before and after. The v9 docs stay online under [v9.0.0](/docs/v9.0.0/getting-started).
