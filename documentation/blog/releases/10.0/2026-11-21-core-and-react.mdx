Optimistic updates, infinite lists and server rendering are the parts of a data layer that every app rebuilds by hand.
HyperFetch 10 ships them in `@hyper-fetch/core` and `@hyper-fetch/react`, together with retry backoff, offline queues
that survive a reload and binary downloads. Upgrading these two packages needs no code changes.

## Optimistic updates

Describe the change, and core snapshots the cache, applies the change, undoes it on failure and refetches.

```ts title="todos.ts"
import { optimistic } from "@hyper-fetch/core";

const toggleTodo = client
  .createRequest<{ response: Todo; payload: { completed: boolean } }>()({
    endpoint: "/todos/:todoId",
    method: "PATCH",
  })
  // highlight-start
  .setOptimistic(({ params, payload }) => [
    optimistic(getTodos).patch(params.todoId, payload),
  ]);
// highlight-end
```

- The helpers are `set`, `patch`, `insert`, `remove` and `increment`. `.list("items")` targets an array inside an
  object response.
- `optimistic.all(getTodos)` changes every cached variant of a request, whatever its query params, so every page of an
  infinite list too.
- A plain `match` value is compared with the item's `id`, and `"1"` matches `1`, so route params work as they are.

Core never guesses an undo. You write it in `.rollback()`, which receives the current `data` and the `previous` data.
Without a rollback, the target is refetched instead. `.commit()` runs on success, for example to swap a temporary id for
the one from the server:

```ts title="create-todo.ts"
const createTodo = postTodo.setOptimistic(({ payload }) => {
  const tempId = crypto.randomUUID();
  return [
    optimistic(getTodos)
      .insert({ ...payload, id: tempId })
      // highlight-start
      .rollback(({ data }) => data.filter((todo) => todo.id !== tempId))
      .commit(({ data, response }) =>
        data.map((todo) => (todo.id === tempId ? response.data : todo)),
      ),
    // highlight-end
  ];
});
```

Once the mutation settles, core finishes the job, also when the component that submitted it has unmounted:

| When                                    | Core                                                     |
| --------------------------------------- | -------------------------------------------------------- |
| The mutation succeeds                   | runs each `.commit()`                                    |
| It fails for good or is aborted         | runs each `.rollback()`, in reverse order                |
| A retry is pending or it waits offline  | keeps the change                                         |
| A fetch started before it settled       | does not write that response to the changed targets      |
| Several mutations change one target     | refetches the target once, after the last of them        |

In React, `useSubmit` takes the same operations, so one component can override the request's optimistic change:

```tsx
const { submit } = useSubmit(toggleTodo, {
  // highlight-start
  optimistic: ({ params, payload }) => [
    optimistic(getTodos).patch(params.todoId, payload),
  ],
  // highlight-end
});
```

The hook option replaces `setOptimistic` for that hook, and `submit({ optimistic })` replaces both for a single call.

## Infinite lists with useInfiniteFetch

`useInfiniteFetch` keeps the pages, the next cursor, the end of the list and filter changes in sync from one
`pagination` description.

```tsx title="feed.tsx"
const getFeed = client.createRequest<{
  response: { data: Post[]; nextCursor: string | null };
  queryParams: { cursor?: string; topic?: string };
}>()({ endpoint: "/feed" });

const { items, hasNextPage, isFetchingNextPage, fetchNextPage } =
  useInfiniteFetch(
    getFeed.setQueryParams({ topic }),
    // highlight-next-line
    { pagination: { cursor: "cursor", next: "nextCursor", items: "data" } },
  );
```

- Every `pagination` key is checked against the request types, so a typo in `"nextCursor"` fails to compile.
- Page numbers (`page`), offsets (`offset` with `limit`) and cursors (`cursor` with `next`) work in the query params,
  the URL params or the payload.
- A changed `topic` starts a new list on its own.
- Each page is a normal request under its own cache key. Deduplication, invalidation, persistence, optimistic updates
  and `Hydrate` work per page, and nothing extra is stored.
- The hook also has `fetchPreviousPage`, `maxPages` to keep a window of pages, `uniqueBy` to drop repeated items, and
  `select`.

The paging logic lives in core, so `fetchInfinite` can fetch the first pages on the server for `Hydrate`.

## Server rendering with Hydrate

`Hydrate` hands server data to the hooks before their first render, so the page skips the loading state and the second
fetch.

<Tabs>
<TabItem value="server" label="Server">

```tsx title="page.tsx"
export default async function Page() {
  const response = await getUsers.send();

  // highlight-next-line
  return <UsersList hydration={[getUsers.dehydrate({ response })]} />;
}
```

</TabItem>
<TabItem value="client" label="Client">

```tsx title="users-list.tsx"
"use client";

import { Hydrate, useFetch, type HydrateProps } from "@hyper-fetch/react";

export const UsersList = ({ hydration }: { hydration: HydrateProps["data"] }) => (
  // highlight-next-line
  <Hydrate client={client} data={hydration}>
    <Users />
  </Hydrate>
);

const Users = () => {
  // The server data, on the first render and without a request while it is fresh
  const { data } = useFetch(getUsers);
  return <UserList users={data} />;
};
```

</TabItem>
</Tabs>

For lists, call `fetchInfinite(getFeed, { pagination, pages: 2 })` on the server and pass its `dehydrated` result.

- Hooks render the hydrated data on the first render, during server rendering too. On the server nothing is written to
  the cache, so concurrent renders never share data.
- In the browser the data reaches the cache before any hook mounts.
- Newer cached data is never replaced by an older snapshot. `override: false` keeps existing data in every case.
- Each `Hydrate` serves only its own client, so boundaries nest and several clients work side by side.

## Retry backoff

Clients that failed together used to retry together, at a fixed pace. `retryTime` now also takes a function.

<Tabs>
<TabItem value="backoff" label="exponentialBackoff">

```ts
import { exponentialBackoff } from "@hyper-fetch/core";

const getReport = client.createRequest<{ response: Report }>()({
  endpoint: "/reports/:reportId",
  retry: 5,
  // highlight-next-line
  retryTime: exponentialBackoff({ min: 500, max: 10_000 }),
});
```

</TabItem>
<TabItem value="custom" label="Custom function">

```ts
const getStatus = client.createRequest<{ response: Status }>()({
  endpoint: "/status",
  retry: 3,
  // highlight-start
  retryTime: ({ attempt, response }) =>
    response.status === 503 ? 5_000 : 1_000 * (attempt + 1),
  // highlight-end
});
```

</TabItem>
</Tabs>

- `exponentialBackoff` defaults to `min: 500`, `max: 30_000` and `jitter: true`.
- `attempt` starts at `0` for the first retry.
- A function that throws stops the retries, like a throwing `retryOnError`.

## Offline queues that survive a reload

Mutations made offline in apps on IndexedDB or AsyncStorage were lost when the app closed, because the queue only took a
synchronous storage. The `Dispatcher` now takes a `lazyStorage`.

```ts title="client.ts"
import { createStore, del, get, keys, set } from "idb-keyval";
import { createClient, Dispatcher } from "@hyper-fetch/core";

const store = createStore("hyper-fetch-queues", "queues");

export const client = createClient({
  url: "https://api.example.com",
  // highlight-start
  submitDispatcher: () =>
    new Dispatcher({
      lazyStorage: {
        set: (key, data) => set(key, data, store),
        get: (key) => get(key, store),
        keys: async () => (await keys(store)).map(String),
        delete: (key) => del(key, store),
      },
    }),
  // highlight-end
});
```

- Every queue change is written as JSON, in order.
- On start the dispatcher sends the restored requests ahead of new ones, once the adapter and plugins you chain after
  `createClient` are in place.
- A request the browser cancels because the page is closing stays queued for the next load.
- Requests are saved with `toJSON()`, so functions such as mappers or a function `retryTime` are not kept.

On the reading side, `useFetch` with `revalidate: false` now waits for the cache `lazyStorage` before it decides to
fetch. Fresh persisted data shows without a request.

## Binary downloads

The fetch adapter decoded every body as text, which corrupted images and archives. `responseType` picks the shape of a
successful body.

```ts
const downloadAvatar = client.createRequest<{ response: Blob }>()({
  endpoint: "/users/:userId/avatar",
  // highlight-next-line
  options: { responseType: "blob" },
});

const { data } = await downloadAvatar.setParams({ userId: 1 }).send();
```

- The values are `"json"`, `"text"`, `"blob"` and `"arrayBuffer"`. Without the option, bodies are parsed as before.
- Error bodies keep their JSON shape, and download progress works for every type.
- `timeout` covers the whole download, so large files need a higher one.

## Failures in the response

`send()` reports failures through the response and never rejects. A throwing response mapper used to leave it pending
forever.

```ts
const getUser = client
  .createRequest<{ response: User }>()({ endpoint: "/users/:userId" })
  .setResponseMapper((response) => {
    if (!response.success) return response;
    // A throw or a rejection here becomes the `error` of the response
    // highlight-next-line
    return { ...response, data: parseUser(response.data) };
  });
```

- A failing mapper resolves `send()` with a failed response that carries the mapper error. Hooks call their error
  callbacks and expose it in `error`.
- Errors thrown by your callbacks, response listeners, plugins or rollbacks no longer stop the request. They are
  thrown from a timer, where `window.onerror` or an `uncaughtException` handler sees them.
- Aborted requests are reported as canceled whatever error shape the adapter uses. GraphQL aborts were reported as
  failures and could even be retried. Adapter timeouts still count as failures.

## Sharper types

### Typed endpoints

An endpoint with the standard `__apiType` decoration, like a graphql-codegen `TypedDocumentNode` or a gql.tada document,
types the response and the payload without generics. Core reads it structurally and has no GraphQL dependency. Generics
you declare still win.

```ts
// The response and the payload come from the document
const getUser = client.createRequest()({ endpoint: GetUserDocument });
```

### URL segments for SDK keys

`camelCaseToKebabCase` turns `findByStatus` into `find-by-status`. APIs that mix both styles map single keys with
`pathSegments`:

```ts
const sdk = createSdk<typeof client, PetStoreSchema>(client, {
  // highlight-next-line
  pathSegments: { findByStatus: "findByStatus" },
});

await sdk.pet.findByStatus.$get.send(); // GET /pet/findByStatus
```

### Reserved SDK keys

Below the top level, the SDK reads a key from the request before it treats it as a path. A procedure named `send`
type-checked, but at runtime it was the request's own method. Such keys are now typed as `SdkReservedKeyError`, so the
mistake fails to compile.

### Query params callbacks

Adapters can register `setQueryParamsResolver` to accept query params given as a function, such as a typed query
builder. The resolver runs at once, so cache keys and `toJSON()` only ever see data. The Firebase adapters use it for
typed constraints.

## Reliability fixes

Most of the two weeks of hardening went into core and the hooks, and the infinite list specs were ported from TanStack
Query and SWR.

### Cache and requests

- Out-of-order responses of one cache key no longer overwrite newer data, in the cache or in hooks.
- Falsy payloads and data (`0`, `false`, `""`) are kept, and `setPayload(null)` removes the payload.
- `cache.update()` restarts the stale and cache time, so updated data is not refetched and dropped.
- `cache.clear()` and `client.clear()` also empty the lazy storage, so the next user never sees old data.
- Scoped requests stay isolated in hooks and Suspense: no data, loading state or invalidation leaks between scopes.
- Request and response interceptors are chained, each receiving the result of the previous one.
- `adapter.setAdapterDefaults()` applies to every request, and partial query params options keep their defaults.
- Colons in GraphQL string documents are no longer read as URL params.
- Clients with a custom adapter stay under the type instantiation depth limit of tsgo.

### Dispatcher and retries

- A request removed from the queue stops retrying, and its `send()` resolves.
- A failed queued request no longer loops, and a paused queue holds its retries.
- Requests with `offline: false` fail at once when sent offline.
- A request added from a response listener no longer sends the answered request twice.

### Transfers

- Download progress of gzip responses stays within 100%, and 100 byte bodies reach 100%.
- Upload progress starts at 0% and ends when the body was sent, with real totals for `Blob`, `ArrayBuffer` and
  `URLSearchParams`.
- Fetch implementations without a stream reader, such as older React Native ones, read text bodies again.
- A rejected async adapter fetcher resolves `send()` with an error instead of an unhandled rejection.
- A mocked request reports exactly one outcome.

### React hooks

- `useFetch` stays `loading` while a retry is pending, and `abort()` also cancels a waiting retry.
- `useFetch`, `useCache` and `useInfiniteFetch` no longer crash on `BigInt` payloads.
- `useSubmit` stays `submitting` until its last request is done, and `abort()` calls `onSubmitAbort` and
  `onSubmitFinished`.
- Debounced and throttled `submit()` promises always settle, also when a callback throws.
- No hook callbacks run after unmount, also when an async mapper resolves late.
- `useQueue` mirrors the dispatcher queue, and sets `failed` only on the final failure.
- `useStream` keeps the request options and stops reading the body on abort, reset and unmount.
- `useListener` follows the socket of its listener.
- `useInfiniteFetch` handles shrinking lists, bounce, StrictMode remounts and throwing pagination callbacks.

## Upgrading

No export of `@hyper-fetch/core` or `@hyper-fetch/react` was removed or renamed, and the object form of `setOptimistic`
works as before. Two fixes can surface in code that was already broken:

- An SDK key named like a request property now fails to compile.
- Errors thrown by plugins and optimistic rollbacks, which were only logged, now also reach the global error handlers.

The breaking changes of v10 are in `@hyper-fetch/sockets`, covered in the
[sockets post](/blog/hyper-fetch-10-sockets#upgrading).
