Your backend already knows the input, output and errors of every route. Writing them again on the frontend is busywork
that drifts the moment someone renames a field. HyperFetch 10 adds four packages that read the types of a tRPC router,
an oRPC router, a Hono app or an Elysia app and hand them to `createSdk`.

{/* truncate */}

:::info Version

Written for **HyperFetch 10**. The [release overview](/blog/hyper-fetch-10-0) links the rest of the series.

:::

## Highlights

- **[tRPC](#trpc)**: `@hyper-fetch/trpc` calls queries and mutations through the HyperFetch cache and queue.
- **[tRPC subscriptions](#subscriptions)**: Subscriptions over WebSocket or SSE become typed listeners that resume after a reconnect.
- **[oRPC](#orpc)**: `@hyper-fetch/orpc` keeps `Date`, `BigInt`, `Map` and files intact, with typed errors.
- **[Event iterators](#event-iterators)**: oRPC event iterators become typed listeners over HTTP or WebSocket.
- **[Hono](#hono)**: `@hyper-fetch/hono` types an SDK from a Hono app and adds no runtime code.
- **[Elysia](#elysia)**: `@hyper-fetch/elysia` types an SDK from an Elysia app, with errors typed per status.
- **[Shared reconnection](#reconnects-you-do-not-have-to-write)**: The new socket adapters reconnect on the engine every socket adapter shares.
- **[One request type](#the-same-request-whichever-backend)**: Every route is a regular `Request`, so hooks, caching and devtools work unchanged.

## tRPC

`@hyper-fetch/trpc` runs tRPC procedures through the same cache, loading states and retries as the rest of your app, so
you do not keep a second data layer next to HyperFetch.

```bash npm2yarn2pnpm
npm install @hyper-fetch/core @hyper-fetch/trpc
```

<Tabs>
<TabItem value="client" label="Client">

```ts title="api.ts"
import { TrpcAdapter, type TrpcSchema } from "@hyper-fetch/trpc";
import type { AppRouter } from "./server";

const client = createClient({ url: "http://localhost:3000/trpc" }).setAdapter(
  TrpcAdapter(),
);

// highlight-next-line
const api = createSdk<typeof client, TrpcSchema<AppRouter>>(client, {
  camelCaseToKebabCase: false, // keep procedure names as written: byId, not by-id
});

// highlight-next-line
const { data, error } = await api.user.byId.$query.setPayload({ id: 1 }).send();
```

</TabItem>
<TabItem value="server" label="Server">

```ts title="server.ts"
const t = initTRPC.create();

export const appRouter = t.router({
  user: t.router({
    byId: t.procedure
      .input((value) => value as { id: number })
      .query(({ input }) => getUser(input.id)),
    create: t.procedure
      .input((value) => value as { name: string })
      .mutation(({ input }) => createUser(input)),
  }),
});

// highlight-next-line
export type AppRouter = typeof appRouter;
```

</TabItem>
</Tabs>

- Queries live under `$query` and go out as `GET` with the encoded input. Mutations live under `$mutation` and go out as
  `POST` with a JSON body.
- The input is part of the cache and query keys, so `{ id: 1 }` and `{ id: 2 }` are cached, deduplicated and queued
  separately.
- Errors keep the shape your router sends, including a custom `errorFormatter`.
- Pass `TrpcAdapter({ transformer: superjson })` when the server uses one.

### Subscriptions

Subscriptions live on a `Socket`. `TrpcWebsocketAdapter` speaks the `wsLink` protocol and `TrpcSseAdapter` the
`httpSubscriptionLink` protocol, and both share one schema type.

<Tabs>
<TabItem value="client" label="Client">

```ts title="socket.ts"
const socket = new Socket({
  url: "ws://localhost:3001",
  adapter: TrpcWebsocketAdapter(),
});

// highlight-next-line
const realtime = createSocketSdk<typeof socket, TrpcSocketSchema<AppRouter>>(
  socket,
  { camelCaseToKebabCase: false },
);

realtime.chat.onMessage.$listener
  .setPayload({ room: "general" })
  // extra.eventId is the id of events yielded with tracked()
  .listen(({ data, extra }) => console.log(data.text, extra.eventId));
```

</TabItem>
<TabItem value="server" label="Server">

```ts title="server.ts"
export const appRouter = t.router({
  chat: t.router({
    onMessage: t.procedure
      .input((value) => value as { room: string; lastEventId?: string })
      .subscription(async function* ({ input, signal }) {
        const after = input.lastEventId;
        for await (const message of messages(input.room, { after, signal })) {
          // highlight-next-line
          yield tracked(message.id, message);
        }
      }),
  }),
});
```

</TabItem>
</Tabs>

- The procedure input is the listener payload. Listeners with the same input share one server subscription.
- After a reconnect, every subscription restarts with the last `tracked()` id as `lastEventId`, so the procedure can send
  what the client missed.
- `onStart` and `onEnd` follow the server's confirmation and end of the subscription, and `useListener` exposes them as
  `status`.
- Errors reach `socket.onError` as a `TrpcSocketError` with the topic and the input that failed.
- Switching to SSE changes only the adapter and the URL:
  `new Socket({ url: "http://localhost:3000/trpc", adapter: TrpcSseAdapter() })`.

## oRPC

oRPC sends `Date`, `BigInt`, `Map` and files with its own serializer, which a generic HTTP client flattens to JSON.
`@hyper-fetch/orpc` encodes inputs and outputs with the serializer from `@orpc/client`, so the client and the server
always agree.

```bash npm2yarn2pnpm
npm install @hyper-fetch/core @hyper-fetch/orpc @orpc/client
```

<Tabs>
<TabItem value="client" label="Client">

```ts title="api.ts"
import { OrpcAdapter, type OrpcSchema } from "@hyper-fetch/orpc";
import type { router } from "./server";

const client = createClient({ url: "http://localhost:3000/rpc" }).setAdapter(
  OrpcAdapter(),
);

// highlight-next-line
const api = createSdk<typeof client, OrpcSchema<typeof router>>(client, {
  camelCaseToKebabCase: false,
});

const { error } = await api.planet.find.$query.setPayload({ id: 1 }).send();

// `error` also holds the client's global error, so check the oRPC shape first
// highlight-start
if (error && "defined" in error && error.defined && error.code === "NOT_FOUND") {
  error.data; // typed from the .errors() map of the procedure
}
// highlight-end
```

</TabItem>
<TabItem value="server" label="Server">

```ts title="server.ts"
export const router = {
  planet: {
    find: os
      .input(z.object({ id: z.number() }))
      .handler(({ input }) => findPlanet(input.id)),
    // An event iterator procedure
    onUpdate: os
      .input(z.object({ id: z.number() }))
      .handler(async function* ({ input, signal }) {
        for await (const planet of planetUpdates(input.id, { signal })) {
          // highlight-next-line
          yield withEventMeta(planet, { id: String(planet.version) });
        }
      }),
  },
};
```

</TabItem>
</Tabs>

- oRPC procedures have no kind, so every procedure is available as both `$query` and `$mutation`.
- Queries are sent as `POST` by default. `OrpcAdapter({ queryMethod: "GET" })` lets browsers and CDNs cache them.
- For contract-first APIs, pass `ContractRouterClient<typeof contract>` instead of the router type.

### Event iterators

Procedures that return an event iterator become typed listeners. `OrpcStreamAdapter` reads them over the same HTTP
`RPCHandler` that serves your queries, and `OrpcWebsocketAdapter` speaks the protocol of `@orpc/server/ws`.

```ts title="socket.ts"
const socket = new Socket({
  url: "http://localhost:3000/rpc",
  adapter: OrpcStreamAdapter(),
});

// highlight-next-line
const events = createSocketSdk<typeof socket, OrpcSocketSchema<typeof router>>(
  socket,
  { camelCaseToKebabCase: false },
);

events.planet.onUpdate.$listener
  .setPayload({ id: 1 })
  // extra.id is the id set with withEventMeta() on the server
  .listen(({ data, extra }) => console.log(data.name, extra.id));
```

As with tRPC, listeners with the same input share one subscription, and a restarted subscription resumes from the id of
its last event. Rich types survive in every event as well as in the input.

## Hono

Hono's own RPC client reads your app type but returns raw `Response` objects. `@hyper-fetch/hono` types a full SDK from
the same app type and adds no code to your bundle, since it exports types only.

```bash npm2yarn2pnpm
npm install @hyper-fetch/core @hyper-fetch/hono
```

<Tabs>
<TabItem value="frontend" label="Frontend">

```ts title="frontend/src/api.ts"
import type { AppSchema } from "@my-app/backend";

const client = createClient({ url: "https://api.example.com" });
// highlight-next-line
const sdk = createSdk<typeof client, AppSchema>(client);

const { data: user } = await sdk.users.$userId.$get
  .setParams({ userId: "1" })
  .send();
const { data: created } = await sdk.users.$post
  .setPayload({ name: "Bob" })
  .send();
```

</TabItem>
<TabItem value="backend" label="Backend">

```ts title="backend/src/app.ts"
const users = new Hono()
  .get("/:userId", (c) => c.json({ id: c.req.param("userId"), name: "Ann" }))
  .post("/", validator("json", (value: { name: string }) => value), (c) =>
    c.json({ id: "2", name: c.req.valid("json").name }, 201),
  );

export const app = new Hono().route("/users", users);

// highlight-next-line
export type AppSchema = HonoSchema<typeof app>;
```

</TabItem>
</Tabs>

| Hono route                         | SDK                                   |
| ---------------------------------- | ------------------------------------- |
| `/users/:userId`                   | `sdk.users.$userId`                   |
| `json` and `query` validators      | typed payload and query params        |
| `/files/:fileId?` (optional param) | two routes, with and without `$fileId` |
| `/posts/:postId{[0-9]+}` (regex)   | a plain `$postId`                     |
| `.all()`                           | every standard method                 |

### Realtime routes

`upgradeWebSocket()` routes work with the built-in `WebsocketAdapter` when they send `{ topic, data }` messages. They are
left out of `HonoSchema`, so nobody calls `send()` on them, and `HonoSocketPath` checks the address a socket connects to
instead.

```ts title="frontend/src/socket.ts"
// highlight-next-line
const path: HonoSocketPath<AppType> = "/ws"; // a typo is a type error

const socket = new Socket({ url: `wss://api.example.com${path}` });
const chat = createSocketSdk<typeof socket, ChatSchema>(socket);

chat.chat.$roomId.$listener
  .setParams({ roomId: "1" })
  .listen(({ data }) => console.log(data.text));
```

Hono does not type WebSocket messages, so `ChatSchema` is a socket SDK schema you write once next to the route, with
`ListenerModel` and `EmitterModel`. `streamSSE()` routes work the same way with the `ServerSentEventsAdapter`.

## Elysia

Elysia's Eden client types what a handler returns, but over HTTP a `Date` arrives as a string and `null` as an empty
body. `@hyper-fetch/elysia` types responses as they arrive, and types errors per status.

```bash npm2yarn2pnpm
npm install @hyper-fetch/core @hyper-fetch/elysia
```

<Tabs>
<TabItem value="frontend" label="Frontend">

```ts title="frontend/src/api.ts"
// highlight-next-line
const sdk = createSdk<typeof client, AppSchema>(client);

const { data, error } = await sdk.users.$userId.$get
  .setParams({ userId: "1" })
  .send();
// data is the 2xx body, error the 404 body
```

</TabItem>
<TabItem value="backend" label="Backend">

```ts title="backend/src/app.ts"
export const app = new Elysia({ prefix: "/users" })
  .get("/:userId", ({ params, status }) =>
    params.userId === "1"
      ? { id: "1", name: "Ann" }
      : status(404, { message: "Not found" }),
  )
  .post("/", ({ body, status }) => status(201, { id: "2", name: body.name }), {
    body: t.Object({ name: t.String() }),
  });

// highlight-next-line
export type AppSchema = ElysiaSchema<typeof app>;
```

</TabItem>
</Tabs>

Bodies returned with a 2xx status type `data`, and every other status types `error`, including the `422` Elysia sends
when a `body` or `query` schema rejects the input. Those schemas also type the payload and the query params.

| Handler returns                           | Typed as   |
| ----------------------------------------- | ---------- |
| A `Date`, also inside objects and arrays  | `string`   |
| `null` or `undefined`                     | `""`       |
| A generator, a stream or a raw `Response` | `unknown`  |
| A `body` schema with `t.File()` or `t.Files()` | `FormData` payload |

The package ships one type and no runtime code, and its specs run against Elysia on Node and Bun. WebSocket routes
registered with `.ws()` are left out of the schema; connect them with [`@hyper-fetch/sockets`](/docs/sockets/overview).

## Reconnects you do not have to write

The tRPC WebSocket and SSE adapters and the oRPC WebSocket and stream adapters reconnect with
`createReconnectingConnection`, the engine every socket adapter shares.

- A lost connection comes back after a backoff with jitter, bounded by `reconnectTime` and `maxReconnectTime`.
- Going offline drops the connection and pauses without counting attempts. Coming back online connects at once, and
  focusing the tab skips a pending delay.
- Every running subscription restarts with the id of its last event.
- A refused WebSocket handshake on Node.js 22 fails the attempt right away instead of waiting for `connectionTimeout`.

The [sockets post](/blog/hyper-fetch-10-sockets#one-reconnection-engine) explains the engine.

## The same request, whichever backend

Every route these packages type is a regular HyperFetch `Request`, and every subscription a regular `Listener`. The
backend decides the types, and HyperFetch keeps the behavior.

```tsx
// A tRPC query, cached for 30 seconds and retried twice
const { data } = useFetch(
  // highlight-next-line
  api.user.byId.$query.setPayload({ id: 1 }).setCacheTime(30000).setRetry(2),
);

// A Hono route, queued so submissions run one at a time
// highlight-next-line
const { submit } = useSubmit(sdk.users.$post.setQueued(true));

// A tRPC subscription, shared by every component with the same input
const { data: message, status } = useListener(
  // highlight-next-line
  realtime.chat.onMessage.$listener.setPayload({ room: "general" }),
);
```

Caching, deduplication, queueing, retries, offline support, `request.setMock()` and the devtools work the same way for
all four packages. You can move one endpoint at a time, and the rest of the app does not notice.
