Realtime streams are fast, servers restart, and RPC subscriptions need input before they send anything. HyperFetch 10
gives listeners delivery strategies, typed subscription payloads with a lifecycle, and one reconnection engine that every
socket adapter shares, in the browser, Node.js, Bun and Deno. The breaking changes are small, and most apps only need
the server rendering one.

## Highlights

- **[Delivery strategies](#delivery-strategies)**: `latest` samples and `batch` groups busy streams before they reach a render.
- **[Subscription payloads](#subscription-payloads)**: Listeners send typed input that starts a subscription on the server.
- **[Listener lifecycle](#listener-lifecycle)**: `onStart`, `onEnd` and a `status` in `useListener` show where a subscription is.
- **[Reconnection engine](#one-reconnection-engine)**: Jittered backoff that reacts to the network and the tab, for every adapter.
- **[Any runtime](#nodejs-bun-and-deno)**: The built-in adapters run in Node.js, Bun and Deno without a `window` shim.
- **[SSE named events](#sse-named-events)**: `event: tick` reaches the listeners of the `tick` topic.
- **[Listener query params](#listener-query-params)**: Filters and ordering on listeners, for adapters that support them.
- **[Typed documents](#typed-documents-on-listeners)**: A GraphQL document types a listener without generics.

## Delivery strategies

A price ticker can push hundreds of updates per second, while the screen refreshes 60 times. The `delivery` option of a
listener decides how messages reach your callbacks.

```ts title="listeners.ts"
// State-like data: only the newest value matters
export const onPrice = socket.createListener<Price>()({
  topic: "prices",
  // highlight-next-line
  delivery: { strategy: "latest", interval: 16 }, // about one animation frame
});

// Event-like data: every message must be processed
export const onTrade = socket.createListener<Trade>()({
  topic: "trades",
  // highlight-next-line
  delivery: { strategy: "batch", interval: 100, maxSize: 500 },
});
```

| Strategy | Delivers                                                                          | Options                                                       |
| -------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `latest` | The first message of an idle period at once, then the newest one per `interval`   | `leading: false` waits a full interval before the first one   |
| `batch`  | Every message of one `interval` as an array, in arrival order, with none dropped  | `maxSize` delivers early once that many messages are waiting  |

Each `listen()` call gets its own timers and buffers, and unsubscribing clears them. Without `delivery`, the callback is
registered as it is, with no wrapper and no timers.

`useListener` and the socket SDK follow the strategy of the listener. With `batch`, the hook's `data` and `onEvent` are
arrays, so one state update covers the whole window:

```tsx title="trade-log.tsx"
const { onEvent } = useListener(onTrade);

onEvent(({ data }) => {
  // One render per 100ms window instead of one per trade
  // highlight-next-line
  setTrades((previous) => [...previous, ...data].slice(-1000));
});
```

For your own rules, `createDeliveryStrategy` takes a factory that receives `deliver` and returns `push` and `dispose`.
`setDelivery()` returns a clone with another strategy, so users can pick the refresh rate at runtime.

Delivery strategies first shipped in a 9.x minor. In 10, messages still waiting in a window are delivered before `onEnd`
runs, and a typed document types the strategy, so `batch` delivers arrays of the document's data.

## Subscription payloads

tRPC, oRPC and GraphQL start one server-side subscription per input. Listeners now carry that input as a typed payload,
the second generic of `createListener`.

```ts title="jobs.ts"
type JobInput = { jobId: string };

// highlight-next-line
export const onJobProgress = socket.createListener<JobProgress, JobInput>()({
  topic: "jobs.onProgress",
});

// highlight-next-line
onJobProgress.setPayload({ jobId: "1" }).listen(({ data }) => render(data));

// For one subscription only, the listener itself stays unchanged
onJobProgress.listen(({ data }) => render(data), { payload: { jobId: "2" } });

// @ts-expect-error the payload is required
onJobProgress.listen(({ data }) => render(data));
```

- Listeners of one topic with different payloads are separate subscriptions, each receiving only its own messages.
- Listeners with an equal payload share one subscription. The last one to stop ends it on the server.
- In a socket SDK schema the payload is a field of `ListenerModel`, for example
  `ListenerModel<{ response: JobProgress; payload: JobInput; topic: "jobs.onProgress" }>`.
- The built-in WebSocket and SSE adapters route by topic and do not send the payload. It is for adapters that start
  subscriptions on the server.

## Listener lifecycle

A subscription can end on the server: a job finishes, an input fails validation, a stream completes. `listen()` now
takes `onStart` and `onEnd`.

```ts
onJobProgress.listen(({ data }) => render(data), {
  payload: { jobId: "1" },
  // highlight-start
  onStart: ({ topic }) => console.log("Server accepted", topic),
  onEnd: ({ error }) => (error ? showError(error) : showDone()),
  // highlight-end
});
```

- With tRPC, oRPC and GraphQL, `onStart` runs when the server accepted the subscription, and again after a reconnect
  restarted it. With the WebSocket and SSE adapters it runs right after `listen()`.
- `onEnd` runs once. Unsubscribing yourself does not call it.
- `socket.events.onListenerStart` and `socket.events.onListenerEnd` watch every subscription of a socket.

In React, `useListener` reports the same lifecycle as `status`, and subscribes again when the payload changes:

```tsx title="job-progress.tsx"
export function JobProgressBar({ jobId }: { jobId: string }) {
  // highlight-next-line
  const { data, status, error, listen } = useListener(
    onJobProgress.setPayload({ jobId }),
  );

  if (status === "failed")
    return <Retry message={error?.message} onClick={listen} />;
  if (status === "starting") return <Spinner />;
  return <ProgressBar value={data?.percent ?? 0} done={status === "ended"} />;
}
```

- `status` is `"idle"`, `"starting"`, `"listening"`, `"ended"` or `"failed"`.
- During server rendering the hook does not subscribe and stays `"idle"`.
- After `"ended"` or `"failed"` it stays unsubscribed until you call `listen()` or pass another listener.
- Passing a listener whose required payload is not set is a type error.

## One reconnection engine

Every adapter used to carry its own copy of the connection lifecycle, with a fixed 5 second delay and no jitter. In 10,
`createReconnectingConnection` owns the lifecycle, and adapters only open transports.

```ts title="socket.ts"
import { Socket, defaultShouldReconnect } from "@hyper-fetch/sockets";

const socket = new Socket({
  url: "wss://api.example.com",
  // The defaults, shown for reference
  reconnectTime: 1000, // the first retry comes 1 to 2 seconds after the loss
  maxReconnectTime: 30_000, // the backoff window stops growing here
  minUptime: 5000, // uptime that resets the attempt counter
  connectionTimeout: 5000, // one attempt, handshake included
  // A rejected token won't get better by retrying
  // highlight-start
  shouldReconnect: (loss) =>
    defaultShouldReconnect(loss) && loss.code !== 4401,
  // highlight-end
});
```

| When                                        | The engine                                                                         |
| ------------------------------------------- | ---------------------------------------------------------------------------------- |
| A connection is lost                        | retries with full jitter: the window doubles per attempt, each client picks a moment in it |
| A connection held for `minUptime`           | resets the attempt counter. One closed right away, say over an expired token, keeps backing off |
| The server closes with 1000                 | stays closed. Restarts (1001, 1012) and crashes are retried                       |
| The network goes offline                    | closes and pauses without counting attempts, then connects at once when back online |
| The tab gets the focus back                 | skips the rest of a pending delay                                                  |
| You call `socket.reconnect()`               | starts fresh with a reset counter, also with `reconnect: 0` or after attempts ran out |

`autoConnect` only decides the first connection, so a socket connected by hand also recovers from a dropped network.
`shouldReconnect: () => true` retries a 1000 closure too.

- `reconnectDelay` replaces the backoff. It receives the `attempt`, the `elapsed` time and the `reason`, and returns a
  delay or `null` to stop.
- Custom adapters get the same behavior by building on `createReconnectingConnection` and reporting their transport
  `ready`, `lost` or `interrupted`.
- The SSE adapter keeps the browser's own retry with `Last-Event-ID` and gives it the connection timeout to come back.

The tRPC, oRPC and GraphQL socket adapters run on this engine too. The
[backend packages post](/blog/hyper-fetch-10-backends) covers them.

## Node.js, Bun and Deno

The built-in adapters now use the runtime's global `WebSocket` and `EventSource`, or the constructor you pass in
`adapterOptions`. Sockets used to need `window`, so nothing connected on a server or in a script.

```ts title="worker.ts"
import { EventSource } from "eventsource";
import { Socket, ServerSentEventsAdapter } from "@hyper-fetch/sockets";

// Node.js has a global WebSocket since 22, but no EventSource
const socket = new Socket({
  url: "http://localhost:3000/events",
  adapter: ServerSentEventsAdapter(),
  // highlight-next-line
  adapterOptions: { EventSource },
});
```

The WebSocket adapter takes a `WebSocket` option the same way.

:::warning Server rendering

Sockets created during server rendering now connect from the server. The [upgrading section](#upgrading) shows how to
keep them in the browser.

:::

## SSE named events

Named events such as `event: tick` never reached the `message` handler of the SSE adapter. They now go to the listeners
whose topic is the event name.

```ts
// Server sends:  event: tick
//                data: {"count":1}
// highlight-next-line
const onTick = sseSocket.createListener<{ count: number }>()({ topic: "tick" });

onTick.listen(({ data }) => console.log(data.count));
```

Data that is not JSON arrives as raw text. The handlers move to the new `EventSource` after a reconnect, are removed when
the last listener of the topic leaves, and respect the `decode` option.

## Listener query params

Listeners take `queryParams` in `createListener` and `setQueryParams()`, for adapters that declare them, such as the
Firebase socket adapters.

```ts
// Firebase: green teas only, newest first
const onGreenTeas = socket
  .createListener<Tea[]>()({ topic: "teas" })
  // highlight-next-line
  .setQueryParams((c) => c.where("type", "==", "Green").orderBy("year", "desc"));
```

The adapter turns a callback into data as soon as it is set, so the listener never holds a function. Query params say
what to receive, and the payload is what the server needs to start. The WebSocket and SSE adapters declare no listener
query params, so `setQueryParams` does not compile for them.

## Typed documents on listeners

`createListener()` reads the `__apiType` decoration that graphql-codegen and gql.tada put on their documents. With the
`GraphqlWsAdapter`, the document alone types the data and the payload:

```ts
const onMessage = graphqlSocket.createListener()({
  topic: "OnMessage",
  // highlight-next-line
  options: { document: OnMessageDocument },
});

onMessage
  .setPayload({ room: "general" })
  .listen(({ data }) => data.onMessage.text);
```

Declared generics still win, and adapters without typed options are unchanged. The
[GraphQL post](/blog/hyper-fetch-10-graphql) covers the adapter.

## Reliability fixes

- Sockets reconnect when the network comes back. The socket never started its app manager, so online and offline events
  went unnoticed. In React Native or Node.js, pass your own with the `appManager` option.
- A manual `disconnect()` sticks: no reconnect after a close while connecting, after going online, or from a pending SSE
  attempt.
- A transport that was already open when created no longer reconnects when the attempt timeout fires.
- A WebSocket handshake that Node.js 22 refuses with only an `error` event is retried at once, and `disconnect()` no
  longer waits for a close that never comes.
- Closing a WebSocket wrapped by a library such as msw closes the real connection on the server.
- `disconnect()` inside `onConnected` leaves no uptime or heartbeat timers behind, so no false heartbeat timeouts fire.
- A pong timeout marks the socket disconnected right away.
- `connect()` resolves once the connection is open, also when it joins an attempt in progress.
- One throwing listener no longer stops the other listeners of its topic.
- Emit failures from interceptors, payload mappers, encoders or a closed connection reach the emitter error event
  instead of becoming unhandled rejections. Async payload mappers are awaited.
- Topic params: `:id` no longer matches inside `:idx`, and setting params again replaces the topic.
- `useListener` follows the socket of the listener, so a listener of another socket with the same topic subscribes
  there.
- `socket.destroy()` removes the online listeners of the adapter.

## Upgrading

The breaking changes are all in `@hyper-fetch/sockets`. Most apps only need the server rendering one.

| Change                   | Before                                                     | After                                                                      |
| ------------------------ | ---------------------------------------------------------- | -------------------------------------------------------------------------- |
| Server rendering         | Sockets connected only through `window`                    | Sockets connect wherever a global `WebSocket` exists                       |
| Reconnect timing         | `reconnectTime` was the delay and the attempt limit, 5s    | `reconnectTime` is the minimum delay, 1s. `connectionTimeout` limits an attempt, 5s |
| `onMessage` interceptors | Received `{ event }`                                       | Receive `{ event, topic, extra }`                                          |
| Listener generics        | `Listener<Response, Topic, Socket, HasParams, Delivered>`  | `Listener<Response, Payload, Topic, Socket, HasPayload, HasParams, Delivered>` |

### Server rendering

Sockets connect wherever a global `WebSocket` exists, Node.js 22+ included. Turn off the automatic connection outside
the browser:

```ts
const socket = new Socket({
  url: "wss://api.example.com",
  // highlight-next-line
  adapterOptions: { autoConnect: typeof window !== "undefined" },
});
```

### Connection timeout and reconnect delay

`reconnectTime` used to be both the delay between attempts and how long one attempt could take, 5 seconds by default.
It is now only the minimum delay, 1 second by default, and grows with backoff up to `maxReconnectTime`.
`connectionTimeout` (5 seconds by default) limits each attempt.

<Tabs>
<TabItem value="before" label="Before">

```ts
const socket = new Socket({
  url,
  reconnectTime: 10_000,
});
```

</TabItem>
<TabItem value="after" label="After">

```ts
const socket = new Socket({
  url,
  reconnectTime: 10_000, // minimum delay before an attempt
  // highlight-next-line
  connectionTimeout: 10_000, // how long one attempt may take
});
```

</TabItem>
</Tabs>

To keep a fixed delay, return it from `reconnectDelay: () => 5000`.

### onMessage interceptors

`onMessage` interceptors receive `{ event, topic, extra }`, where `extra` is the adapter extra, such as the
`MessageEvent`. Interceptors that read only `event` keep working.

```ts
socket.onMessage(({ event, topic }) =>
  topic === "prices" ? roundPrice(event) : event,
);
```

### Listener generics

`Listener` gained the payload and its flag. Prefer `ListenerInstance<{ response: Price }>` for constraints and
`ListenerModel` in SDK schemas: both read the fields by name and do not change with the generic order.

<Tabs>
<TabItem value="before" label="Before">

```ts
type PriceListener = Listener<Price, "prices", typeof socket, false, Price>;
```

</TabItem>
<TabItem value="after" label="After">

```ts
type PriceListener = Listener<
  Price,
  // highlight-next-line
  undefined, // Payload
  "prices",
  typeof socket,
  // highlight-next-line
  false, // HasPayload
  false, // HasParams
  Price
>;
```

</TabItem>
</Tabs>

- `ListenType` takes `<Payload, HasPayload, Socket, Delivered>` instead of `<Listener, Socket>`.
- For custom adapters, `ListenerOfAdapter` holds only the listener data they read: `topic`, `params`, `payload`,
  `options`, `queryParams`, `delivery`, `socket` and `listenerOptions`.
