# Listener

A **`Listener`** describes one topic you receive from the server and the type of its messages. Like a
[Request](/docs/core/request), it is a template: define it once next to the [socket](/docs/sockets/socket), then derive
concrete listeners with params, a payload or a delivery strategy.

```ts title="listeners.ts"
import { socket } from "./socket";

type ChatMessage = { id: string; author: string; text: string };

export const onChatMessage = socket.createListener<ChatMessage>()({
  topic: "chat",
});

const unlisten = onChatMessage.listen(({ data, extra }) => {
  // data: ChatMessage, extra: the adapter's details, such as the MessageEvent
  console.log(data.author, data.text);
});

unlisten(); // stop listening
```

`createListener` is called twice: the first call takes the message type, the second the options, so the topic stays a
literal type.

:::tip Purpose

1. **Typed messages**: `data` has the type you declared, for every adapter.
2. **Reusable templates**: params, payload and delivery derive new listeners without changing the original.
3. **Throttling built in**: fast topics deliver the latest message or batches instead of every message.
4. **Clean unsubscribing**: `listen()` returns the function that stops it.

:::

## Stop listening

`listen()` returns a function that removes this subscription. Call it when you no longer need the messages, for
example when a screen closes. To handle only the next message, call it inside the callback.

```ts title="once.ts"
const unlisten = onChatMessage.listen(({ data }) => {
  console.log("First message:", data.text);
  unlisten();
});
```

In React, [`useListener`](/docs/react/sockets/use-listener) subscribes on mount and unsubscribes on unmount.

## Address one resource with topic params

Put params in the topic with a colon, such as `:roomId`. `setParams` fills them in and returns a new listener. Each
param combination is its own topic: topics match exactly, without prefixes or wildcards.

```ts title="rooms.ts"
export const onRoomMessage = socket.createListener<ChatMessage>()({
  topic: "rooms/:roomId",
});

// topic "rooms/general"
onRoomMessage
  .setParams({ roomId: "general" })
  .listen(({ data }) => console.log(data.text));
// topic "rooms/random"
onRoomMessage
  .setParams({ roomId: "random" })
  .listen(({ data }) => console.log(data.text));
```

Param names come from the topic string, so a missing or misspelled param is a type error.

---

## Throttle or batch fast topics

Prices, cursors and logs can arrive hundreds of times per second. The `delivery` option decides how messages reach
callbacks, inside the listener, so `listen()`, `useListener` and the SDK all follow it. Without `delivery`, every message
is delivered right away with no overhead.

```ts title="market.ts"
// The first message at once, then at most one, the newest, per 16 ms
export const onPrice = socket.createListener<Price>()({
  topic: "prices",
  delivery: { strategy: "latest", interval: 16 },
});

// Every message, as an array per 100 ms window
export const onTrade = socket.createListener<Trade>()({
  topic: "trades",
  delivery: { strategy: "batch", interval: 100, maxSize: 500 },
});

onTrade.listen(({ data }) => console.log(data.length)); // data: Trade[]
```

|                 | `latest`                                 | `batch`                                     | custom (`createDeliveryStrategy`) |
| --------------- | ---------------------------------------- | ------------------------------------------- | --------------------------------- |
| Callback `data` | `Response`                               | `Response[]`                                | your output type                  |
| Drops messages  | Yes, the ones in between                 | Never                                       | Up to you                         |
| Options         | `interval`, `leading` (default `true`)   | `interval`, `maxSize` (default `Infinity`)  | -                                 |

- Every `listen()` gets its own buffers and timers. Unsubscribing clears them and drops pending messages.
- `extra` is the `extra` of the last message in the delivery.
- `setDelivery` returns a clone with another strategy. Pass `undefined` to deliver every message again.
- `socket.events.onListenerEvent` still receives every raw message, for logging and devtools.

The [throttling and batching guide](/docs/guides/sockets/throttling) has timelines and custom strategies.

## Start a server-side subscription with a payload

Some servers need data to start a subscription, such as the input of a tRPC subscription, the variables of a GraphQL
subscription or the input of an oRPC event iterator. This is the subscription payload: pass its type as the second
generic and set it with `setPayload`, or for one subscription in `listen`.

```ts title="chat.ts"
export const onMessage = socket.createListener<
  ChatMessage,
  { roomId: string }
>()({ topic: "chat.onMessage" });

onMessage
  .setPayload({ roomId: "1" })
  .listen(({ data }) => console.log(data.text));
onMessage.listen(({ data }) => console.log(data.text), {
  payload: { roomId: "2" },
});
```

- A required payload must be set before listening. `listen` without it is a type error.
- Listeners of one topic with different payloads are separate subscriptions. Listeners with an equal payload share one.
- The tRPC, oRPC and GraphQL socket adapters send the payload. The WebSocket and SSE adapters route by topic and ignore
  it.
- A typed document in the listener options, such as the `document` of the
  [GraphQL adapter](/docs/integrations/adapter-graphql/subscriptions), types the response and payload without generics.

## Follow the subscription lifecycle

`listen` takes `onStart` and `onEnd`. They matter for adapters where the server starts and ends each subscription, such
as tRPC and oRPC.

```ts title="job-progress.ts"
onJobProgress.listen(({ data }) => console.log(data.percent), {
  payload: { jobId: "1" },
  onStart: ({ topic }) => console.log("Server accepted", topic),
  onEnd: ({ error }) => console.log(error ? "Failed" : "Finished"),
});
```

- `onStart` runs when the server confirmed the subscription, and again after a reconnect restarted it. With the
  WebSocket and SSE adapters, it runs right after `listen()`.
- `onEnd` runs once, when the server ended the subscription. `error` is `null` when it finished normally. Pending
  delivered messages are flushed first, then the listener unsubscribes.
- Unsubscribing yourself does not call `onEnd`.

## Filter with listener query params

Adapters that support it, such as the [Firebase adapter](/docs/integrations/adapter-firebase/realtime-queries), let a
listener ask for filters, order or limits with `setQueryParams`. A callback is turned into data as soon as it is set.

```ts title="teas.ts"
const onGreenTeas = firebaseSocket
  .createListener<Tea[]>()({ topic: "teas" })
  .setQueryParams((c) => c.where("type", "==", "Green").orderBy("year", "desc"));
```

These are separate from the socket's own `queryParams`, which belong to the connection URL. The WebSocket and SSE
adapters have no listener query params, so `setQueryParams` does not compile for them.

## Keep the HTTP cache in sync

A realtime update can write straight into the cache of a [request](/docs/core/request), so every component that shows
it updates without a refetch.

```ts title="notes.ts"
const getNote = client.createRequest<{ response: Note }>()({
  endpoint: "/notes/:noteId",
});
const onNoteChange = socket.createListener<Note>()({ topic: "notes" });

onNoteChange.listen(({ data }) => {
  client.cache.update(getNote.setParams({ noteId: data.id }), { data });
});
```

To observe every message of a socket, use `socket.events.onListenerEvent` and filter on `topic`.
`socket.events.onListenerEventByTopic(listener, callback)` matches the listener's exact topic string, so pass a listener
with its params set, not a template like `"notes/:noteId"`.

---

## Setters return clones

`setParams`, `setPayload`, `setOptions`, `setQueryParams` and `setDelivery` return a new listener and leave the
original unchanged. Use the returned value.

```ts title="clones.ts"
// error-next-line
onRoomMessage.setParams({ roomId: "general" }); // the result is discarded
onRoomMessage.listen(callback); // listens on the literal topic "rooms/:roomId"

onRoomMessage.setParams({ roomId: "general" }).listen(callback); // OK
```

## TypeScript

A listener carries the **response type** (what arrives on the wire) and the **delivered type** (what callbacks
receive). They differ only when a delivery strategy changes the shape, and both are inferred.

```ts title="types.ts"
import type {
  ExtractListenerDeliveredType,
  ExtractListenerPayloadType,
  ExtractListenerResponseType,
} from "@hyper-fetch/sockets";

type Wire = ExtractListenerResponseType<typeof onTrade>; // Trade
type Delivered = ExtractListenerDeliveredType<typeof onTrade>; // Trade[]
type Payload = ExtractListenerPayloadType<typeof onMessage>; // { roomId: string }
```

Type `createListener<ChatMessage>()`, not `createListener<{ response: ChatMessage }>()`: the generic is the message
itself. For reusable helpers, constrain with `ListenerInstance<{ response: Trade }>`, or
`ListenerInstance<{ delivered: Trade[] }>` to constrain what callbacks receive.

---

:::secondary Summary

- Define a listener once per topic with `createListener<Response>()({ topic })`.
- Fill topic params with `setParams` and the subscription payload with `setPayload`, and use the returned clone.
- Add `delivery` to fast topics instead of throttling in components.
- Always call the function `listen()` returns, or use `useListener`.

:::
