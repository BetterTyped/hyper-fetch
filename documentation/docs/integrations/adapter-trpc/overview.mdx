# tRPC client with React hooks and caching

[Read the API Reference »](/docs/api/adapter-trpc/Functions/TrpcAdapter.mdx)

`@hyper-fetch/trpc` is a tRPC client for HyperFetch. You keep your tRPC server and router as they are, and the frontend
calls procedures through the same `createRequest`, `send()` and React hooks you use for REST and GraphQL. Types come
from your `AppRouter`, and every call gets caching, deduplication, retries and offline queues.

:::tip Purpose

1. **Call tRPC procedures** with the same request API you use for REST and GraphQL.
2. **Infer types from your router** through the regular `createSdk`.
3. **Cache every input separately**, without writing query keys by hand.
4. **Support transformers** such as `superjson`.
5. **Listen to subscriptions** over WebSocket or Server-Sent Events with the
   [socket adapters](/docs/integrations/adapter-trpc/subscriptions.mdx).

:::

---

## What is tRPC

tRPC is a way to call server functions from a TypeScript client without writing an API schema. The server defines a
router of procedures, and the client imports only the router's type. When you rename a procedure or change its input,
the client stops compiling. There is no code generation step and no OpenAPI file to keep in sync.

There are three kinds of procedures:

| Procedure      | What it does                    | How it goes over the wire                     |
| -------------- | ------------------------------- | --------------------------------------------- |
| `query`        | Reads data                      | `GET` with the input in the `input` param     |
| `mutation`     | Changes data                    | `POST` with the input as a JSON body          |
| `subscription` | Streams events to the client    | WebSocket or Server-Sent Events               |

tRPC fits best when the frontend and backend are both TypeScript and live in one repo, so the client can import the
router type. If other teams or languages call your API, a REST or GraphQL schema is usually the better contract.

---

## tRPC and React Query

The official React integration of tRPC is built on TanStack Query, so "trpc react query" is how most people meet it.
TanStack Query owns the cache and you work with query keys and query options generated from the router.

This adapter is a different client for the same server. HyperFetch owns the cache, the queue and the hooks, and the
request object is the key. You pass `api.user.byId.$query.setPayload({ id: 1 })` to `useFetch` and the input becomes
part of the cache key, so there is nothing to write by hand. Pick it when you want one client for tRPC, REST, GraphQL
and sockets, or when you need offline queues and request cancellation that work the same for every backend.

## tRPC with Next.js

With the Next.js App Router, the tRPC router is usually mounted through tRPC's fetch adapter in a route handler, for
example `app/api/trpc/[trpc]/route.ts`. The server side does not change for HyperFetch. Point the client at the path
where the handler lives:

```ts
import { createClient, createSdk } from "@hyper-fetch/core";
import { TrpcAdapter } from "@hyper-fetch/trpc";
import type { TrpcSchema } from "@hyper-fetch/trpc";

import type { AppRouter } from "@/server/router";

export const client = createClient({ url: "/api/trpc" }).setAdapter(TrpcAdapter());

export const api = createSdk<typeof client, TrpcSchema<AppRouter>>(client, { camelCaseToKebabCase: false });
```

A relative URL works in the browser. Code that runs on the server, such as a route handler or a server component that
calls another service, needs the absolute URL, for example from an environment variable.

## Installation

Install the adapter next to the core package. `@trpc/server` is only needed for the `TrpcSchema` type, and your project
that imports the `AppRouter` type usually has it already.

```bash
npm install @hyper-fetch/core @hyper-fetch/trpc
```

## Getting Started

Point the client at the URL where your tRPC handler is mounted, and describe the router with `TrpcSchema`.

```ts
import { createClient, createSdk } from "@hyper-fetch/core";
import { TrpcAdapter } from "@hyper-fetch/trpc";
import type { TrpcSchema } from "@hyper-fetch/trpc";

import type { AppRouter } from "./server";

const client = createClient({ url: "http://localhost:3000/trpc" }).setAdapter(TrpcAdapter());

const api = createSdk<typeof client, TrpcSchema<AppRouter>>(client, { camelCaseToKebabCase: false });

const { data, error } = await api.user.byId.$query.setPayload({ id: 1 }).send();
```

`camelCaseToKebabCase: false` keeps procedure names as they are written in the router (`byId`, not `by-id`).

---

## Queries

Queries are available under `$query`. The procedure input is the request payload.

```tsx
import { useFetch } from "@hyper-fetch/react";

const { data, loading } = useFetch(api.user.byId.$query.setPayload({ id: 1 }));
```

They are sent as `GET {url}/user.byId?input={"id":1}`, with the input URL-encoded. Like `GET` requests in the
`HttpAdapter`, identical queries running at the same time are deduplicated by default.

---

## Mutations

Mutations are available under `$mutation` and are sent as `POST {url}/user.create` with a JSON body.

```tsx
import { useSubmit } from "@hyper-fetch/react";

const { submit } = useSubmit(api.user.create.$mutation);

await submit({ payload: { name: "John" } });
```

---

## Requests without the SDK

The SDK is optional. `QUERY` and `MUTATION` are the methods of this adapter, and the endpoint is the procedure path.

```ts
const getUser = client.createRequest<{ response: User; payload: { id: number } }>()({
  endpoint: "user.byId",
  method: "QUERY",
});

const createUser = client.createRequest<{ response: User; payload: { name: string } }>()({
  endpoint: "user.create",
  method: "MUTATION",
});
```

`QUERY` is the default method. The paths `user.byId` and `/user/byId` point to the same procedure and share the cache.

---

## Cache keys

The adapter adds the input to the cache and query keys, so `{ id: 1 }` and `{ id: 2 }` are cached, deduplicated and
queued separately. The abort key does not contain the input, so `request.abort()` stops every running call of the
procedure.

A `cancelable` request replaces the running call with the same query key, which means the same input. To cancel the
previous call when the input changes, for example in a search field, share the query key between the inputs.

```ts
const search = api.user.search.$query.setCancelable(true).setDeduplicate(false).setQueryKey("user-search");
```

## Errors

Failed procedures resolve with the error sent by the server and the HTTP status of the response.

```ts
const { error, status, extra } = await api.user.byId.$query.setPayload({ id: 999 }).send();

status; // 404
error?.message; // "User not found"
error?.code; // -32004
error?.data.code; // "NOT_FOUND"
error?.data.httpStatus; // 404
extra?.headers; // response headers
```

With `TrpcSchema` the error type follows the router, including a custom `errorFormatter`. For requests created by hand,
use the exported `TrpcErrorType`.

A response that did not come from a procedure, such as an HTML error page from a proxy, resolves with an `UnexpectedError`
and the status of that response.

## Transformers

Pass the same transformer that the server uses in `initTRPC.create()`. It handles the input, the output and the errors.

```ts
import superjson from "superjson";

const client = createClient({ url: "http://localhost:3000/trpc" }).setAdapter(
  TrpcAdapter({ transformer: superjson }),
);

const { data } = await api.event.byDate.$query.setPayload({ date: new Date() }).send();

data?.createdAt; // Date
```

Any object with `serialize` and `deserialize` methods works. When the server uses separate transformers for each
direction, pass `{ serialize: input.serialize, deserialize: output.deserialize }`.

---

## Options

Request options are passed to `fetch`, with an additional `timeout` in milliseconds (5 seconds by default).

```ts
const getUser = client.createRequest<{ response: User }>()({
  endpoint: "user.me",
  options: { credentials: "include", timeout: 10000 },
});
```

Query params are appended to the URL. The `input` and `batch` keys are reserved for the tRPC format and are skipped.

## Limitations

- Request batching is not supported.
- Subscriptions are not requests, so they are left out of `TrpcSchema`. Listen to them with a `Socket` and the
  [tRPC socket adapters](/docs/integrations/adapter-trpc/subscriptions.mdx).
- A `null` payload removes the payload, so the procedure receives no input. Procedures that need a `null` input
  should take an object instead, for example `{ value: null }`.
- The SDK can't reach a procedure named like a request property, such as `send` or `method`. Use `createRequest` with
  the procedure path for those.
