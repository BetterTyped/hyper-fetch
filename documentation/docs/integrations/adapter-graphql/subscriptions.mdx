# GraphQL subscriptions in React over WebSocket

A GraphQL subscription is an operation the server keeps answering: you subscribe once and get a result for every event,
such as a new message. `GraphqlWsAdapter` connects a HyperFetch [Socket](/docs/sockets/socket) to the server, and each
subscription document becomes a typed [Listener](/docs/sockets/listener) whose payload is the variables.

:::tip Purpose

1. **Listen to subscriptions** with the `Socket`, `Listener` and `useListener` API of other realtime sources.
2. **Speak `graphql-transport-ws`**, the `graphql-ws` protocol of Apollo Server, GraphQL Yoga, Mercurius, Hot Chocolate
   and Hasura.
3. **Share one server subscription** between listeners with the same document and variables.
4. **Recover on its own**: reconnect with backoff, fresh connection params and every subscription sent again.

:::

---

## Anatomy of a GraphQL subscription

```graphql title="OnMessage.graphql"
subscription OnMessage($room: String!) {
  onMessage(room: $room) {
    id
    text
  }
}
```

A subscription looks like a query with `subscription` in front and exactly one top-level field. It needs a connection
that stays open, so the server can push a result per event. With `graphql-transport-ws` the client sends
`connection_init` with optional params such as a token, then one `subscribe` message per subscription. The server
answers with `next` messages, and `complete` when it ends.

---

## Listen to a subscription

The adapter ships in `@hyper-fetch/graphql` and needs `@hyper-fetch/sockets`, see the
[install step](/docs/integrations/adapter-graphql/overview#install). Create a `Socket` with the adapter, then a listener
per subscription with the `document` option. The variables are the payload.

```ts title="socket.ts"
import { Socket } from "@hyper-fetch/sockets";
import { GraphqlWsAdapter } from "@hyper-fetch/graphql";
import gql from "graphql-tag";

export const socket = new Socket({ url: "ws://localhost:4000/graphql", adapter: GraphqlWsAdapter() });

type Message = { onMessage: { id: string; text: string } };

export const onMessage = socket.createListener<Message, { room: string }>()({
  topic: "OnMessage",
  options: {
    document: gql`
      subscription OnMessage($room: String!) {
        onMessage(room: $room) {
          id
          text
        }
      }
    `,
  },
});

const stop = onMessage.setPayload({ room: "general" }).listen(({ data }) => console.log(data.onMessage.text));
```

- The `topic` names the listener in devtools and `socket.events`. The operation name is a good choice.
- Without `document`, the `topic` is sent as the document: `socket.createListener()({ topic: "subscription { tick }" })`.
- Queries and mutations stay on the [`GraphqlAdapter`](/docs/integrations/adapter-graphql/overview). `emit()` throws.

---

## Typed documents

A typed document from GraphQL Code Generator or gql.tada types the listener's data and variables on its own. Generics
passed to `createListener` win over it.

```ts title="socket.ts"
import { OnMessageDocument } from "./gql/graphql"; // generated

export const onMessage = socket.createListener()({ topic: "OnMessage", options: { document: OnMessageDocument } });

onMessage.setPayload({ room: "general" }).listen(({ data }) => data.onMessage.text);
```

## Subscriptions in React

[`useListener`](/docs/react/sockets/use-listener) starts the subscription on mount, restarts it when the variables
change and stops it on unmount. In `StrictMode` the server still sees one subscription.

```tsx title="ChatRoom.tsx"
import { useListener } from "@hyper-fetch/react";

import { onMessage } from "./socket";

export const ChatRoom = ({ room }: { room: string }) => {
  const { data, status, error } = useListener(onMessage.setPayload({ room }));

  if (status === "failed") return <p>{error?.message}</p>;

  return (
    <div>
      <p>{status === "listening" ? "Live" : "Connecting..."}</p>
      <p>{data?.onMessage.text}</p>
    </div>
  );
};
```

`status` is `"idle"`, `"starting"` until the subscription is sent over an acknowledged connection, `"listening"`, then
`"ended"` when the server completes it or `"failed"` with the `error`. Call `listen()` from the hook to subscribe again.

---

## Share one subscription between listeners

A document with one set of variables is one server subscription. Listeners with the same document and variables share
it: the first one starts it and the last one to stop sends `complete`.

```ts title="chat.ts"
const general = onMessage.setPayload({ room: "general" });

general.listen(renderMessages);
general.listen(playSound); // same server subscription
onMessage.setPayload({ room: "random" }).listen(renderMessages); // a second one
```

Each event carries its variables in `extra.payload`, so events of different subscriptions can be told apart where they
meet, like `socket.events.onListenerEvent`.

---

## Errors

GraphQL reports subscription errors in two ways, and the adapter keeps them apart:

- **Errors of one event** come in `extra.errors`, next to the partial `data`. The subscription keeps running.
- **Errors of the subscription** end it. The server sent the `error` message, and the listener ends with a
  `GraphqlSubscriptionError` (`errors`, `topic`, `payload`), which also reaches `socket.onError`.

```ts title="chat.ts"
import { GraphqlSubscriptionError } from "@hyper-fetch/graphql";

onMessage.setPayload({ room: "general" }).listen(
  ({ data, extra }) => {
    if (extra.errors) console.warn("partial event", extra.errors);
  },
  {
    onEnd: ({ error }) => {
      if (error instanceof GraphqlSubscriptionError) console.error(error.errors, error.payload);
    },
  },
);
```

A subscription the server can't execute at all, for example with missing variables, gets one event with errors and
`null` data, then completes. Messages that break the protocol close the connection with `4004` and reach
`socket.onError`.

---

## Subscription lifecycle

The protocol has no confirmation, so a subscription counts as started once it is sent over an acknowledged connection.
`listen()` takes `onStart` and `onEnd`.

```ts title="chat.ts"
onMessage.setPayload({ room: "general" }).listen(renderMessages, {
  onStart: ({ topic }) => {}, // sent to the server, and again after every reconnect
  onEnd: ({ topic, error }) => {}, // completed (error is null) or failed with a GraphqlSubscriptionError
});
```

- A listener that joins a running subscription gets `onStart` right away.
- On the end, events pending in a `delivery` strategy are delivered first, then `onEnd` runs.
- An ended subscription is never restarted by a reconnect. Unsubscribing yourself does not call `onEnd`.

## Connection

The connection is open once the server acknowledged `connection_init`. The socket's `connectionTimeout` covers the
handshake and the acknowledgement, and subscriptions started earlier wait for it.

### Connection params

`connectionParams` are sent with `connection_init`, and `graphql-ws` servers read them as `ctx.connectionParams`. A
function runs on every connection attempt, so a reconnect sends a fresh token. When it throws, the connection closes
with `4005` and is not retried.

```ts title="socket.ts"
export const socket = new Socket({
  url: "wss://api.example.com/graphql",
  adapter: GraphqlWsAdapter(),
  adapterOptions: { connectionParams: async () => ({ token: await auth.getFreshToken() }) },
});
```

### Reconnecting

A lost connection reconnects with the socket's [reconnection options](/docs/guides/sockets/connection), and every
running subscription is sent again once the new connection is acknowledged. Close codes a retry can't fix stop it, the
same ones the `graphql-ws` client gives up on:

| Close code                                                   | Reconnects |
| ------------------------------------------------------------ | ---------- |
| `1000` normal closure                                        | no         |
| `1001`, `1005`, `1006`, `1012`-`1014`                        | yes        |
| other `1xxx` codes, for example `1002`, `1011`               | no         |
| `4400`, `4401`, `4004`, `4005`, `4406`, `4409`, `4429`, `4500` | no       |
| `4403` forbidden, `4408` and `4504` timeouts                 | yes        |
| everything else, for example `4499`, `3000`                  | yes        |

The socket's `shouldReconnect` replaces these rules. Call `shouldReconnectGraphqlWs` from yours to keep them:

```ts title="socket.ts"
import { GraphqlWsAdapter, shouldReconnectGraphqlWs } from "@hyper-fetch/graphql";

export const socket = new Socket({
  url: "wss://api.example.com/graphql",
  adapter: GraphqlWsAdapter(),
  // also retry after 4401, the connectionParams function fetches a fresh token
  shouldReconnect: (loss) => loss.code === 4401 || shouldReconnectGraphqlWs(loss),
});
```

### Keep-alive and lazy connections

The adapter always answers the server's `ping`. Turn on `keepAlive` to notice a connection that died without a close,
for example behind a proxy. With `lazy`, the connection opens with the first subscription and closes after the last one.

```ts title="socket.ts"
export const socket = new Socket({
  url: "wss://api.example.com/graphql",
  adapter: GraphqlWsAdapter(),
  adapterOptions: { keepAlive: { enabled: true }, lazy: true, lazyCloseTimeout: 3000 },
});
```

## Options

Adapter options, passed as `adapterOptions` to the `Socket`:

| Option             | Type                             | Default | Description                                                            |
| ------------------ | -------------------------------- | ------- | ---------------------------------------------------------------------- |
| `autoConnect`      | `boolean`                        | `true`  | Connect when the socket is created. Ignored with `lazy`.               |
| `lazy`             | `boolean`                        | `false` | Hold a connection only while there are subscriptions.                  |
| `lazyCloseTimeout` | `number`                         | `0`     | With `lazy`, how long the connection stays after the last one, in ms.  |
| `connectionParams` | `object \| () => object`         | -       | Sent with `connection_init`. A function runs on every attempt.         |
| `keepAlive`        | `{ enabled, intervalMs?, pongTimeoutMs? }` | off | Ping after `intervalMs` (default `10000`) of quiet, wait `pongTimeoutMs` (default `5000`) for `pong`. |
| `WebSocket`        | `typeof WebSocket`               | global  | The `WebSocket` class, for example from `ws` before Node.js 22.        |

Listener option: `document` (`string | DocumentNode`), the subscription document. Without it the `topic` is sent.

---

## Limits

- Only `graphql-transport-ws` is supported. The deprecated `subscriptions-transport-ws` protocol (subprotocol
  `graphql-ws`) is not.
- Queries and mutations go over HTTP with the `GraphqlAdapter`, not over the WebSocket.
- Incremental delivery (`@defer`, `@stream`) results are delivered as they arrive, without merging.

---

:::secondary Summary

- `GraphqlWsAdapter()` turns subscription documents into typed listeners, with the variables as the payload.
- Listeners with the same document and variables share one server subscription.
- Event errors come in `extra.errors`. Subscription errors end it with a `GraphqlSubscriptionError`.
- The connection reconnects with fresh connection params and sends every subscription again.

:::
