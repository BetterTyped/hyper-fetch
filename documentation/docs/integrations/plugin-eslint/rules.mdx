# ESLint rules for typed requests and clients

The HyperFetch ESLint plugin has two rules. Both check the first generic passed to a HyperFetch factory and report what
TypeScript lets through: every generic key is optional, so next to any valid key a typo like `rsponse` is legal and the
data quietly falls back to the default type.

| Rule                                              | Description                                                    | Recommended | Fixable |
| ------------------------------------------------- | -------------------------------------------------------------- | ----------- | ------- |
| [`client-generic-types`](#client-generic-types)   | Checks the generic of `createClient` from `@hyper-fetch/core` | Yes         | No      |
| [`request-generic-types`](#request-generic-types) | Checks the generic of every `.createRequest<...>()` call      | Yes         | No      |

---

## What both rules report and accept

Both rules report:

- **Unexpected keys**: any key the factory does not accept. All unknown keys are listed in one report.
- **Empty generics**: `<{}>`, which sets nothing.
- **Non-object generics**: a keyword, union or other type where an object is expected, such as `<unknown>`.

Both rules accept:

- **Type references** such as `createRequest<RequestType>()`. TypeScript already checks those against the constraint.
- **Intersections** such as `createRequest<GqlResponse<User> & { payload: Input }>()`. Each object part is checked, and
  references inside it are trusted.
- **Quoted keys** such as `{ "response": User }`, which count the same as `{ response: User }`.

Neither rule has options or an autofix: the right key depends on what you meant.

---

## client-generic-types

Checks the generic of `createClient` when it is imported from `@hyper-fetch/core` by name, alias or namespace. A
`createClient` from another library is ignored. The only allowed key is `error`, the global error type of the
[client](/docs/core/client).

```ts title="api/client.ts"
import { createClient } from "@hyper-fetch/core";

// error-next-line
const typo = createClient<{ eror: ApiError }>({ url: "http://localhost:3000" });
// Unexpected generic type(s) found: eror

// error-next-line
const empty = createClient<{}>({ url: "http://localhost:3000" });
// Generic type provided to createClient is empty

// error-next-line
const notObject = createClient<unknown>({ url: "http://localhost:3000" });
// Generic type provided to createClient is not matching the expected object-like format

// Correct
const client = createClient<{ error: ApiError }>({ url: "http://localhost:3000" });
```

It only reads `createClient` calls from `@hyper-fetch/core`, so it has no false positives to turn it off for.

---

## request-generic-types

Checks the generic of every `.createRequest<...>()` call. The allowed keys are `response`, `payload`, `error`,
`queryParams`, `endpoint` and `params`, matching `RequestGenericType` in `@hyper-fetch/core`.

```ts title="api/users.ts"
// error-next-line
const getUser = client.createRequest<{ rsponse: User; eror: ApiError }>()({
  endpoint: "/users/:id",
});
// Unexpected generic type(s) found: rsponse, eror

// error-next-line
const listUsers = client.createRequest<{}>()({ endpoint: "/users" });
// Generic type provided to createRequest is empty

// Correct
const getUserById = client.createRequest<{ response: User; params: { id: number } }>()({
  endpoint: "/users/:id",
});
```

The rule matches the method name, so a `createRequest` method on an object that is not a HyperFetch client is checked
too. Turn it off for those files if their generics use other keys.
