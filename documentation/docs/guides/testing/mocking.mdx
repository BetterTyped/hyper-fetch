A mock replaces the network call of a request with a response you control, so tests are fast, deterministic and need no
backend. In HyperFetch you attach it with `request.setMock()`, typed by the request itself. This guide covers mocks on
single requests, timings and errors, a test SDK with all mocks in one place, and MSW.

:::secondary What you'll learn

1. How to **mock a request** with `setMock` and remove the mock.
2. How to mock **errors, delays and timeouts**.
3. How to **centralize mocks** in a test SDK and override them per test.
4. When to use **MSW** instead.

:::

---

## Mock a request

`setMock` takes a function that receives `{ request, requestId }` and returns a response: a `status` plus `data` for a
success or `error` for a failure. The returned values are checked against the request's types.

```ts title="src/api/users.test.ts"
import { getUsers } from "./users";

afterEach(() => getUsers.clearMock());

it("returns the mocked users", async () => {
  getUsers.setMock(() => ({ data: [{ id: 1, name: "Ann" }], status: 200 }));

  const { data, success } = await getUsers.send();

  expect(success).toBe(true);
  expect(data).toEqual([{ id: 1, name: "Ann" }]);
});
```

The mock replaces only the adapter call. Interceptors, mappers, deduplication, retries, cache writes and lifecycle
callbacks run as with a real server.

`setMock` is the one setter that changes the request instance instead of returning a copy, so the mock stays on the
exported request until `clearMock()`. `setMockingEnabled(false)` turns one request's mock off, and
`client.setEnableGlobalMocking(false)` turns off every mock of the client.

## Mock errors, delays and timeouts

Return `error` and a status to test failure states. The function can read the request, for example its params, and can
be async.

```ts title="src/api/users.test.ts"
// A 404 for every user except 1
getUser.setMock(({ request }) =>
  request.params?.userId === 1
    ? { data: { id: 1, name: "Ann", email: "ann@example.com" }, status: 200 }
    : { error: { message: "Not found", code: "NOT_FOUND" }, status: 404 },
);
```

The second argument controls timing:

| Option            | Default | Simulates                                                  |
| ----------------- | ------- | ---------------------------------------------------------- |
| `requestTime`     | `20`    | Upload time in milliseconds, with progress events          |
| `responseTime`    | `20`    | Download time in milliseconds, with progress events        |
| `timeout`         | none    | A `TimeoutError` after this many milliseconds              |
| `totalUploaded`, `totalDownloaded` | `1000` | Sizes reported in progress events        |

```ts title="src/api/users.test.ts"
// A slow response, to test loading states
getUsers.setMock(() => ({ data: [], status: 200 }), { responseTime: 1000 });

// A timeout, to test the timeout message
getUsers.setMock(() => ({ data: [], status: 200 }), { requestTime: 500, timeout: 100 });
```

## Test a component

In component tests, mock the request before rendering. The hooks read the mocked response like a real one.

```tsx title="src/components/users.test.tsx"
import { render, screen } from "@testing-library/react";

import { client } from "../api/client";
import { getUsers } from "../api/users";
import { Users } from "./users";

beforeEach(() => client.clear());
afterEach(() => getUsers.clearMock());

it("renders the users", async () => {
  getUsers.setMock(() => ({ data: [{ id: 1, name: "Ann" }], status: 200 }));

  render(<Users />);

  expect(await screen.findByText("Ann")).toBeInTheDocument();
});
```

See [isolation](/docs/guides/testing/isolation) for why the client is cleared before each test.

## Centralize mocks in a test SDK

With an [SDK](/docs/core/sdk), put every mock in one `$configure` call. `$configure` returns a new SDK, so the production
SDK stays untouched, and the endpoint keys are checked against the schema.

```ts title="test/sdk.ts"
import { sdk } from "../src/api/sdk";

export const testSdk = sdk.$configure({
  "users.$get": (request) => request.setMock(() => ({ data: [{ id: 1, name: "Ann" }], status: 200 })),
  "users.$userId.$get": (request) =>
    request.setMock(({ request: sent }) => {
      // Callback requests are typed loosely, so read the filled endpoint: "/users/1"
      const userId = Number(sent.endpoint.split("/").pop());
      return userId === 1
        ? { data: { id: 1, name: "Ann" }, status: 200 }
        : { error: new Error("Not found"), status: 404 };
    }),
});
```

Pass it to components the way your app passes the SDK, such as a prop or a context:

```tsx title="src/components/users.test.tsx"
it("renders the users", async () => {
  render(<Users sdk={testSdk} />);
  expect(await screen.findByText("Ann")).toBeInTheDocument();
});
```

### Override mocks per test

`$configure` can be chained, so a test starts from `testSdk` and changes only what it needs:

```tsx title="src/components/users.test.tsx"
it("shows the empty state", async () => {
  const emptySdk = testSdk.$configure({
    "users.$get": (request) => request.setMock(() => ({ data: [], status: 200 })),
  });

  render(<Users sdk={emptySdk} />);
  expect(await screen.findByText("No users found")).toBeInTheDocument();
});

it("shows the error state", async () => {
  const errorSdk = testSdk.$configure({
    "users.$get": (request) => request.setMock(() => ({ error: new Error("Server error"), status: 500 })),
  });

  render(<Users sdk={errorSdk} />);
  expect(await screen.findByText("Something went wrong")).toBeInTheDocument();
});
```

## Mock with MSW

[MSW](https://mswjs.io/) intercepts requests at the network level, so the adapter runs too. Use it when you want to test
the adapter, such as headers sent by the fetch adapter, or when the same handlers serve other clients. `setMock` is
faster to set up and is typed by the request, so prefer it for component and logic tests.

| Use                 | When                                                             |
| ------------------- | ---------------------------------------------------------------- |
| `request.setMock`   | A few requests in one test, typed against the request            |
| Test SDK            | Many endpoints, one set of defaults, per-test overrides          |
| MSW                 | Testing the adapter itself, or handlers shared with other tools  |
