# Optimistic Updates in React

An optimistic update changes the UI right after a user action, before the server answers, and reverts it if the request
fails. In HyperFetch you describe the change on the mutation request with `optimistic()` and write the undo in
`.rollback()`; core applies, reverts and refreshes, for `send()`, SDK hooks and React hooks alike.

:::secondary What you'll learn

1.  When **optimistic UI** is the right choice, and when a loading state is better.
2.  How to describe a change with **`setOptimistic`** and the `optimistic()` helpers.
3.  How to write the undo in **`.rollback()`** and swap temporary items in **`.commit()`**.
4.  What core does **when the request settles**: refresh, stale responses, retries.
5.  How it maps to React Query's **`onMutate`** approach.

:::

---

## When to update optimistically

Optimistic UI is a bet that the server will say yes. Every optimistic update has four steps:

1. **Apply** the expected result to the data on screen.
2. **Protect** it, so a refetch already in flight does not overwrite it with old data.
3. **Undo** it if the request fails, without wiping out other changes made in the meantime.
4. **Reconcile** with the server once it is done, so the screen shows what was saved.

You write steps 1 and 3; core does 2 and 4. Use it for small, frequent, likely-to-succeed actions: toggles, likes,
reordering, renaming, comments. Skip it when failure is common or costly, like payments, or when the server computes the
result, such as an order number or a price with tax.

## Update a list item

Return the changes from `setOptimistic` on the mutation request. The callback receives the mutation's `params`,
`queryParams` and `payload`.

```ts title="api/todos.ts"
import { optimistic } from "@hyper-fetch/core";

export const getTodos = client.createRequest<{ response: Todo[] }>()({
  endpoint: "/todos",
});

export const toggleTodo = client
  .createRequest<{ response: Todo; payload: { completed: boolean } }>()({
    endpoint: "/todos/:todoId",
    method: "PATCH",
  })
  .setOptimistic(({ params, payload }) => [
    optimistic(getTodos)
      .patch(params.todoId, payload)
      // Restore only this item, built from the current data
      .rollback(({ data, previous }) => {
        const before = previous.find(
          (todo) => todo.id === Number(params.todoId),
        );
        return data.map((todo) =>
          todo.id === Number(params.todoId) && before ? before : todo,
        );
      }),
  ]);
```

Components need nothing optimistic-specific. The mutation is a normal [`useSubmit`](/docs/guides/react/basics/submitting)
call, and the list re-renders in the same tick when `setOptimistic` returns synchronously.

```tsx title="components/todos.tsx"
function Todos() {
  const { data: todos } = useFetch(getTodos);
  const { submit } = useSubmit(toggleTodo);

  return todos?.map((todo) => (
    <div
      key={todo.id}
      onClick={() =>
        submit({
          params: { todoId: todo.id },
          payload: { completed: !todo.completed },
        })
      }
    >
      {todo.title}
    </div>
  ));
}
```

## Pick a helper and a target

| Helper                                                  | Use                                                     |
| ------------------------------------------------------- | ------------------------------------------------------- |
| `set(updater)`                                          | Anything else, receives and returns the data            |
| `patch(match, fields)`                                  | Merge fields into matching list items                   |
| `insert(item, { at })`                                  | Add an item at `"end"` (default), `"start"` or an index |
| `remove(match)`                                         | Remove matching items                                   |
| `increment(field, by)` / `increment(match, field, by)`  | Counters on the data or on matching items               |

`match` is a predicate, or a value compared with the item's `id`. Numbers and strings match each other, so a route param
`"1"` matches the id `1`. Compare another field with `{ key }`:

```ts title="Matching items"
optimistic(getTodos).remove(params.todoId);
optimistic(getTodos).patch((todo) => todo.listId === params.listId, {
  archived: true,
});
optimistic(getTodos).remove(params.slug, { key: "slug" });
```

The target decides which cache entries change:

- `optimistic(getUser.setParams({ userId }))` changes one entry. A target whose params are not set is a compile error.
- `optimistic.all(getUsers)` changes every cached variant, whatever the query params: filters, sorting and every page of
  an [infinite list](/docs/react/hooks/use-infinite-fetch).
- `.list("items")` reaches an array inside an object response, such as `optimistic(getFeed).list("items").insert(post)`.

A helper that matches nothing does not write to the cache, and unchanged items keep their references.

## Write the undo in rollback

Core never infers an undo. `.rollback()` receives the target's current `data`, the `previous` data from just before this
change, the `reason` (`"error"`, `"abort"` or `"removed"` from the queue), and the failed `response` and `request`. It
returns the new data synchronously; returning nothing leaves the data as it is.

```ts title="Rollback patterns"
// Re-add a removed item
optimistic(getTodos)
  .remove(params.todoId)
  .rollback(({ data, previous }) => {
    const removed = previous.find((todo) => todo.id === Number(params.todoId));
    return removed ? [...data, removed] : data;
  });

// Opposite increment
optimistic(getStats)
  .increment("total", -1)
  .rollback(({ data }) => ({ ...data, total: data.total + 1 }));

// No .rollback(): on failure the user is refetched
optimistic(getUser.setParams({ userId: params.userId })).set((user) => ({
  ...user,
  ...payload,
}));
```

:::caution Build the result from data

`previous` is a snapshot from before the change. Returning it whole discards everything that happened since, such as
other mutations on the same list. Use it only to look old values up.

:::

## Swap a temporary item with commit

`.commit()` runs on success, for example to replace a temporary item with the server's. Use the `optimistic` builder
passed to the callback, so `response` is typed with the mutation's response.

```ts title="api/todos.ts"
export const createTodo = client
  .createRequest<{ response: Todo; payload: { title: string } }>()({
    endpoint: "/todos",
    method: "POST",
  })
  .setOptimistic(({ payload, optimistic }) => {
    const temp = { id: -Date.now(), ...payload, completed: false };
    return [
      optimistic(getTodos)
        .insert(temp)
        .commit(({ data, response }) =>
          data.map((todo) => (todo.id === temp.id ? response.data : todo)),
        )
        .rollback(({ data }) => data.filter((todo) => todo.id !== temp.id)),
    ];
  });
```

## What happens when the request settles

Core handles the rest, also when the component that submitted has unmounted.

| Outcome                                | What happens                                            | Then            |
| -------------------------------------- | ------------------------------------------------------- | --------------- |
| Success                                | Each `.commit()` runs                                   | Targets refresh |
| Final error                            | Each `.rollback()` runs, in reverse order of the changes | Targets refresh |
| Abort, or removed from the queue       | Each `.rollback()` runs, in reverse order               | Targets refresh |
| Will retry, or waits offline to resend | The change stays                                        | Nothing yet     |

- **No flicker on success.** The optimistic value stays in the cache until the refresh returns.
- **One refresh for many mutations.** With several mutations pending on one key, it is refreshed once, after the last
  one settles. The refresh is a cache invalidation, so mounted `useFetch` hooks refetch.
- **Stale responses are discarded.** While a mutation that changed a key is pending, fetch responses that started before
  it settled are not written to that key. Manual `cache.set` and `cache.update` calls are never held back.
- **No data, no change.** A target without cached data is left alone and its `.rollback()` is not called.
- **Errors in your code stay contained.** When a helper, `.commit()` or `.rollback()` throws, the request still completes
  and the target is refreshed. The error is rethrown from a timer, so global error handlers see it.

## Coming from React Query

React Query's cache approach to optimistic updates writes to the cache in `onMutate`: cancel queries, snapshot with
`getQueryData`, write with `setQueryData`, restore in `onError` and invalidate in `onSettled`. The same steps in
HyperFetch:

| Step      | React Query                         | HyperFetch                           |
| --------- | ----------------------------------- | ------------------------------------ |
| Apply     | `setQueryData` in `onMutate`        | `optimistic(target).patch(...)`      |
| Protect   | `cancelQueries` in `onMutate`       | Automatic                            |
| Undo      | Restore the snapshot in `onError`   | `.rollback(...)`                     |
| Reconcile | `invalidateQueries` in `onSettled`  | Automatic refresh of the targets     |
