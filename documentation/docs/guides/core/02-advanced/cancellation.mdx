# Cancel Requests with AbortController

A request you no longer need still costs bandwidth, and its late response can overwrite newer data. The browser's
answer is `AbortController`: you hand its `signal` to `fetch`, call `abort()`, and the request stops. This guide shows
how AbortController works on its own, then how HyperFetch uses it to cancel stale requests automatically and to abort
in-flight requests by hand.

:::secondary What you'll learn

1.  How **AbortController** and **AbortSignal** cancel a fetch request.
2.  How to automatically **cancel stale requests** to prevent race conditions.
3.  How to **manually abort** a request in TypeScript.
4.  The difference between **aborting** a request and **stopping** the dispatcher queue.
5.  How to **pause and resume** request queues.

:::

## How AbortController works

[`AbortController`](https://developer.mozilla.org/en-US/docs/Web/API/AbortController) is a small browser and Node.js
API with one property and one method. `controller.signal` is an `AbortSignal` you pass to whatever should be
cancellable. `controller.abort()` flips that signal, and everything listening to it stops.

```ts
const controller = new AbortController();

fetch("/api/users", { signal: controller.signal })
  .then((response) => response.json())
  .catch((error) => {
    if (error.name === "AbortError") return; // we cancelled it, not an error
    throw error;
  });

// Later, for example when the user leaves the page
controller.abort();
```

What to know before you cancel a fetch request:

- An aborted `fetch` rejects with a `DOMException` named `AbortError`. Check the name so a cancel isn't reported as a
  failure.
- A controller works once. After `abort()` its signal stays aborted, so create a new controller for the next request.
- `AbortSignal.timeout(ms)` gives you a signal that aborts on its own, which is the simplest way to put a timeout on
  `fetch`. It rejects with a `TimeoutError` instead.
- Aborting stops the client side. If the server already received a `POST`, it may still process it.

In React, the classic pattern is to abort fetch in the `useEffect` cleanup, so a fast re-render or unmount doesn't
apply an old response:

```tsx
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/users?search=${search}`, { signal: controller.signal })
    .then((response) => response.json())
    .then(setUsers)
    .catch(() => {});
  return () => controller.abort();
}, [search]);
```

HyperFetch creates and tracks these controllers for you. Every request gets its own `AbortController`, grouped by the
request's `abortKey`, and the adapter passes the signal to `fetch` (or to Axios with the
[Axios adapter](../../../integrations/adapter-axios/overview.mdx)).

## Automatic cancellation

When a user performs actions that trigger rapid, successive requests (like typing in a search bar), you can end up with
a race condition: responses arrive out of order. The response to an earlier request might arrive after a later one,
leaving the UI showing results for an old query.

HyperFetch solves this with the `cancelable` option. When it is `true`, a new request cancels the pending requests in
the same queue. The queue is picked by `queryKey`. By default the `queryKey` includes the query params, so a search
request with a different `search` value lands in a different queue. Give the request a fixed `queryKey` to make every
search share one queue:

```ts
// 1. Create a cancelable request
const searchUsers = client.createRequest()({
  endpoint: "/users",
  method: "GET",
  cancelable: true,
  // highlight-next-line
  queryKey: "search-users", // one queue for every search term
});

// 2. Simulate rapid search requests
// The first request will be sent
searchUsers.send({ queryParams: { search: "M" } });

setTimeout(() => {
  // 50ms later, this request will cancel the first one and be sent
  searchUsers.send({ queryParams: { search: "Ma" } });
}, 50);

setTimeout(() => {
  // 100ms later, this request will cancel the second one
  // Only the result for "Mac" will be processed
  searchUsers.send({ queryParams: { search: "Mac" } });
}, 100);
```

This ensures that only the most recent request's response is processed. If you'd rather not send every keystroke at
all, combine it with debouncing (`bounce` in [useFetch](../../../react/04-hooks/use-fetch.mdx)).

## Manual cancellation

There are times when you need to manually abort a request. For instance, a user might navigate away from a page while a
request is still pending, or click a "cancel" button on a file upload. HyperFetch provides an `abort` method on the
`request` instance. It aborts every in-flight request that shares the request's `abortKey`.

```ts
const getUsers = client.createRequest()({
  endpoint: "/users",
  method: "GET",
});

// 1. Make a request
// highlight-next-line
getUsers.send();

setTimeout(() => {
  // 2. Abort it before it completes
  // highlight-next-line
  getUsers.abort();
}, 50);
```

or via the RequestManager:

```ts
import { client } from "./client";

const getUsers = client.createRequest()({
  endpoint: "/users",
  method: "GET",
});

// 1. Make a request
// highlight-next-line
getUsers.send();

setTimeout(() => {
  // 2. Abort it before it completes
  // highlight-next-line
  client.requestManager.abortByKey(getUsers.abortKey);
}, 50);
```

An aborted request resolves with an error response instead of throwing, and it is not retried. In React, `useFetch`
and `useSubmit` both return an `abort` function, and `onAbort` / `onSubmitAbort` let you react to it without it
counting as an error.

The RequestManager also holds the `AbortController` for each request. You can reach them through the
`abortControllers` property.

```ts
// Map<abortKey, Map<requestId, AbortController>>
// highlight-next-line
client.requestManager.abortControllers;

// Get map of all requests with the same abortKey
// highlight-next-line
client.requestManager.abortControllers.get(getUsers.abortKey);

// Abort a single request by its id
// highlight-next-line
client.requestManager.abortByRequestId(getUsers.abortKey, requestId);
```

## Cancelling one call with a signal

`.abort()` cancels every request with the same `abortKey`. To cancel a single call, pass your own `AbortSignal` to
`send()` or `exec()`. The signal does not replace HyperFetch's controller. It triggers the controller of that one call,
so the call ends exactly like `.abort()` ends it, and the other calls with the same key keep running.

```ts
const controller = new AbortController();

// highlight-next-line
const response = getUsers.send({ signal: controller.signal });

// Cancels only the call above
controller.abort();

const { error } = await response; // the abort error, not retried and not cached
```

What the signal does depends on where the call is:

- **Running**: the request is aborted, and `onResponse` gets `details.isCanceled`.
- **Queued, waiting for a retry or for the connection**: the request is taken out of the queue and never sent.
- **Already aborted when you call `send()`**: nothing is queued or sent, and an optimistic update does not run.
- **Deduplicated into another call**: only your call stops waiting. The shared request keeps running for the others.

The listener is removed once the call settles, so a long-lived signal, such as the one of a route loader, does not leak.
The same option works with `submit()` from `useSubmit`.

## Pausing and resuming queues

Aborting a request terminates it. But what if you want to temporarily pause requests without losing them? This is common
in offline-first applications where you want to queue requests while offline and send them once the connection is
restored.

Each client has two dispatchers. `client.fetchDispatcher` handles safe reads (`GET`), and `client.submitDispatcher`
handles everything else (`POST`, `PUT`, `PATCH`, `DELETE`). Both let you `stop` and `start` a queue by its `queryKey`.
Stopping a queue keeps its requests in storage without sending them. Starting it resumes dispatching.

```ts
const postFile = client.createRequest()({
  method: "POST",
  endpoint: "/files",
  offline: true, // keep the request when the network is down
});

// This request will be queued if offline
postFile.send({ payload: { some: "data" } });

// POST requests live in the submit dispatcher
// Later, you can stop the whole queue for this request
client.submitDispatcher.stop(postFile.queryKey);

// And resume it when ready (e.g., when back online)
client.submitDispatcher.start(postFile.queryKey);
```

:::caution Important

`stop` does not affect requests that are already in progress. It only prevents new requests in the queue from being
dispatched.

:::
