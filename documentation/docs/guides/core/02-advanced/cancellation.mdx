# Cancel requests with AbortController

A request you no longer need still costs bandwidth, and its late response can overwrite newer data. The browser's answer
is `AbortController`. This guide shows how it works with plain `fetch`, then how HyperFetch uses it to cancel stale
requests on its own, abort requests by hand and time them out.

:::secondary What you'll learn

1. How **AbortController** cancels a `fetch` call.
2. How to **cancel stale requests** with `cancelable`.
3. How to **abort** requests by `abortKey`, by id or with your own **signal**.
4. How to put a **timeout** on a request.
5. The difference between **aborting** a request and **stopping** a queue.

:::

---

## How AbortController works

[`AbortController`](https://developer.mozilla.org/en-US/docs/Web/API/AbortController) has one property and one method.
`controller.signal` is passed to whatever should be cancelable, and `controller.abort()` stops it.

```ts title="plain-fetch.ts"
const controller = new AbortController();

fetch("/api/users", { signal: controller.signal })
  .then((response) => response.json())
  .catch((error) => {
    if (error.name === "AbortError") return; // canceled on purpose, not a failure
    throw error;
  });

// Later, for example when the user leaves the page
controller.abort();
```

- An aborted `fetch` rejects with a `DOMException` named `AbortError`.
- A controller works once, so create a new one for the next request.
- `AbortSignal.timeout(ms)` gives a signal that aborts on its own.
- Aborting stops the client side only. A server that already received a `POST` may still process it.

HyperFetch creates a controller for every request, groups them by the request's `abortKey` and passes the signal to the
adapter. An aborted request does not reject: `send()` resolves with an `AbortError` in `error`, and it is not retried.

## Cancel stale requests automatically

Fast, repeated requests, such as search as you type, can answer out of order and leave the UI showing an old query. With
`cancelable: true`, a new request aborts the running requests in its queue before it starts.

The queue is picked by `queryKey`, which includes the query params by default, so each search term would get its own
queue. Give the request a fixed `queryKey` so all terms share one:

```ts title="src/api/users.ts"
export const searchUsers = client.createRequest<{
  response: User[];
  queryParams: { search: string };
}>()({
  endpoint: "/users",
  cancelable: true,
  queryKey: "users-search", // one queue for every search term
});
```

```ts title="src/search.ts"
searchUsers.send({ queryParams: { search: "M" } });
searchUsers.send({ queryParams: { search: "Ma" } }); // aborts "M"
// aborts "Ma"
const { data } = await searchUsers.send({ queryParams: { search: "Mac" } });
```

Only the last response reaches the UI. To skip sending every keystroke, debounce as well, for example with `bounce` in
[`useFetch`](/docs/react/hooks/use-fetch). A cancelable request is never deduplicated.

## Abort requests by hand

`request.abort()` aborts every in-flight request with the same `abortKey`. The default `abortKey` is built from the
method, the endpoint template and `cancelable`, so `getUser.abort()` aborts calls for every `userId`.

```ts title="src/upload.ts"
const promise = uploadFile.send({ payload: formData });

cancelButton.onclick = () => uploadFile.abort();

const { error } = await promise; // AbortError when canceled
```

The [RequestManager](/docs/core/managers) holds the controllers and aborts them from anywhere:

| Method                                  | Aborts                                        |
| --------------------------------------- | --------------------------------------------- |
| `request.abort()`                       | Requests with the request's `abortKey`        |
| `requestManager.abortByKey(abortKey)`   | Requests with this `abortKey`                 |
| `requestManager.abortByRequestId(abortKey, requestId)` | One call, by the id from `onBeforeSent` |
| `requestManager.abortAll()`             | Every request of the client                   |

```ts title="src/upload.ts"
let requestId = "";

uploadFile.send({
  payload: formData,
  onBeforeSent: (event) => (requestId = event.requestId),
});

// Abort this call only
client.requestManager.abortByRequestId(uploadFile.abortKey, requestId);
```

To group requests that should be aborted together, such as everything on one page, give them the same `abortKey` with
`setAbortKey`. In React, `useFetch` and `useSubmit` return `abort`, and `onAbort` / `onSubmitAbort` react to it without
counting it as an error.

## Abort one call with a signal

Pass your own `AbortSignal` to `send()` or `exec()`. It does not replace the controller HyperFetch keeps: it triggers
the controller of that one call, so the call ends like `abort()` ends it and the other calls with the same key keep
running. Route loaders, TanStack Query and `useSubmit`'s `submit()` can pass theirs.

```ts title="src/search.ts"
const controller = new AbortController();
const promise = searchUsers.send({ signal: controller.signal });

controller.abort();

const { error } = await promise; // AbortError, not retried
```

| Where the call is                              | What the signal does                               |
| ---------------------------------------------- | -------------------------------------------------- |
| Running                                        | Aborts it, `onResponse` gets `details.isCanceled`  |
| Queued, or waiting for a retry or the network | Removes it from the queue, it is never sent        |
| Not started, the signal is aborted already     | Sends nothing and skips the optimistic update      |
| Deduplicated into another call                 | Stops waiting, the shared request keeps running    |

The listener is removed once the call settles, so a long-lived signal does not leak.

## Time out slow requests

The fetch adapter aborts a request after `timeout` milliseconds, 5000 by default, and resolves with a `TimeoutError`.
It is an adapter option: change it per request in `options`, or for every request with `setAdapterDefaults`.

```ts title="src/api/reports.ts"
export const exportReport = client.createRequest()({
  endpoint: "/reports/export",
  options: { timeout: 60_000 },
});

client.adapter.setAdapterDefaults(() => ({ timeout: 10_000 }));
```

Unlike an abort, a timeout is a failure, so it is retried when the request has `retry` set.

---

## Abort or stop

Aborting ends a request. Stopping a queue keeps its requests and sends them later:

| Action                              | Running request            | Waiting requests          |
| ----------------------------------- | -------------------------- | ------------------------- |
| `request.abort()`                   | Ends with `AbortError`     | Not affected              |
| `dispatcher.stop(queryKey)`         | Canceled, kept in the queue | Held until `start`       |
| `dispatcher.pause(queryKey)`        | Finishes                   | Held until `start`        |

Queue control is covered in [queueing](/docs/guides/core/advanced/queueing).
