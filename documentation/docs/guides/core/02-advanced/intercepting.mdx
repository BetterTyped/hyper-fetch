# Request interceptors

An interceptor runs on every request before it leaves your app, or on every response before your code sees it. It holds
logic that would otherwise be copied into every call: headers, logging, error reporting, token refresh. This guide
compares Axios interceptors and fetch wrappers with HyperFetch's client interceptors.

:::secondary What you'll learn

1. How **Axios interceptors** and **fetch wrappers** map to HyperFetch.
2. How to **intercept requests** with `onRequest` and `onAuth`.
3. How to **intercept responses** with `onResponse`, `onSuccess` and `onError`.
4. How interceptors **chain**, and how to **remove** or **skip** them.

:::

---

## Axios interceptors and fetch wrappers

Axios registers interceptors with
[`axios.interceptors.request.use()` and `axios.interceptors.response.use()`](https://axios-http.com/docs/interceptors)
and removes them with `eject(id)`. Request interceptors run in reverse order, the last added first.

`fetch` has no interceptor API. A fetch interceptor is a wrapper you call everywhere instead of `fetch`, and code that
calls `fetch` directly skips it:

```ts title="api-fetch.ts"
export async function apiFetch(input: string, init: RequestInit = {}) {
  const headers = new Headers(init.headers);
  headers.set("Authorization", `Bearer ${getToken()}`);

  const response = await fetch(input, { ...init, headers });
  if (response.status === 401) {
    // refresh and retry, redirect to login, ...
  }
  return response;
}
```

In HyperFetch interceptors live on the client, so every request created from it goes through them, whatever adapter
sends it.

| Step                  | Axios                              | HyperFetch                                    |
| --------------------- | ---------------------------------- | --------------------------------------------- |
| Before the request    | `interceptors.request.use(fn)`     | `client.onRequest(fn)`                        |
| Only for `auth: true` | Not built in                       | `client.onAuth(fn)`                           |
| Every response        | Not built in                       | `client.onResponse(fn)`                       |
| Successful response   | `interceptors.response.use(fn)`    | `client.onSuccess(fn)`                        |
| Failed response       | `interceptors.response.use(_, fn)` | `client.onError(fn)`                          |
| Remove                | `eject(id)`                        | `client.removeOnRequestInterceptors([fn])` and the others |
| Order                 | Request: last added first          | Always the order they were added              |

## Intercept requests

`onRequest` runs before every request is sent. It receives the request and returns a request, usually built with
setters. `onAuth` runs after it, only for requests with `auth: true`, which is the default.

```ts title="src/api/client.ts"
export const client = createClient({ url: "https://api.example.com" })
  .onRequest((request) => {
    console.log(`-> ${request.method} ${request.endpoint}`);
    return request.setHeaders({
      ...request.headers,
      "X-Client-Version": "1.4.0",
    });
  })
  .onAuth((request) =>
    request.setHeaders({
      ...request.headers,
      Authorization: `Bearer ${getToken()}`,
    }),
  );
```

Interceptors can be async, for example to read a token from async storage. The
[authentication guide](/docs/guides/core/basics/authentication) covers `onAuth` step by step.

## Intercept responses

Response interceptors run after the adapter, before the response is cached and before `send()` resolves. `onResponse`
runs first for every response, then `onSuccess` or `onError`. Each receives the response and the request and returns a
response.

```ts title="src/api/client.ts"
client
  .onResponse((response, request) => {
    console.log(`<- ${request.endpoint} ${response.status}`);
    return response;
  })
  .onError(async (response, request) => {
    // Refresh the token once, then send the original request again
    if (response.status === 401 && !request.used) {
      await refreshToken();
      return request.setUsed(true).send();
    }
    return response;
  });
```

`setUsed(true)` marks the resent request, so a second `401` does not refresh again and the resend is not deduplicated
against the request still waiting on this interceptor. An interceptor that throws turns the response into a failure
with the thrown value in `error`.

A response interceptor may change `data`, but the types of `data` come from each request, not from the interceptor. To
reshape data with types, use [`setResponseMapper`](/docs/guides/core/basics/data-mapping) on the request.

## Chain, remove and skip interceptors

Several interceptors of one kind form a pipeline in the order they were added, each receiving what the previous one
returned. To remove one, keep a reference and pass it to the matching `remove...` method:

```ts title="src/api/client.ts"
const logRequest = (request: RequestInstance) => {
  console.log(request.endpoint);
  return request;
};

client.onRequest(logRequest);

// Later
client.removeOnRequestInterceptors([logRequest]);
```

A single request can skip them with `disableRequestInterceptors: true` (skips `onRequest` and `onAuth`) or
`disableResponseInterceptors: true` (skips the response ones), for example a health check that must not trigger a token
refresh.

| Need                                  | Use                                             |
| ------------------------------------- | ----------------------------------------------- |
| Change every request of a client      | `onRequest`, `onAuth`                           |
| Handle every response or error        | `onResponse`, `onSuccess`, `onError`            |
| Change one request                    | `setRequestMapper`, `setResponseMapper`         |
| Observe without changing, for metrics | A [plugin](/docs/core/plugin)                   |
