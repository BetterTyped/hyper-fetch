# Persistence

The cache and the request queues live in memory, so a reload empties them. Give them a storage and they survive: the
app opens with the last data, and writes made offline are sent on the next start. This guide covers cache persistence,
queue persistence and the difference between sync and async storages.

:::secondary What you'll learn

1. The difference between a **sync `storage`** and an **async `lazyStorage`**.
2. How to **persist the cache** in IndexedDB or MMKV.
3. How to **persist request queues** for offline writes.
4. What is **not kept**, and how to clear data on logout.

:::

---

## Sync storage or lazy storage

Both the [Cache](/docs/core/cache) and the [Dispatcher](/docs/core/dispatcher) take one of two storages:

| Option        | Shape                                         | Use it for                               |
| ------------- | --------------------------------------------- | ---------------------------------------- |
| `storage`     | Sync `get`, `set`, `keys`, `delete`, `clear`  | MMKV, or `localStorage` wrapped with JSON |
| `lazyStorage` | Async `get`, `set`, `keys`, `delete`          | IndexedDB, AsyncStorage                  |

A `storage` replaces the in-memory `Map`. A `lazyStorage` is a mirror next to it: every change is written to it, and
data is read from it when it is not in memory. Values must be JSON-serializable, so convert files to Base64 or keep them
out of the cache.

---

## Persist the cache

With IndexedDB through `idb-keyval`, pass a `lazyStorage`. A read that misses memory loads the entry from IndexedDB in
the background and emits it to the readers.

```ts title="src/api/client.ts"
import { Cache, CacheAsyncStorageType, createClient } from "@hyper-fetch/core";
import { del, get, keys, set } from "idb-keyval";

const cacheStorage: CacheAsyncStorageType = {
  get: (key) => get(key),
  set: (key, value) => set(key, value),
  keys: () => keys() as Promise<string[]>,
  delete: (key) => del(key),
};

export const client = createClient({
  url: "https://api.example.com",
  // Bump the version when response shapes change, old entries are dropped
  cache: () => new Cache({ lazyStorage: cacheStorage, version: "2" }),
});
```

In React, `useFetch` with `revalidate: false` waits for the lazy storage before it decides to fetch, so fresh persisted
data is shown without a request. With the default `revalidate: true` the request starts at once, and the persisted data
is shown as soon as it is read.

For a sync store such as MMKV in React Native, pass a `storage` instead:

```ts title="src/api/client.ts"
import { Cache, CacheStorageType, createClient } from "@hyper-fetch/core";
import { MMKV } from "react-native-mmkv";

const mmkv = new MMKV({ id: "hyper-fetch-cache" });

const cacheStorage: CacheStorageType = {
  get: (key) => {
    const value = mmkv.getString(key);
    return value ? JSON.parse(value) : undefined;
  },
  set: (key, data) => mmkv.set(key, JSON.stringify(data)),
  keys: () => mmkv.getAllKeys(),
  delete: (key) => mmkv.delete(key),
  clear: () => mmkv.clearAll(),
};

export const client = createClient({
  url: "https://api.example.com",
  cache: () => new Cache({ storage: cacheStorage }),
});
```

## Persist request queues

Give the `submitDispatcher` a storage to keep writes made offline through a reload. On start the dispatcher reads the
persisted queues, puts their requests in front of the ones added meanwhile and sends them. Requests with `offline: true`
wait for the connection first.

```ts title="src/api/client.ts"
import {
  createClient,
  Dispatcher,
  DispatcherAsyncStorageType,
} from "@hyper-fetch/core";
import { createStore, del, get, keys, set } from "idb-keyval";

// A separate store, so queue entries never mix with cache entries
const queueStore = createStore("hyper-fetch", "submit-queue");

const queueStorage: DispatcherAsyncStorageType = {
  get: (key) => get(key, queueStore),
  set: (key, data) => set(key, data, queueStore),
  keys: () => keys(queueStore) as Promise<string[]>,
  delete: (key) => del(key, queueStore),
};

export const client = createClient({
  url: "https://api.example.com",
  submitDispatcher: () => new Dispatcher({ lazyStorage: queueStorage }),
});
```

The restored requests are sent once the current task ends, so the adapter, interceptors and plugins chained after
`createClient` apply to them. A sync `DispatcherStorageType` also works, with an extra `entries` method. Give each
dispatcher its own store or key prefix.

:::caution Several browser tabs

Every open tab reads the same persisted queue on start and may send its requests. Persist queues in the browser only
when duplicates are harmless or the API is idempotent. They are safest where one instance of the app runs, such as
React Native.

:::

## What is not kept

Requests are stored with `request.toJSON()`, so functions are lost: mappers, `setRetryOnError`, a function `retryTime`
and `$hooks`. A restored request is rebuilt as a `Request` and uses the client's interceptors, so keep logic that must
survive a reload in client interceptors rather than on the request.

Call `client.clear()` on logout. It removes every queued request and empties the cache, including its lazy storage, so
the next user never sees persisted data of the previous one.

| Persist           | Option                                | Result after a reload                       |
| ----------------- | ------------------------------------- | ------------------------------------------- |
| Cache             | `Cache({ lazyStorage })` or `storage` | Screens open with the last data             |
| Write queue       | `submitDispatcher` storage            | Offline writes are sent on the next start   |
| Read queue        | `fetchDispatcher` storage             | Rarely needed, reads are repeated anyway    |
