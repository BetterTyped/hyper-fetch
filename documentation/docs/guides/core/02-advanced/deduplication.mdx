# Request Deduplication

Request deduplication means that when the same request is already on its way to the server, a second identical call
doesn't open a new connection. It waits for the first one and gets the same response. You send one request instead of
four, the server does the work once, and every caller ends up with the same data.

---

1.  Why React apps end up with **duplicate API calls**.
2.  How to **enable deduplication** on a request to optimize data fetching.
3.  How to use `deduplicateTime` to **control the time window** for combining requests.
4.  How deduplication differs from **caching** and **cancellation**.

:::

## Why React apps make duplicate API calls

If you open the network tab and see the same `GET /users` twice or more, the usual causes are:

- **Several components need the same data.** A header avatar, a sidebar and a settings page all fetch the current user
  on mount, each in its own `useEffect`.
- **Strict Mode in development.** React runs effects twice in development to surface missing cleanup, so a bare
  `fetch` in `useEffect` fires twice.
- **Re-renders that change effect dependencies.** An object or array created during render makes the effect run again.
- **Fast repeated actions.** A user double-clicks a refresh button, or a list and its detail view mount at the same time.

The first three are fixed by moving fetching out of individual components into a shared layer that knows what is
already in flight. That is what deduplication does.

---

## Deduplication, caching and cancellation

These three often get mixed up. They solve different problems:

| Technique     | When a second identical request comes in...           | Use it for                                    |
| ------------- | ----------------------------------------------------- | --------------------------------------------- |
| Deduplication | It joins the request already in flight               | Many callers asking for the same data at once |
| Caching       | It gets the stored response if it's still fresh       | Data asked for again later                    |
| Cancellation  | The earlier request is aborted, the new one goes out | Search inputs where only the latest matters   |

They work together. Deduplication covers the window while the request is in flight, and the
[cache](./cache-revalidation.mdx) covers the time after it finished. For the opposite behaviour, see
[cancellation](./cancellation.mdx).

## Setup

In Hyper Fetch, `GET` requests sent through the default HTTP adapter are deduplicated already. The adapter turns on
`deduplicate` for safe methods, and an explicit `deduplicate` option on the request still wins. For other methods, or
other adapters, set it yourself:

```ts
const getUsers = client.createRequest()({
  endpoint: "/users",
  deduplicate: true,
});
```

Two requests count as identical when they share the same `queryKey`. By default that is built from the method, the
endpoint with its params, and the query string, so `/users?page=1` and `/users?page=2` are never merged.

## How it works

In the example below, we call the `getUsers.send()` method four times in quick succession. Since `deduplicate` is
enabled, Hyper Fetch sends a single request to the backend. The other calls receive the response from the first one.

```typescript
// We are using pre-build 'getUsers' request and 'client' instance

// highlight-start
const getUsers = client.createRequest()({
  endpoint: "/users",
  deduplicate: true,
});
// highlight-end

// Multiple calls of the same request
getUsers.send({
  onRequestStart: ({ request, requestId }) => {
    console.log("Request starting...", { requestId, request });
  },
});
getUsers.send();
getUsers.send();
getUsers.send();

// Only a single request will be sent to the backend,
// and you will see only one "Request starting..." log in the console.
```

In React, the same happens when several components call `useFetch(getUsers)` at once. They share one request and one
cache entry, so moving duplicated `useEffect` fetches to `useFetch` removes the duplicate API calls. See
[fetching data in React](../../react/01-basics/fetching.mdx).

## Deduplication time

By default `deduplicateTime` is `null`: a new request joins an identical request for as long as that request is in
flight. Set `deduplicateTime` to a number of milliseconds to shorten this window. A new request then joins only an
in-flight request that started at most that many milliseconds ago. Once the first request has finished, the next call
is always sent, whatever the window.

In this example, we set `deduplicateTime` to 2000 milliseconds. An identical request sent within 2000ms of the first one
joins it, as long as the first one has not finished yet.

```typescript
// We are using pre-build 'getUsers' request and 'client' instance

// highlight-start
const getUsersWithTime = client.createRequest()({
  endpoint: "/users",
  deduplicate: true,
  deduplicateTime: 2000,
});
// highlight-end

getUsersWithTime.send({
  onRequestStart: ({ request, requestId }) => {
    console.log("Request starting with deduplicateTime...", { requestId, request });
  },
});

setTimeout(() => {
  getUsersWithTime.send({
    onRequestStart: ({ request, requestId }) => {
      // Not logged when the first request is still in flight, because it's within the 2000ms window
      console.log("Second request starting...", { requestId, request });
    },
  });
}, 500);
```

:::caution Mutations

Be careful turning on deduplication for `POST`, `PUT` or `DELETE`. Two clicks that create two orders are two different
intentions. Merging them hides a real second request. For writes, prefer disabling the button while `submitting`, or
[queueing](./queueing.mdx) the requests one by one.

:::

A request with `cancelable: true` or `queued: true` is never deduplicated. Those modes take precedence.
