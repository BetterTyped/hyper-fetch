# Cache Invalidation and Revalidation

Once you cache API responses, you have to decide when a cached copy stops being true. Another user edits a record, a
background job changes a total, or your own form creates a new item that the cached list doesn't have. Cache
invalidation is how you tell the cache "this is out of date", and revalidation is the fresh request that replaces it.
This guide covers the general strategies, how React Query and React's own `cache()` handle it, and how to invalidate
cache in HyperFetch with `client.cache.invalidate`.

## Three ways to keep a cache fresh

| Strategy              | How it works                                              | Good for                                    |
| --------------------- | --------------------------------------------------------- | ------------------------------------------- |
| Time-based            | Data is fresh for a fixed time, then refetched on next use | Lists and dashboards that change slowly     |
| Event-based           | You invalidate when you know data changed                  | After a mutation, a websocket message       |
| Pattern-based         | One call invalidates a family of keys                      | Every page of a paginated list, all `/users/*` |

Most apps use all three. A sensible `staleTime` covers the background drift, and explicit invalidation after mutations
covers the changes your own app makes.

In HyperFetch the time-based part is two request options:

- `staleTime` (default 5 minutes): how long a cached response counts as fresh. After that, the next consumer refetches.
- `cacheTime` (default 5 minutes): how long the entry stays in memory at all before garbage collection.

```ts
const getUsers = client.createRequest<{ response: { id: number; name: string }[] }>()({
  endpoint: "/users",
  staleTime: 30_000, // refetch on next use after 30 seconds
  cacheTime: 10 * 60_000, // keep in memory for 10 minutes
});
```

## React Query cache and React cache()

If you're coming from React Query, `queryClient.invalidateQueries({ queryKey: ["todos"] })` marks every query whose key
starts with `todos` as stale and refetches the ones on screen
([TanStack docs](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation)). HyperFetch does
the same with `client.cache.invalidate`. Instead of array prefixes, you pass the request itself, an exact key, or a
`RegExp` over the keys.

React's own [`cache()`](https://react.dev/reference/react/cache) is something else. It memoizes a function inside React
Server Components, and React clears it for every server request. It doesn't keep data between page views in the
browser, so there is nothing to invalidate. For a client-side cache of API responses you need a data layer like the one
below.

---

## The basics

Invalidation marks cached data as stale by setting its `staleTime` to `0`. The next consumer, whether a React
`useFetch` hook or a manual `send()` call with caching enabled, sees that the data is out of date and requests it again.

Every cached request is identified by a `cacheKey`. By default it is built from the method, the endpoint (with params
filled in) and the query string, joined with underscores. For example `GET_/users_`, `GET_/users/1_` or
`GET_/users_?page=2`. Invalidation works by targeting these keys.

---

## Invalidating by request, string, or RegExp

The `client.cache.invalidate` method accepts three different argument types:

```typescript
import { client, getUsers } from "./api";

// 1. Pass a request instance - uses the request's cacheKey and scope
// highlight-next-line
client.cache.invalidate(getUsers);

// 2. Pass an exact cacheKey string
// highlight-next-line
client.cache.invalidate(getUsers.cacheKey);

// 3. Pass a RegExp to match multiple cache entries at once
// highlight-next-line
client.cache.invalidate(new RegExp("GET_/users"));
```

Passing the request instance is the safest choice. You don't need to know how the key is built, and it respects the
request's `scope`. Calling `invalidate()` with no arguments invalidates everything.

:::note When is it helpful?

- After a **mutation** (create, update, delete) to refresh related lists.
- When you need to **force fresh data** from the server for a specific resource.
- When **external events** (e.g. websocket notifications) indicate stale data.
- When you need to **bulk-invalidate** a family of related endpoints (e.g. all paginated pages).

:::

## Invalidate cache after mutations

The most common pattern is invalidating a list after adding, updating, or deleting an item. Here is a practical example:

```typescript
const getUsers = client.createRequest()({
  endpoint: "/users",
  method: "GET",
});

const addUser = client.createRequest<{
  response: { id: number; name: string };
  payload: { name: string };
}>()({
  endpoint: "/users",
  method: "POST",
});

// 1. Fetch and cache the users list
const { data } = await getUsers.send();
console.log("Initial users list:", data);

// 2. Add a new user
const { success } = await addUser.send({
  payload: { name: "New User" },
});

if (success) {
  console.log("New user added successfully.");
  // 3. Invalidate the list so hooks will re-fetch automatically
  // highlight-next-line
  client.cache.invalidate(getUsers);
}
```

If you'd rather show the new item before the server confirms it, update the cache first and roll back on error. That is
covered in [optimistic updates](../../react/01-basics/optimistic-approach.mdx).

## Batch invalidation

You can invalidate multiple cache entries in a single call by passing an array. The array can mix request instances,
strings, and RegExp patterns:

```ts
// Invalidate several related endpoints at once
// highlight-start
client.cache.invalidate([
  getUsers,
  getUser.setParams({ userId: 1 }),
  new RegExp("GET_/users/\\d+/posts"),
]);
// highlight-end
```

This is useful after a complex mutation that affects multiple resources.

---

## Pattern matching with RegExp

Sometimes you need to invalidate multiple cache entries that follow a pattern. For instance, you might have cached data
for individual items (`/articles/1`, `/articles/2`) and a list of all items (`/articles`). A `RegExp` handles this.

```ts
const getArticles = client.createRequest()({
  method: "GET",
  endpoint: "/articles",
});

const getArticle = client.createRequest()({
  method: "GET",
  endpoint: "/articles/:id",
});
```

When a single article is updated, you can invalidate the entire family of article caches:

```ts
// This will invalidate every cache entry whose key matches the pattern:
// 1. The main list:      GET_/articles_
// 2. Individual items:   GET_/articles/1_, GET_/articles/2_
// 3. Paginated lists:    GET_/articles_?page=1, GET_/articles_?page=2
// highlight-next-line
client.cache.invalidate(new RegExp("GET_/articles"));
```

## Reading, updating, and deleting cache

Beyond invalidation, the cache gives you direct access for advanced cases like optimistic updates or debugging:

### Reading cache

```ts
const cachedData = client.cache.get(getUsers.cacheKey);

if (cachedData) {
  console.log("Cached response:", cachedData.data);
  console.log("Cached at:", cachedData.responseTimestamp);
}
```

### Updating cache directly

Use `cache.update` to change the cached data without a network request. The update is merged with the existing cache
entry, and it does nothing if there is no entry yet. It also sets `responseTimestamp` to the time of the update, so
`staleTime` and `cacheTime` count from that moment. Use `cache.set` when the entry should keep another timestamp:

```ts
// Optimistically add a new user to the cached list
client.cache.update(getUsers, (previousData) => {
  if (!previousData) return previousData;
  return {
    ...previousData,
    data: [...previousData.data, { id: 999, name: "Optimistic User" }],
  };
});
```

### Deleting cache entries

Use `cache.delete` to completely remove an entry from both sync and async storage. Unlike `invalidate`, which marks
data as stale and keeps showing it until the new response arrives, `delete` removes it entirely:

```ts
// Remove the cached users list entirely
client.cache.delete(getUsers.cacheKey);
```

### Clearing all cache

```ts
// Remove all cached data, for example on logout
await client.cache.clear();
```

## How invalidation triggers revalidation

When you call `client.cache.invalidate`, it emits an invalidation event for each matching `cacheKey`. React hooks like
`useFetch` listen for these events and dispatch a fresh request when the data they show is invalidated. You don't need
to refetch by hand after invalidating.

Two `useFetch` options are related:

- `revalidate` (on by default) refetches in the background on mount even when the cache has data, so users see the
  cached copy instantly and the fresh one a moment later. Set it to `false` to fetch on mount only when the data is
  stale.
- `refresh` and `refreshTime` refetch on an interval. See [auto-refreshing data](../../react/01-basics/refreshing.mdx).

In plain TypeScript (without React hooks), invalidation only marks data as stale. Call `send()` again to fetch it. To
keep the cache across reloads, see [persistence](./persistence.mdx), and for the full cache API see the
[cache reference](../../../core/cache.mdx).
