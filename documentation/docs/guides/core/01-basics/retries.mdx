# Retry failed requests

Networks drop, servers restart and proxies return a `503` for a second. Most of those failures pass if you try again,
so the usual fix is to retry a few times with a pause in between. This guide covers which failures to retry, how
`fetch` and Axios do it, and how HyperFetch does it with `retry`, `retryTime` and `setRetryOnError`.

:::secondary What you'll learn

1. Which failures are **worth retrying**.
2. How to set **retries and a delay** on a request.
3. How to retry only **some errors** with `setRetryOnError`.
4. How to add **exponential backoff** or honor `Retry-After`.
5. How to **watch retry attempts** with `onRetry`.

:::

---

## What to retry

A retry is safe only when the second attempt can succeed and can do no harm.

| Failure                                   | Retry?                                                       |
| ----------------------------------------- | ------------------------------------------------------------ |
| Network error, connection reset           | Yes                                                          |
| `502`, `503`, `504`                       | Yes, the server or proxy is briefly unavailable              |
| `429 Too Many Requests`                   | Yes, after the `Retry-After` delay                           |
| `500`                                     | Often, when the operation is idempotent                      |
| `400`, `401`, `403`, `404`, `422`         | No, the same request fails the same way                      |
| A `POST` that may have reached the server | Only when the endpoint is idempotent, such as with an idempotency key |

Cap the number of attempts and space them out. Retrying at once in a tight loop makes an overloaded server worse.

`fetch` has no retry option, so a fetch retry is a loop around the call. Axios has none either, and the
[axios-retry](https://github.com/softonic/axios-retry) package adds `retries`, a `retryCondition` and a `retryDelay`. In
HyperFetch retries are request options run by the [dispatcher](/docs/core/dispatcher), so they work with every adapter,
including the [Axios adapter](/docs/integrations/adapter-axios/overview).

## Set retries on a request

`retry` is the number of extra attempts after a failure, default `0`. `retryTime` is the delay between them in
milliseconds, default `500`.

```ts title="src/api/reports.ts"
export const getReport = client.createRequest<{ response: Report }>()({
  endpoint: "/reports/:reportId",
  retry: 3,
  retryTime: 1000,
});

// One promise, resolved with the last attempt's response
const { data, error } = await getReport.send({ params: { reportId: 7 } });
```

`send()` resolves once, after the last attempt, so your code does not see the failures in between. Change the values on
an existing request with `setRetry` and `setRetryTime`, or for one call with `send({ retry: 1 })`:

```ts live
// failingRequest fails on purpose
const withRetries = failingRequest.setRetry(2).setRetryTime(2000);

const { data, error } = await withRetries.send();
console.log({ data, error });
```

Some failures are never retried:

- **Aborted requests.** Canceling ends the request, see [cancellation](/docs/guides/core/advanced/cancellation).
- **Offline failures.** With `offline: true`, the default, the request waits for the connection instead of using its
  retries, see [offline](/docs/guides/core/advanced/offline).

To set retries for every request, use [global defaults](/docs/guides/core/basics/global-defaults).

## Retry only some errors

By default every failed response is retried. `setRetryOnError` decides per response: return `true` to retry, `false` to
stop. It is the counterpart of axios-retry's `retryCondition`.

```ts title="src/api/reports.ts"
export const getReports = client
  .createRequest<{ response: Report[] }>()({
    endpoint: "/reports",
    retry: 3,
    retryTime: 1000,
  })
  // Retry network errors (status 0) and 5xx, never 4xx
  .setRetryOnError(({ status }) => !status || Number(status) >= 500);
```

When the callback throws, the request is not retried.

## Add backoff

`retryTime` also takes a function. It receives the `attempt` (`0` for the first retry) and the failed `response`, and
returns the delay. `exponentialBackoff` builds one that doubles the delay with each attempt up to a maximum, with random
jitter so clients that failed together do not retry at the same instant.

```ts title="src/api/reports.ts"
import { exponentialBackoff } from "@hyper-fetch/core";

export const getStats = client.createRequest()({
  endpoint: "/stats",
  retry: 5,
  retryTime: exponentialBackoff({ min: 500, max: 10_000 }),
});

// Or honor the Retry-After header of a 429 response
export const getQuota = getStats.setRetryTime(({ attempt, response }) => {
  const retryAfter = Number(response.extra?.headers?.["retry-after"]);
  return Number.isFinite(retryAfter) ? retryAfter * 1000 : 1000 * (attempt + 1);
});
```

| `exponentialBackoff` option | Default       | Description                                                 |
| --------------------------- | ------------- | ----------------------------------------------------------- |
| `min`                       | `500`         | Delay of the first retry in milliseconds                    |
| `max`                       | `30000`       | Longest delay in milliseconds                               |
| `jitter`                    | `true`        | Pick a random delay from `min` up to `min * 2 ** attempt`   |
| `random`                    | `Math.random` | Source of the randomness, for deterministic tests           |

A delay that is not a positive number retries at once. A function cannot be stored as JSON, so a request restored from a
[persisted queue](/docs/guides/core/advanced/persistence) uses the default 500 ms.

For most screens, `retry: 2` or `3` with a fixed `retryTime` of one or two seconds is enough. Use backoff when many
clients call the same endpoint, or when the server asks you to slow down.

## Watch retry attempts

`onResponse` fires only for the last attempt. `onRetry` fires for each failed attempt that schedules a retry, so you can
show "Retrying (2 of 3)" while the request waits.

```ts title="src/app.ts"
await getReport.send({
  params: { reportId: 7 },
  onRetry: ({ retry, delay, response }) => {
    console.log(
      `${response.status}: retry ${retry} of ${getReport.retry} in ${delay} ms`,
    );
  },
  onResponse: ({ response, details }) =>
    console.log(response.status, `retries used: ${details.retries}`),
});
```

| Field      | Description                                                              |
| ---------- | ------------------------------------------------------------------------ |
| `retry`    | Number of the scheduled retry, counted from `1`                          |
| `delay`    | Milliseconds before the next attempt                                     |
| `response` | The failed response, after `setRetryOnError` allowed the retry           |
| `details`  | The same details as in `onResponse`, with `willRetry: true`              |

`onRetry` does not fire when the request succeeds, runs out of retries, is aborted or fails offline. Listen to every
call of a request with `request.$hooks.onRetry()`, or to every request of the client with
`client.requestManager.events.onRetry()`. In React, [`useFetch`](/docs/react/hooks/use-fetch) returns `onRetry` and a
`retries` counter, and [`useSubmit`](/docs/react/hooks/use-submit) returns `onSubmitRetry`.
