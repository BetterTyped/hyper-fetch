# Retry Failed Requests

Networks drop packets, servers restart, load balancers return a 503 for a second. Most of those failures go away if you
just try again, so the usual fix is to retry failed requests a few times with a pause in between. This guide covers
what a good retry policy looks like, how people do it with `fetch` and Axios, and how HyperFetch handles it with the
`retry` and `retryTime` options.

## What to retry, and what not to

Retrying is only safe when the second attempt can succeed and can't do harm. A short checklist:

| Failure                                 | Retry?                                                   |
| --------------------------------------- | -------------------------------------------------------- |
| Network error, connection reset         | Yes                                                      |
| `502`, `503`, `504`                     | Yes, the server or proxy is temporarily unavailable      |
| `429 Too Many Requests`                 | Yes, but wait longer (respect `Retry-After` if present) |
| `500`                                   | Often, if the operation is idempotent                    |
| `400`, `401`, `403`, `404`, `422`       | No, the same request will fail the same way              |
| A `POST` that may have reached the server | Only if the endpoint is idempotent (for example with an idempotency key) |

Two more rules: cap the number of attempts, and space them out. Retrying instantly in a tight loop makes an overloaded
server worse.

## Fetch retry and axios retry

`fetch` has no retry option. A fetch retry is a loop around the call that checks `response.ok` and catches network
errors.

Axios has no built-in retry either. The common choice is the
[axios-retry](https://github.com/softonic/axios-retry) package. It adds `retries` (default `3`), a `retryCondition`
(by default network errors and 5xx responses on idempotent methods), a `retryDelay` callback with a built-in
`exponentialDelay`, and an `onRetry` hook.

In HyperFetch, retries are part of the request. They are scheduled by the dispatcher, so they work with every adapter,
including the [Axios adapter](../../../integrations/adapter-axios/overview.mdx), and they show up in the hooks state.

## Basic configuration

You can configure retries directly on a request using the `retry` and `retryTime` options.

- `retry`: The number of times to re-attempt the request after it fails.
- `retryTime`: The delay in milliseconds between each retry attempt.

Let's create a request that will fail (by pointing to a non-existent endpoint) and see how retries work.

```tsx
// We are using non-existent endpoint to showcase the retry mechanism
const getUsers = client.createRequest()({
  method: "GET",
  endpoint: "/users-fake-endpoint",
  // highlight-start
  retry: 3,
  retryTime: 1000, // 1 second
  // highlight-end
});

const sendRequest = async () => {
  const { data, error } = await getUsers.send();
  console.log({ data, error });
};

sendRequest();
```

In the example above, if the request to `/users-fake-endpoint` fails, HyperFetch retries it up to **3 times**, with a
**1-second delay** between each attempt. The `send()` promise resolves once, with the last response, so your code
doesn't see the intermediate failures.

A few things are never retried:

- **Aborted requests.** Cancelling a request ends it. See [cancellation](../02-advanced/cancellation.mdx).
- **Offline failures.** With `offline: true` (the default) the request waits for the network to come back instead of
  burning its retries. See [offline-first requests](../02-advanced/offline.mdx).

## Dynamic configuration

You can also configure retries dynamically using the `.setRetry()` and `.setRetryTime()` methods. This is useful when
you need to change the retry behavior based on application state or other conditions.

These methods return a new `Request` instance, leaving the original request unchanged.

```tsx live
import { failingRequest } from "./api";

// For our example we import request that will fail on purpose
// We can set retries and retryTime on creation or dynamically
const failingRequestWithRetries = failingRequest.setRetry(2).setRetryTime(2000); // 2 seconds

const { data, error } = await failingRequestWithRetries.send();
console.log({ data, error });
```

Here, we created a new request `failingRequestWithRetries` with 2 retries and a 2-second delay, without modifying the
original `failingRequest`.

## Backoff

`retryTime` also takes a function that returns the delay of each attempt. It receives the `attempt` (`0` for the first
retry) and the failed `response`. `exponentialBackoff` builds one that doubles the delay with every attempt, up to a
maximum. By default it adds random jitter, so many clients that failed at the same time don't all retry together.

```ts
import { exponentialBackoff } from "@hyper-fetch/core";

const getUsers = client.createRequest()({
  endpoint: "/users",
  retry: 5,
  // highlight-next-line
  retryTime: exponentialBackoff({ min: 500, max: 10_000 }),
});

// Or your own function - honor the Retry-After header of a 429 response
const getReports = getUsers.setRetryTime(({ attempt, response }) => {
  const retryAfter = Number(response.extra?.headers?.["retry-after"]);
  return Number.isFinite(retryAfter) ? retryAfter * 1000 : 1000 * (attempt + 1);
});
```

| `exponentialBackoff` option | Default       | Description                                                         |
| --------------------------- | ------------- | ------------------------------------------------------------------- |
| `min`                       | `500`         | Delay of the first retry in milliseconds                            |
| `max`                       | `30000`       | Longest delay in milliseconds                                       |
| `jitter`                    | `true`        | Pick a random delay from `min` up to `min * 2 ** attempt`           |
| `random`                    | `Math.random` | Source of the randomness, for deterministic tests                   |

When the function throws, the request is not retried. A delay that is not a positive number retries right away. A
function can't be stored as JSON, so a request restored from a persistent queue uses the default delay of 500 ms.

## Conditional retries

By default, HyperFetch retries on any error. You can use `setRetryOnError` to add a condition. For example, only retry
on server errors (5xx) but not on client errors (4xx) where retrying won't help:

```ts
const getUsers = client.createRequest()({
  endpoint: "/users",
  retry: 3,
  retryTime: 1000,
});

// highlight-start
const smartRetry = getUsers.setRetryOnError((response) => {
  // Only retry on server errors, not client errors
  return response.status >= 500;
});
// highlight-end
```

The callback receives the error response and must return `true` to allow the retry or `false` to stop retrying. This is
how you avoid retrying a `400 Bad Request` or `404 Not Found`, and it's the HyperFetch counterpart of axios-retry's
`retryCondition`.

## Watching retry attempts

`send()` resolves once, with the last response, and `onResponse` fires only for that one. The failed attempts in
between are announced by `onRetry`. It fires when a failed attempt schedules a retry, right before the request starts
waiting, so you can tell the user what is going on:

```ts
await getUsers.send({
  onRetry: ({ retry, delay, response }) => {
    console.log(`Attempt failed with ${response.status}, retry ${retry} of ${getUsers.retry} in ${delay} ms`);
  },
  onResponse: ({ response, details }) => {
    console.log(response.status, `retries used: ${details.retries}`);
  },
});
```

| Field      | Description                                                                         |
| ---------- | ----------------------------------------------------------------------------------- |
| `retry`    | Number of the scheduled retry, counted from `1`, up to the `retry` option            |
| `delay`    | Milliseconds before the next attempt, as returned by `retryTime`                    |
| `response` | The failed response of the attempt, after `retryOnError` allowed the retry          |
| `details`  | The same details as in `onResponse`, with `willRetry: true`                         |

`onRetry` does not fire when the request succeeds, runs out of retries, is aborted or fails offline. It is also
available on the request with `request.$hooks.onRetry()`, and on the client for every request with
`client.requestManager.events.onRetry()` (or `onRetryById` and `onRetryByQueue`).

In React, `useFetch` returns an `onRetry` callback and a `retries` counter, and `useSubmit` returns `onSubmitRetry`, so
you can show "Retrying (2 of 3)..." while the request waits. See [useFetch](../../../react/04-hooks/use-fetch.mdx).

## When backoff matters

Exponential backoff doubles the wait after every failure: 500 ms, 1 s, 2 s, 4 s. Random jitter on top stops many
clients from retrying at the same instant after an outage, which is why `exponentialBackoff` adds it by default (see
[Backoff](#backoff) above).

For most screens a fixed `retryTime` of one or two seconds with `retry: 2` or `3` is enough. Reach for
`exponentialBackoff` when many clients hit the same endpoint, or when the server tells you to slow down with a `429`
and a `Retry-After` header.
