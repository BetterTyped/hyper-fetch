# Axios vs fetch

`fetch` is built into browsers and modern runtimes. Axios is a library that wraps the same job with interceptors,
timeouts and JSON handling. This page compares them on the work around a request, then shows how HyperFetch keeps one
request API on either transport.

:::info How this page was written

`fetch` claims come from [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API) and Axios claims from the
[Axios docs](https://axios.rest/pages/getting-started/features), linked where they are used. HyperFetch claims are
checked against its source. If something is out of date, [open an issue](https://github.com/BetterTyped/hyper-fetch/issues)
and we will fix it.

:::

---

## When to choose which

- **fetch** when you call a few endpoints and can live with a small wrapper, or run where you can't add packages.
- **Axios** when many requests share auth headers, token refresh or error handling, and interceptors keep that in one
  place.
- **Axios** when you upload files and want a progress bar.
- **A request layer** such as HyperFetch when you like `fetch` being built in but don't want to write and maintain the
  wrapper.

---

## Feature comparison

**Yes**: built in. **Partial**: possible with your own code or an extra package. **No**: not available.

| Concern                       | fetch                                              | Axios                                          |
| ----------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| Install                       | Built in                                           | npm package                                    |
| Rejects on 404 or 500         | No, you check `response.ok` ¹                      | Yes, change it with `validateStatus` ²         |
| JSON request body             | Partial, `JSON.stringify` and a header yourself    | Yes, serialized for you                        |
| JSON response                 | Partial, `await response.json()`                   | Yes, parsed for you                            |
| Timeout                       | Partial, `AbortSignal.timeout()` ³                 | Yes, `timeout` option                          |
| Cancel                        | Yes, `AbortController`                             | Yes, `signal`                                  |
| Interceptors                  | No, wrap `fetch` yourself                          | Yes, `interceptors.request` and `.response`    |
| Upload progress               | No progress callback                               | Yes, `onUploadProgress`                        |
| Retry                         | No                                                 | Partial, an interceptor or `axios-retry` ⁴     |

1. A fetch promise ["does not reject"](https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch) on HTTP error
   statuses. It rejects on network failures, aborts and invalid requests.
2. Per [error handling](https://axios.rest/pages/advanced/error-handling), statuses outside 200 to 299 reject.
3. [`AbortSignal.timeout()`](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static) aborts with a
   `TimeoutError`. Combining it with a user cancel means merging two signals.
4. The request config has no retry option. The [retry guide](https://axios.rest/pages/advanced/retry) builds retries in
   a response interceptor, with backoff and `Retry-After` for 429.

## Side by side

### Handle an error status

<Tabs>
<TabItem value="fetch" label="fetch">

```ts title="get-user.ts"
const response = await fetch("/api/users/1");

if (!response.ok) {
  throw new Error(`HTTP error! Status: ${response.status}`);
}

const user = await response.json();
```

</TabItem>
<TabItem value="axios" label="Axios">

```ts title="get-user.ts"
try {
  const { data: user } = await axios.get("/api/users/1");
} catch (error) {
  if (error.response) {
    // The server responded with a status outside 2xx
    console.log(error.response.status, error.response.data);
  } else if (error.request) {
    // The request went out but no response came back
  }
}
```

</TabItem>
</Tabs>

### Add a token to every request

<Tabs>
<TabItem value="fetch" label="fetch">

```ts title="http.ts"
// Everyone must call this helper instead of fetch
export const request = (url: string, init: RequestInit = {}) =>
  fetch(url, {
    ...init,
    headers: { ...init.headers, Authorization: `Bearer ${getToken()}` },
    signal: init.signal ?? AbortSignal.timeout(5000),
  });
```

</TabItem>
<TabItem value="axios" label="Axios">

```ts title="http.ts"
export const http = axios.create({ timeout: 5000 });

http.interceptors.request.use((config) => {
  config.headers.Authorization = `Bearer ${getToken()}`;
  return config;
});
```

</TabItem>
</Tabs>

The Axios [first steps](https://axios.rest/pages/getting-started/first-steps) guide warns that without a `timeout`, a
stalled request can hang indefinitely, so set one in either case.

## Where each one is the better choice

- **fetch** wins on size and availability: no install, and the same API in browsers, Node, Deno, Bun and workers.
- **fetch** reads response bodies as streams, which suits large downloads and streaming responses.
- **Axios** wins when many calls share logic, since interceptors and `axios.create` defaults replace a hand-written
  wrapper.
- **Axios** wins for uploads in the browser, where it uses XHR and reports `onUploadProgress`.
- **Axios** has options `fetch` lacks, such as XSRF cookie handling, `maxContentLength` and Node's `httpAgent`.

## One request API on either transport

HyperFetch sits above the transport. You define requests once, and the client's adapter decides how they go over the
wire: native `fetch` by default, or Axios through [`@hyper-fetch/axios`](/docs/integrations/adapter-axios/overview).
Requests and hooks don't change.

```ts title="api/client.ts"
import { createClient } from "@hyper-fetch/core";
import { AxiosAdapter } from "@hyper-fetch/axios";

// Native fetch by default. Add .setAdapter(AxiosAdapter) to switch to Axios.
export const client = createClient({ url: "https://api.example.com" });

export const getUser = client.createRequest<{ response: User }>()({
  endpoint: "/users/:userId",
});

// Resolves with `error` and `status` on 404 or 500, never throws
const { data, error, status } = await getUser.setParams({ userId: 1 }).send();
```

The default fetch adapter fills the gaps from the table:

- **Errors.** Non-2xx responses resolve with `error` and `status` set. See [error handling](/docs/guides/core/basics/error-handling).
- **JSON.** Object payloads are serialized with `Content-Type: application/json` unless you set your own. Responses are
  parsed as JSON when they can be, and `options: { responseType: "blob" }` (or `"text"`, `"arrayBuffer"`) reads other
  bodies.
- **Timeouts.** Default 5 seconds, change it with `options: { timeout }` on the request.
- **Interceptors.** `client.onAuth`, `onRequest`, `onResponse`, `onSuccess` and `onError` work on both adapters. See
  [intercepting](/docs/guides/core/advanced/intercepting).
- **Retries.** Default 0, change it with `retry` and `retryTime`. See [retries](/docs/guides/core/basics/retries).

The main reason to switch to the Axios adapter is **upload progress**: the fetch adapter reports download progress from
the response stream but cannot measure an upload, while the Axios adapter passes `onUploadProgress` through to
`useSubmit`'s `onSubmitUploadProgress`. With the Axios adapter, request `options` take Axios config. See
[progress](/docs/guides/react/basics/progress).
