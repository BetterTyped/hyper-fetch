# HyperFetch vs SWR

SWR is a small set of React hooks built around stale-while-revalidate: show cached data at once, then fetch fresh data
in the background. HyperFetch defines and sends typed requests, with cache, queues, sockets and offline handling. This
page compares the two on reads, writes and realtime.

:::info How this page was written

SWR claims come from the [SWR 2 docs](https://swr.vercel.app/docs/getting-started), linked where they are used.
HyperFetch claims are checked against its source. If something is out of date,
[open an issue](https://github.com/BetterTyped/hyper-fetch/issues) and we will fix it.

:::

---

## When to choose which

- **SWR** when your app mostly reads data and you want one small hook with very little setup.
- **SWR** when you already have a fetcher or SDK and only need caching and revalidation on top.
- **HyperFetch** when you want typed params, payload, query params and errors defined once per endpoint.
- **HyperFetch** when your app writes a lot: forms, uploads with progress, requests that must survive going offline.
- **HyperFetch** when you need WebSockets or SSE next to HTTP without a second library.

---

## Feature comparison

**Yes**: built in. **Partial**: possible with your own code or an extra package. **No**: not available.

| Capability              | SWR                                         | HyperFetch                                                  |
| ----------------------- | ------------------------------------------- | ----------------------------------------------------------- |
| Sends HTTP requests     | No, you write the fetcher                   | Yes, `fetch` adapter built in                               |
| Non-2xx as error        | Partial, your fetcher must throw ¹          | Yes, lands in `error`                                       |
| Reads                   | `useSWR`                                    | [`useFetch`](/docs/react/hooks/use-fetch)                   |
| Writes                  | `mutate`, `useSWRMutation`                  | [`useSubmit`](/docs/react/hooks/use-submit)                 |
| Refetch on focus        | Yes, on by default                          | Yes, off by default, turn it on with `refetchOnFocus`       |
| Refetch on reconnect    | Yes, on by default                          | Yes, off by default, turn it on with `refetchOnReconnect`   |
| Deduplication           | Yes, 2 second window (`dedupingInterval`)   | Yes, GET and QUERY while the first call is in flight        |
| Retry on error          | Yes, on by default                          | Yes, off by default, change it with `retry`                 |
| Optimistic updates      | `optimisticData`, `rollbackOnError`         | `setOptimistic` on the request                              |
| Realtime                | Partial, `useSWRSubscription` ²             | Yes, [`@hyper-fetch/sockets`](/docs/sockets/overview)       |
| Offline write queue     | No ³                                        | Yes, [request queue](/docs/guides/core/advanced/offline)    |
| Upload progress         | Partial, up to your fetcher                 | Yes, with the [Axios adapter](/docs/integrations/adapter-axios/overview) |
| Devtools                | Partial, community extension ⁴              | [HyperFlow](/docs/hyper-flow) desktop app                   |
| UI frameworks           | React                                       | React                                                       |

1. `fetch` does not reject on 404 or 500 ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch)), so
   `error` stays empty unless the fetcher checks `res.ok` and throws.
2. [`useSWRSubscription`](https://swr.vercel.app/docs/subscription) (SWR 2.1.0 and later) feeds a source you open into
   the cache and shares one subscription per key. The transport is yours.
3. The [API reference](https://swr.vercel.app/docs/api) has `refreshWhenOffline` and `isPaused`, and revalidates on
   reconnect. Queueing writes made offline is not described.
4. [SWRDevTools](https://swr.vercel.app/docs/advanced/devtools) is a browser extension that is not an official Vercel
   project.

## Side by side

### Read a resource

<Tabs>
<TabItem value="hf" label="HyperFetch">

```tsx title="profile.tsx"
import { createClient } from "@hyper-fetch/core";
import { useFetch } from "@hyper-fetch/react";

export const client = createClient({ url: "https://api.example.com" });

export const getUser = client.createRequest<{ response: User; error: ApiError }>()({
  endpoint: "/users/:userId",
});

function Profile({ userId }: { userId: number }) {
  // `userId` is a required, typed param. A 404 lands in `error` as ApiError.
  const { data, error, loading } = useFetch(getUser.setParams({ userId }));
}
```

</TabItem>
<TabItem value="swr" label="SWR">

```tsx title="profile.tsx"
import useSWR from "swr";

const fetcher = async (url: string) => {
  const res = await fetch(url);
  if (!res.ok) throw new Error("Request failed");
  return res.json();
};

function Profile({ userId }: { userId: number }) {
  const { data, error, isLoading } = useSWR(`/api/users/${userId}`, fetcher);
}
```

</TabItem>
</Tabs>

### Save and refresh

<Tabs>
<TabItem value="hf" label="HyperFetch">

```tsx title="save-button.tsx"
import { useSubmit } from "@hyper-fetch/react";

export const updateUser = client.createRequest<{ response: User; payload: { name: string } }>()({
  endpoint: "/users/:userId",
  method: "PATCH",
});

function SaveButton({ userId }: { userId: number }) {
  const { submit, submitting, onSubmitSuccess } = useSubmit(updateUser.setParams({ userId }));

  onSubmitSuccess(() => client.cache.invalidate(getUser.setParams({ userId })));

  return (
    <button disabled={submitting} onClick={() => submit({ payload: { name: "Ada" } })}>
      Save
    </button>
  );
}
```

</TabItem>
<TabItem value="swr" label="SWR">

```tsx title="save-button.tsx"
import useSWRMutation from "swr/mutation";

async function updateUser(url: string, { arg }: { arg: { name: string } }) {
  await fetch(url, { method: "PATCH", body: JSON.stringify(arg) });
}

function SaveButton({ userId }: { userId: number }) {
  // Revalidates useSWR(`/api/users/${userId}`) when it resolves
  const { trigger, isMutating } = useSWRMutation(`/api/users/${userId}`, updateUser);

  return (
    <button disabled={isMutating} onClick={() => trigger({ name: "Ada" })}>
      Save
    </button>
  );
}
```

</TabItem>
</Tabs>

SWR ties the write to the read through the shared key. In HyperFetch you link them with `client.cache.invalidate()`,
and in exchange the payload is typed, the body is serialized for you, and `useSubmit` reports upload and download
progress. See [submitting](/docs/guides/react/basics/submitting).

## Where SWR is the better choice

- **Smallest API.** One hook, `useSWR(key, fetcher)`, covers most reads, and the key is usually the URL.
- **Fresh data with no configuration.** Focus and reconnect revalidation and error retries are on by default. In
  HyperFetch you turn them on per hook or request.
- **Any fetcher.** SWR caches whatever your function returns, so any HTTP client or SDK works without an adapter.
- **Read-heavy apps with simple calls.** If you rarely write data and don't need sockets or offline writes, SWR is less
  to learn.
