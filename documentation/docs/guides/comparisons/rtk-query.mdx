# HyperFetch vs RTK Query

RTK Query is the data fetching layer that ships with Redux Toolkit. Like HyperFetch, it makes you define your API up
front and sends the requests itself. The difference is where state lives: RTK Query keeps it in a Redux store,
HyperFetch keeps it in its own client.

:::info How this page was written

RTK Query claims come from the [RTK Query docs](https://redux.js.org/toolkit/rtk-query/overview) and their
[comparison page](https://redux.js.org/toolkit/rtk-query/comparison), linked where they are used. HyperFetch claims are
checked against its source. If something is out of date, [open an issue](https://github.com/BetterTyped/hyper-fetch/issues)
and we will fix it.

:::

---

## When to choose which

- **RTK Query** when your app already uses Redux and you want server data in the same store and Redux DevTools.
- **RTK Query** when other Redux logic (middleware, listeners, reducers) needs to react to API calls.
- **HyperFetch** when you don't use Redux and don't want a store just for data fetching.
- **HyperFetch** when WebSockets or SSE, request queues and offline writes should be part of the request layer.

---

## Feature comparison

**Yes**: built in. **Partial**: possible with your own code or an extra package. **No**: not available.

| Capability           | RTK Query                                     | HyperFetch                                                    |
| -------------------- | --------------------------------------------- | ------------------------------------------------------------- |
| Requires Redux       | Yes, or `<ApiProvider />` without a store     | No                                                            |
| API definition       | One `createApi` slice                         | Separate [`createRequest`](/docs/core/request) objects        |
| Default transport    | `fetchBaseQuery`, a `fetch` wrapper           | `fetch` adapter, or [Axios, GraphQL, Firebase adapters](/docs/core/adapter) |
| Cache by             | Endpoint and serialized arguments             | Request cache key                                             |
| Invalidation         | Tags, with optional ids                       | Request, cache key or RegExp                                  |
| Realtime             | Partial, `onCacheEntryAdded` ¹                | Yes, [`@hyper-fetch/sockets`](/docs/sockets/overview)         |
| Offline write queue  | No                                            | Yes, [request queue](/docs/guides/core/advanced/offline)      |
| Codegen              | OpenAPI and a GraphQL Codegen plugin ²        | OpenAPI and Swagger, [CLI](/docs/cli/overview)                |
| Devtools             | Redux DevTools                                | [HyperFlow](/docs/hyper-flow) desktop app                     |
| UI frameworks        | UI-agnostic, React hooks                      | React                                                         |
| Normalized cache     | No, by design                                 | No ³                                                          |

1. [Streaming updates](https://redux.js.org/toolkit/rtk-query/usage/streaming-updates) run in the `onCacheEntryAdded`
   lifecycle: you open the connection, await `cacheDataLoaded`, apply messages with `updateCachedData` and close it when
   `cacheEntryRemoved` resolves.
2. `@rtk-query/codegen-openapi` and a GraphQL Codegen plugin. The comparison page calls code generation "currently
   experimental".
3. The separate [`@hyper-fetch/db`](/docs/db/overview) package keeps records as rows shared by every query.

## Side by side

### Define a list and an edit

<Tabs>
<TabItem value="hf" label="HyperFetch">

```ts title="api/posts.ts"
import { createClient } from "@hyper-fetch/core";

export const client = createClient({ url: "https://api.example.com" });

export const getPosts = client.createRequest<{ response: Post[] }>()({ endpoint: "/posts" });

export const editPost = client
  .createRequest<{ response: Post; payload: Partial<Post> }>()({
    endpoint: "/posts/:postId",
    method: "PATCH",
  })
  // Refetch the list after every successful edit
  .setOptimistic(() => ({ invalidate: [getPosts] }));
```

</TabItem>
<TabItem value="rtk" label="RTK Query">

```ts title="api/posts.ts"
import { createApi, fetchBaseQuery } from "@reduxjs/toolkit/query/react";

export const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: "https://api.example.com" }),
  tagTypes: ["Post"],
  endpoints: (build) => ({
    getPosts: build.query<Post[], void>({
      query: () => "/posts",
      providesTags: ["Post"],
    }),
    editPost: build.mutation<Post, Partial<Post> & Pick<Post, "id">>({
      query: (body) => ({ url: `/posts/${body.id}`, method: "PATCH", body }),
      invalidatesTags: ["Post"],
    }),
  }),
});

export const { useGetPostsQuery, useEditPostMutation } = api;
```

</TabItem>
</Tabs>

The RTK slice is then registered with your store, or wrapped in `<ApiProvider />`. In HyperFetch each request is its own
export, and `:postId` in the endpoint becomes a required, typed param.

### Use them in a component

<Tabs>
<TabItem value="hf" label="HyperFetch">

```tsx title="posts.tsx"
import { useFetch, useSubmit } from "@hyper-fetch/react";

function Posts() {
  const { data, loading } = useFetch(getPosts);
  const { submit, submitting } = useSubmit(editPost.setParams({ postId: 1 }));

  return (
    <button disabled={submitting} onClick={() => submit({ payload: { title: "Updated" } })}>
      Rename
    </button>
  );
}
```

</TabItem>
<TabItem value="rtk" label="RTK Query">

```tsx title="posts.tsx"
function Posts() {
  const { data, isLoading } = useGetPostsQuery();
  const [editPost, { isLoading: isSaving }] = useEditPostMutation();

  return (
    <button disabled={isSaving} onClick={() => editPost({ id: 1, title: "Updated" })}>
      Rename
    </button>
  );
}
```

</TabItem>
</Tabs>

RTK Query generates one hook per endpoint. HyperFetch has generic hooks that take any request. Tags carry ids, so
editing post 5 can refetch only data tagged `{ type: "Post", id: 5 }`. HyperFetch invalidates by request, by cache key,
or by RegExp such as every page of `/posts`. See [cache revalidation](/docs/guides/core/advanced/cache-revalidation).

## Where RTK Query is the better choice

- **You already run Redux.** It is ["an optional addon included in the Redux Toolkit package"](https://redux.js.org/toolkit/rtk-query/overview),
  with no extra dependency.
- **Redux DevTools history.** RTK Query dispatches normal Redux actions, so every request and state change shows in
  Redux DevTools.
- **Declarative invalidation at scale.** Tags describe what each mutation affects in one slice, which helps when many
  endpoints share data.
- **Other UI layers.** The core API is UI-agnostic and runs wherever Redux runs. HyperFetch's hooks are React only,
  though its core runs anywhere.

## Migrating and next steps

There is no dedicated RTK Query migration guide. Each `build.query` becomes a request used with `useFetch`, each
`build.mutation` a request used with `useSubmit`, and `invalidatesTags` becomes `client.cache.invalidate` or the
`invalidate` list of `setOptimistic`. The runnable [Typed SDK](/examples/getting-started/sdk) and
[OpenAPI codegen](/examples/integrations/openapi-codegen) examples group requests the way an API slice does.
