# React data fetching libraries compared

These pages compare HyperFetch with TanStack Query, SWR, RTK Query and Apollo Client, one library per page, with code for
the same tasks in both. Start here to pick the page that matches your stack.

:::info How these pages were written

Every head-to-head page links each claim about the other library to its official docs, and HyperFetch claims are
checked against its source. Libraries change fast. If something is out of date,
[open an issue](https://github.com/BetterTyped/hyper-fetch/issues) and we will fix it.

:::

---

## When to choose which

- **HyperFetch** for a REST or mixed backend where you want typed requests, realtime, request queues and offline writes
  in one place, without Redux or GraphQL.
- **TanStack Query** when you want the most widely used option, full control over the fetch call, or a framework other
  than React.
- **SWR** for a small app that mostly reads data and needs a light hook with very little setup.
- **RTK Query** when your app already runs on Redux Toolkit.
- **Apollo Client** when your API is GraphQL and you need a normalized cache that updates one record across every view.

---

## Two kinds of library

| Kind                  | Libraries                              | You write                                           |
| --------------------- | -------------------------------------- | --------------------------------------------------- |
| Server-state managers | TanStack Query, SWR                    | A key and a function that fetches. They cache what it returns. |
| API layers            | RTK Query, Apollo Client, HyperFetch   | Endpoints or operations up front. They send the request and cache it. |

Neither kind is better. Server-state managers drop into any codebase because they don't care how you fetch. API layers
give you more structure and less glue code, at the cost of describing requests their way. The
[feature table across all five](/docs/getting-started/comparison) shows the differences in one place.
