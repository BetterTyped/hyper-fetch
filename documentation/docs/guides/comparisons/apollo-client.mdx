# HyperFetch vs Apollo Client

Apollo Client is a GraphQL client built around a normalized cache: each object is stored once, so one mutation updates
every query that shows it. HyperFetch's [GraphQL adapter](/docs/integrations/adapter-graphql/overview) caches each
operation with its variables, next to REST, sockets and other backends. This page compares the two for GraphQL in React.

:::info How this page was written

Apollo claims come from the [Apollo Client docs](https://www.apollographql.com/docs/react), linked where they are used,
with the `@apollo/client/react` imports of the current major version. HyperFetch claims are checked against its source.
If something is out of date, [open an issue](https://github.com/BetterTyped/hyper-fetch/issues) and we will fix it.

:::

---

## When to choose which

- **Apollo Client** when the same entities show up across many queries and mutations should update all of them without
  extra code.
- **Apollo Client** when you use subscriptions over multipart HTTP, or GraphOS features such as the Explorer.
- **HyperFetch** when GraphQL is one of several backends. REST, Firebase and WebSockets use the same requests, cache and
  hooks.
- **HyperFetch** when your queries rarely overlap on the same objects, so invalidating a query is simpler than cache
  merge rules.

## Feature comparison

**Yes**: built in. **Partial**: possible with your own code or an extra package. **No**: not available.

| Capability                    | Apollo Client                                   | HyperFetch                                              |
| ----------------------------- | ----------------------------------------------- | ------------------------------------------------------- |
| Cache                         | Normalized by `__typename` and `id` ¹           | Per operation and variables ²                           |
| Default read                  | `cache-first`                                   | Cached data, refetched in the background on mount       |
| Mutation updates other views  | Yes, for objects returned with their id ³       | Partial, you invalidate or update the queries           |
| React hooks                   | `useQuery`, `useMutation`, `useSubscription`    | `useFetch`, `useSubmit`, `useListener`                  |
| Optimistic UI                 | `optimisticResponse`                            | `setOptimistic` on the request                          |
| Subscriptions over WebSocket  | Yes, `GraphQLWsLink` (`graphql-ws`)             | Yes, `GraphqlWsAdapter` (`graphql-transport-ws`)        |
| Subscriptions over HTTP       | Yes, multipart through `HttpLink`               | No                                                      |
| Offline write queue           | No                                              | Yes, [request queue](/docs/guides/core/advanced/offline) |
| REST and other backends       | No, GraphQL only                                | Yes, swap the [adapter](/docs/core/adapter)             |
| Devtools                      | Browser extension, VS Code (experimental) ⁴     | [HyperFlow](/docs/hyper-flow) desktop app               |
| UI frameworks                 | React, community integrations                   | React                                                   |

1. Per the [caching overview](https://www.apollographql.com/docs/react/caching/overview), the cache ID joins
   `__typename` and `id`, and nested objects become references to one entry.
2. The cache key is built from the operation name, a fingerprint of the document and the variables, so two documents
   with the same name but different fields never share an entry. For records shared across queries, see the
   [`@hyper-fetch/db`](/docs/db/overview) package.
3. Per the [mutations docs](https://www.apollographql.com/docs/react/data/mutations), a new object is not added to list
   fields on its own. That needs `refetchQueries` or an `update` function.
4. The [developer tooling](https://www.apollographql.com/docs/react/development-testing/developer-tooling) page lists a
   Chrome and Firefox extension with cache, query and mutation inspectors, and an experimental VS Code integration that
   also debugs React Native and Node apps.

## Side by side

### Query a user

<Tabs>
<TabItem value="hf" label="HyperFetch">

```tsx title="profile.tsx"
import { Client } from "@hyper-fetch/core";
import { GraphqlAdapter, GraphqlErrorType } from "@hyper-fetch/graphql";
import { useFetch } from "@hyper-fetch/react";
import gql from "graphql-tag";

export const client = new Client<GraphqlErrorType>({ url: "https://api.example.com/graphql" }).setAdapter(
  GraphqlAdapter(),
);

export const getUser = client.createRequest<{ response: { user: User }; payload: { id: string } }>()({
  endpoint: gql`
    query GetUser($id: ID!) {
      user(id: $id) { id name }
    }
  `,
});

function Profile({ id }: { id: string }) {
  // Variables are the request payload. No provider needed.
  const { data, loading, error } = useFetch(getUser.setPayload({ id }));
}
```

</TabItem>
<TabItem value="apollo" label="Apollo Client">

```tsx title="profile.tsx"
import { ApolloClient, HttpLink, InMemoryCache, gql } from "@apollo/client";
import { useQuery } from "@apollo/client/react";

export const client = new ApolloClient({
  link: new HttpLink({ uri: "https://api.example.com/graphql" }),
  cache: new InMemoryCache(),
});

const GET_USER = gql`
  query GetUser($id: ID!) {
    user(id: $id) { id name }
  }
`;

function Profile({ id }: { id: string }) {
  // Needs <ApolloProvider client={client}> above it
  const { data, loading, error } = useQuery(GET_USER, { variables: { id } });
}
```

</TabItem>
</Tabs>

With [GraphQL Code Generator](https://the-guild.dev/graphql/codegen) or [gql.tada](https://gql-tada.0no.co/) you pass a
typed document as `endpoint` and drop the generics. See [GraphQL queries](/docs/integrations/adapter-graphql/queries).

### Rename a user

<Tabs>
<TabItem value="hf" label="HyperFetch">

```tsx title="rename-button.tsx"
import { useSubmit } from "@hyper-fetch/react";

export const renameUser = client.createRequest<{
  response: { renameUser: User };
  payload: { id: string; name: string };
}>()({
  endpoint: gql`
    mutation RenameUser($id: ID!, $name: String!) {
      renameUser(id: $id, name: $name) { id name }
    }
  `,
});

function RenameButton({ id }: { id: string }) {
  const { submit, submitting, onSubmitSuccess } = useSubmit(renameUser);

  // The cost of no normalized cache: say which queries the mutation affects
  onSubmitSuccess(() => client.cache.invalidate(getUser.setPayload({ id })));

  return (
    <button disabled={submitting} onClick={() => submit({ payload: { id, name: "Ada" } })}>
      Rename
    </button>
  );
}
```

</TabItem>
<TabItem value="apollo" label="Apollo Client">

```tsx title="rename-button.tsx"
import { gql } from "@apollo/client";
import { useMutation } from "@apollo/client/react";

const RENAME_USER = gql`
  mutation RenameUser($id: ID!, $name: String!) {
    renameUser(id: $id, name: $name) { id name }
  }
`;

function RenameButton({ id }: { id: string }) {
  // The returned `User:id` object updates every query that holds it
  const [renameUser, { loading }] = useMutation(RENAME_USER);

  return (
    <button disabled={loading} onClick={() => renameUser({ variables: { id, name: "Ada" } })}>
      Rename
    </button>
  );
}
```

</TabItem>
</Tabs>

### Subscribe to messages

<Tabs>
<TabItem value="hf" label="HyperFetch">

```tsx title="chat-room.tsx"
import { Socket } from "@hyper-fetch/sockets";
import { GraphqlWsAdapter } from "@hyper-fetch/graphql";
import { useListener } from "@hyper-fetch/react";

const socket = new Socket({ url: "wss://api.example.com/graphql", adapter: GraphqlWsAdapter() });

const onMessage = socket.createListener<{ onMessage: { text: string } }, { room: string }>()({
  topic: "OnMessage",
  options: {
    document: gql`
      subscription OnMessage($room: String!) {
        onMessage(room: $room) { text }
      }
    `,
  },
});

function ChatRoom({ room }: { room: string }) {
  const { data, status } = useListener(onMessage.setPayload({ room }));
  return <p>{status === "listening" ? data?.onMessage.text : "Connecting..."}</p>;
}
```

</TabItem>
<TabItem value="apollo" label="Apollo Client">

```tsx title="chat-room.tsx"
import { gql } from "@apollo/client";
import { useSubscription } from "@apollo/client/react";

// The client's link uses ApolloLink.split to send subscriptions over GraphQLWsLink
const ON_MESSAGE = gql`
  subscription OnMessage($room: String!) {
    onMessage(room: $room) { text }
  }
`;

function ChatRoom({ room }: { room: string }) {
  const { data, loading } = useSubscription(ON_MESSAGE, { variables: { room } });
  return <p>{loading ? "Connecting..." : data?.onMessage.text}</p>;
}
```

</TabItem>
</Tabs>

HyperFetch listeners with the same topic, document and variables share one server subscription, and every subscription is
sent again after a reconnect. See [GraphQL subscriptions](/docs/integrations/adapter-graphql/subscriptions).

## Where Apollo Client is the better choice

- **Entity-heavy UIs.** When a user's name shows in a header, a list, a detail panel and a comment thread, the
  normalized cache fixes all of them after one mutation.
- **Cache-aware devtools.** The browser extension inspects the normalized store and runs queries through GraphiQL.
- **Subscriptions over multipart HTTP**, which HyperFetch does not support.
- **GraphOS and the wider Apollo ecosystem**, and community integrations for other UI frameworks.
