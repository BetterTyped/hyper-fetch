# WebSocket Authentication

WebSocket authentication is harder than HTTP authentication for one reason: the browser won't let you set headers on
the handshake. There's no `Authorization: Bearer ...` for a `new WebSocket()`. You have to carry the credentials some
other way, and you have to keep them valid across reconnects that may happen hours after the token was issued. This
guide covers the options and how Hyper Fetch sockets resolve credentials fresh for every connection attempt.

:::secondary What you'll learn

1.  Why the browser **WebSocket API has no auth headers** and what to use instead.
2.  How to provide **initial authentication data** using query parameters when creating a socket instance.
3.  How to resolve **short-lived credentials before every connection attempt** with the `onConnect` interceptor.
4.  How to authenticate through **WebSocket subprotocols**, **cookies** and adapter options.

:::

---

## Where WebSocket credentials can go

The browser [`WebSocket` constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket) takes a URL
and an optional list of subprotocols. Nothing else. That leaves four places for credentials:

| Method                   | How it works                                                   | Watch out for                                                    |
| ------------------------ | -------------------------------------------------------------- | ---------------------------------------------------------------- |
| Query param              | `wss://api.example.com/ws?token=...`                            | URLs end up in server and proxy logs. Use short-lived tokens     |
| Subprotocol              | Token sent in the `Sec-WebSocket-Protocol` header              | Echo one protocol back from the server, some browsers drop the connection otherwise |
| Cookie                   | The browser sends cookies for the host with the handshake      | Check the `Origin` header so other sites can't open a socket as the user |
| First message            | Connect, then send `{ type: "auth", token }`                   | The connection is open but unauthenticated until the server replies |

A common pattern is a one-time "ticket": the client calls an authenticated HTTP endpoint, gets a token that's valid for
a few seconds, and opens the socket with it in the query string. A leaked URL is then useless by the time anyone reads
the log.

Whatever you pick, the token has to be read when the connection opens, not when the socket object is created.
Otherwise the automatic reconnect after a network drop sends an expired token and the server rejects it. That's the
part Hyper Fetch handles with `onConnect`.

## Authentication via query parameters

The most common way to authenticate a WebSocket connection is by including a token in the connection URL's query
parameters. Hyper Fetch handles this with the `queryParams` option in the `Socket` constructor.

```tsx
import { Socket } from "@hyper-fetch/sockets";

const token = "your-initial-auth-token";

const socket = new Socket({
  url: "ws://localhost:8080",
  queryParams: { token },
});

socket.onConnected(() => {
  console.log("Socket connected with token!");
});

socket.onDisconnected(() => {
  console.log("Socket disconnected");
});
```

The `queryParams` are appended to the connection URL, so the server receives them during the WebSocket handshake and can
verify the client's identity before accepting the connection.

## Resolving credentials on every connection attempt

Access tokens expire. A connection established with a valid token may be lost hours later, and the automatic reconnect
must not reuse the token captured when the socket was created. The `onConnect` interceptor solves this: Hyper Fetch calls
it right before **every** connection attempt (the initial connection, automatic reconnects and manual reconnects) and
uses whatever it returns to open the connection.

```tsx
import { Socket } from "@hyper-fetch/sockets";

const socket = new Socket({
  url: "ws://localhost:8080",
}).onConnect(({ connection }) => ({
  // highlight-start
  ...connection,
  queryParams: { token: authStore.getState().accessToken },
  // highlight-end
}));
```

The interceptor receives the current `connection` details (`url`, `queryParams` and `adapterOptions`) and must return
them, modified or not. It can be async, so you can refresh the token before connecting. The `attempt` number tells you
whether this is a fresh connection (`0`) or a reconnection attempt.

```tsx
const socket = new Socket({
  url: "ws://localhost:8080",
}).onConnect(async ({ connection, attempt }) => {
  // highlight-start
  const token = await auth.getValidAccessToken({ forceRefresh: attempt > 0 });
  return { ...connection, queryParams: { token } };
  // highlight-end
});
```

Credentials stay in your auth store and the socket reads them only when it actually needs them. A token refreshed while
the connection is alive does not force a reconnect. The next attempt picks up the latest value.

If the interceptor throws, the connection attempt fails, the `onError` callbacks receive the error and the socket stays
disconnected. Call `connect()` (or let the socket reconnect when the app goes back online) to try again.

:::info setQueryParams

`socket.setQueryParams()` replaces the defaults used by the next connection attempt. It does not reconnect on its own.
Call `socket.reconnect()` to apply the new values to a live connection. For credentials that change over time, prefer
`onConnect`.

:::

The same rule applies on logout or account switch: change what your auth store returns, then call `socket.reconnect()`
so the server sees the new identity.

## Authentication via WebSocket subprotocols

Some backends read credentials from the `Sec-WebSocket-Protocol` handshake header instead of the URL. With the
`WebsocketAdapter` you can pass them through the `protocols` adapter option, and resolve them per attempt with
`onConnect` exactly like query params.

```tsx
import { Socket, WebsocketAdapter } from "@hyper-fetch/sockets";

const socket = new Socket({
  url: "wss://example.com/ws",
  adapter: WebsocketAdapter(),
}).onConnect(({ connection }) => ({
  ...connection,
  // highlight-start
  adapterOptions: {
    ...connection.adapterOptions,
    protocols: ["authorization", authStore.getState().accessToken],
  },
  // highlight-end
}));
```

## Authentication via cookies and adapter options

If your session lives in a cookie on the same site as the socket server, the browser sends it with the WebSocket
handshake on its own. There's nothing to configure on the client. On the server, check the `Origin` header before
trusting the cookie.

Server-Sent Events work the same way, with one switch for cross-origin servers. The `ServerSentEventsAdapter` takes `eventSourceInit`,
which is passed to `EventSource`:

```tsx
import { Socket, ServerSentEventsAdapter } from "@hyper-fetch/sockets";

const events = new Socket({
  url: "https://api.example.com/events",
  adapter: ServerSentEventsAdapter(),
  // highlight-next-line
  adapterOptions: { eventSourceInit: { withCredentials: true } },
});
```

A custom adapter can expose its own connection options, for example an `auth` object for a protocol that has one.
Because `onConnect` receives `adapterOptions` too, the same per-attempt resolution works for every adapter. See the
[socket adapter docs](../../sockets/adapter.mdx).
