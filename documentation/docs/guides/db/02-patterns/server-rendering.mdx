# Server rendering with Next.js

The db runs on the server too: each request gets its **own db**, the page loads its queries before rendering, and
`db.dehydrate()` captures the rows. The browser's db starts from them, so its first render matches the server's, then
carries on live. This guide sends Teamboard's team page with its posts already in the HTML.

:::secondary What you'll learn

1.  Why a **module-level db** is a data leak on the server, and how to create one **per request**.
2.  How to load and **dehydrate** queries in a Next.js App Router **Server Component**.
3.  How to **hydrate** the client db and read it with `DbProvider` and `useDb`.
4.  What a hydrated query shows, and **what is never dehydrated**.
5.  How the same pattern works with the **Pages Router** and plain `renderToString`.

:::

---

## One db per request

Most DB guides use a module-level db:

```ts title="src/db.ts"
// error-next-line
export const db = createDb({ post: Post, postSummary: PostSummary });
// On a server, every request shares this one db
```

That is fine in the browser, where one module serves one user. On a server, one module serves **every** request. A
module-level db would keep Alice's private drafts in memory and show them in Bob's render. Collections, on the other
hand, are plain definitions that hold no data, so they can be shared. Export a factory instead:

```ts title="src/db.ts"
import { createDb } from "@hyper-fetch/db";
import type { DbOptions } from "@hyper-fetch/db";

const collections = { post: Post, postSummary: PostSummary };

export const createAppDb = (options?: DbOptions) => createDb(collections, options);
export type AppDb = ReturnType<typeof createAppDb>;
```

Components stop importing `db` and read it from the nearest [`DbProvider`](/docs/react/db/db-provider) with
`useDb<AppDb>()`. The type argument gives back the typed collections.

## App Router

The Server Component creates a db, loads what the page shows, and passes the dehydrated state to a Client Component:

```tsx title="app/teams/[teamId]/page.tsx"
import { eq } from "@hyper-fetch/db";
import { createAppDb } from "@/db";
import { TeamFeedRoot } from "./team-feed";

export default async function TeamPage({ params }: { params: Promise<{ teamId: string }> }) {
  const { teamId } = await params;

  const db = createAppDb();
  // highlight-start
  await db.postSummary.where((post) => eq(post.teamId, teamId)).get();
  const state = db.dehydrate();
  // highlight-end
  db.destroy();

  return <TeamFeedRoot state={state} teamId={teamId} />;
}
```

- `query.get()` loads the query and resolves with its first state that is not `loading`. Like every read, it never
  throws: a failed load resolves with `status: "error"`, and the client loads again on its own.
- `db.dehydrate()` returns plain, JSON-safe data, so it crosses the Server/Client boundary as a prop.
- `db.destroy()` stops the db's timers once it has served its purpose, so finished requests do not keep it in memory.

The Client Component creates the browser's db **once**, from that state:

```tsx title="app/teams/[teamId]/team-feed.tsx"
"use client";

import { useState } from "react";
import { eq } from "@hyper-fetch/db";
import type { DehydratedDb } from "@hyper-fetch/db";
import { DbProvider, useDb, useLiveQuery } from "@hyper-fetch/react";
import { createAppDb, type AppDb } from "@/db";

export function TeamFeedRoot({ state, teamId }: { state: DehydratedDb; teamId: string }) {
  // highlight-next-line
  const [db] = useState(() => createAppDb({ state }));

  return (
    <DbProvider db={db}>
      <TeamFeed teamId={teamId} />
    </DbProvider>
  );
}

function TeamFeed({ teamId }: { teamId: string }) {
  const db = useDb<AppDb>();
  const { data, isFetching } = useLiveQuery(
    db.postSummary.where((post) => eq(post.teamId, teamId)).orderBy((post) => post.createdAt, "desc"),
  );

  return (
    <ul>
      {isFetching && <li className="text-sm text-gray-500">Refreshing...</li>}
      {data?.map((post) => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  );
}
```

`useState` with an initializer creates the db on the first render and keeps it across re-renders. Creating it in the
component body would start a new db, and drop every loaded row, on every render.

## What the first render shows

A hydrated query does not wait for anything:

1.  On the first render, it is **`ready`** with the server's rows, so the HTML React hydrates matches the server's.
2.  It is also **`stale`**: the rows are as old as the server's response.
3.  When the component subscribes, the query **refetches** and opens its syncs. Rows the server no longer returns leave,
    and new ones join.

A query the server did not load starts as `loading` in the browser, as it would without server rendering. You do not
have to dehydrate every query, only the ones the first paint needs.

`isFetching` is true during that background refetch, which makes a quiet "Refreshing..." hint possible without hiding
the rows.

---

## What crosses the wire

`db.dehydrate()` holds the server rows and the loaded subsets of every collection that holds any, with their load times,
as type-tagged JSON. Some things never leave the server:

- **Pending writes and optimistic layers.** A write still in flight on the server is not shown in the browser.
- **The outbox and syncs.** Live updates start in the browser, from the browser's own socket.
- **Empty collections.** They are left out to keep the payload small.

Type-tagged JSON keeps `Date`, `bigint`, `Map` and `Set` values intact through `JSON.stringify`. A value of your own
class needs a codec, and the codec has to be passed on **both** sides:

```ts title="src/db.ts"
export const createAppDb = (options?: DbOptions) => createDb(collections, { codecs: [money], ...options });
```

Putting codecs in the factory is the simplest way to never forget one side. State for a collection the client db does
not have is ignored.

:::caution Authentication on the server

Loaders run your requests on the server, with your client's authentication, such as `onAuth` from the
[authentication guide](/docs/guides/core/basics/authentication). On the server it has to find the current request's
credentials, not a token kept in a module. When that is not possible, load only public data on the server and let the
browser load the rest: a failed server load only means the browser loads it itself.

:::

## Pages Router and other frameworks

The pattern does not depend on the App Router. With the Pages Router, dehydrate in `getServerSideProps` and hydrate in
the page:

```tsx title="pages/teams/[teamId].tsx"
export const getServerSideProps = async ({ params }: { params: { teamId: string } }) => {
  const db = createAppDb();
  await db.postSummary.where((post) => eq(post.teamId, params.teamId)).get();
  const state = db.dehydrate();
  db.destroy();

  return { props: { state, teamId: params.teamId } };
};

export default function TeamPage({ state, teamId }: { state: DehydratedDb; teamId: string }) {
  return <TeamFeedRoot state={state} teamId={teamId} />;
}
```

With any other server, render inside the request's db and send the state with the HTML:

```tsx title="server.tsx"
const db = createAppDb();
await db.postSummary.where((post) => eq(post.teamId, teamId)).get();

const html = renderToString(
  <DbProvider db={db}>
    <TeamFeed teamId={teamId} />
  </DbProvider>,
);
const state = db.dehydrate(); // embed as JSON next to the HTML
db.destroy();
```

On the client, `hydrateRoot` the same tree with `createAppDb({ state })` in the provider.

## Before and after

| Client-only app                           | SSR-friendly app                                                         |
| ----------------------------------------- | ------------------------------------------------------------------------ |
| `export const db = createDb(collections)` | `export const createAppDb = (options) => createDb(collections, options)` |
| Components import `db`                    | Components call `useDb<AppDb>()` under a `DbProvider`                    |
| Queries load in the browser               | The server awaits `query.get()` for what the first paint shows           |
| Nothing is sent with the page             | `db.dehydrate()` is sent with the page                                   |
| `createDb(collections)` in the browser    | `createAppDb({ state })` in a `useState` initializer                     |
| Codecs on the client                      | Codecs in the factory, on both sides                                     |

:::note When to render on the server

- The page is **public** and has to be indexed: a blog, a docs page, a profile.
- The first paint matters on **slow devices**: a feed, a landing page.
- Skip it for screens behind a login that users open once loaded, such as a settings panel. Client rendering with a
  module-level db is simpler there.

:::

Teamboard's team page arrives with its posts.

- You can create a **db per request** with a factory, and read it with `DbProvider` and `useDb<AppDb>()`.
- You can load queries with **`query.get()`** and send **`db.dehydrate()`** with the page.
- You can hydrate the client with **`createAppDb({ state })`**, ready on the first render and refreshed after.
- You can tell what is **never dehydrated**, and pass **codecs** on both sides.
- You can use the same pattern with the **Pages Router** or plain `renderToString`.
