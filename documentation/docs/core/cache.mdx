The **Cache** stores successful responses by `cacheKey` and tells every reader when an entry changes. Requests write to
it on every successful `send()`, hooks read from it, and you can read, update, invalidate or persist entries yourself.
It is in memory by default, with optional persistent storage.

:::tip Purpose

1. **Store responses** by key, with freshness (`staleTime`) and removal (`cacheTime`) per request.
2. **Notify readers** when an entry is set, updated, invalidated or removed.
3. **Persist** entries across sessions with an async `lazyStorage`.

:::

```ts title="api/notes.ts"
const getNotes = client.createRequest<{ response: { text: string }[] }>()({ endpoint: "/notes" });

await getNotes.send(); // every successful send() writes to the cache

const cached = getNotes.read(); // the cached response, if any, without a network call

client.cache.invalidate(getNotes); // mark it stale, mounted hooks refetch
```

## How entries are keyed

Each entry is stored under the request's `cacheKey`, built from the method, the filled endpoint and the query params.
Two requests with the same values share one entry. Set your own key with `cacheKey` or `setCacheKey`.

```ts
getUser.setParams({ userId: 1 }).cacheKey; // "GET_/users/1_"
getUsers.setQueryParams({ page: 2 }).cacheKey; // 'GET_/users_{"page":2}'
getUser.setCacheKey("current-user").cacheKey; // "current-user"
```

Query params are serialized with `JSON.stringify`, so `{ a, b }` and `{ b, a }` are two entries. Build query objects in
a fixed order. See [Request keys](/docs/core/request#keys).

---

## Freshness and removal

Only successful responses are stored. A failed refetch keeps the last good `data` in the entry.

| Option      | Default          | What it controls                                                          |
| ----------- | ---------------- | ------------------------------------------------------------------------- |
| `cache`     | `true`           | Whether the request writes to the cache                                   |
| `staleTime` | `300000` (5 min) | How long data counts as fresh. Hooks refetch stale data.                  |
| `cacheTime` | `300000` (5 min) | How long the entry is kept, counted from `responseTimestamp`              |

Change them on the request, for example `staleTime: Time.MIN` or `setCacheTime(Infinity)`. When `cacheTime` passes, the
entry is removed, but only while the app is online.

```ts
import { Time } from "@hyper-fetch/core";

const getSettings = client.createRequest<{ response: Settings }>()({
  endpoint: "/settings",
  staleTime: Time.MIN * 10,
  cacheTime: Time.HOUR,
});
```

## Invalidate after a mutation

`invalidate` sets the entry's `staleTime` to `0` and emits an event, so every mounted reader refetches. It takes a
request, a key, a RegExp or an array of them. With no argument it invalidates everything.

```ts
const { success } = await createNote.send({ payload: { text: "Hello" } });

if (success) {
  client.cache.invalidate([getNotes, /GET_\/notes\//]);
}
```

See [cache revalidation](/docs/guides/core/advanced/cache-revalidation).

---

## Update entries yourself

`update` changes an existing entry and does nothing when there is none. It sets `responseTimestamp` to now, so
`staleTime` and `cacheTime` count from the update.

```ts
client.cache.update(getNotes, (previous) => ({
  data: [...(previous?.data ?? []), { text: "New note" }],
}));
```

`delete(cacheKey)` removes an entry. To seed the cache, prefer `client.hydrate()` over `set`, which needs a complete
response with its details. For optimistic changes, use [`setOptimistic`](/docs/core/request#update-the-cache-optimistically).

---

## Scope the cache on the server

The client `mode` decides whether requests are cached without a scope. Default `"auto"`: `"client"` in the browser,
`"server"` everywhere else.

- **`"client"`**: requests are cached. A scope is an optional key prefix.
- **`"server"`**: a request is cached only when it has a scope, so one user's data never reaches another.

```ts title="server.ts"
// Not cached on the server
await getUser.setParams({ userId: 1 }).send();

// Cached, under "<sessionId>__GET_/users/1_"
await getUser.setParams({ userId: 1 }).setScope(session.id).send();
```

For data that is the same for everyone, use a shared scope such as `setScope("public")`.

## Persist the cache

Pass an async `lazyStorage` with `get`, `set`, `keys` and `delete`. Every entry is written to it, and a read loads the
fresh entry from it in the background and emits it to the readers. With IndexedDB through `idb-keyval`:

```ts title="api/client.ts"
import { Cache, createClient } from "@hyper-fetch/core";
import { del, get, keys, set } from "idb-keyval";

export const client = createClient({
  url: "https://api.example.com",
  cache: () =>
    new Cache({
      version: "2", // bump when response shapes change, old persisted entries are dropped
      lazyStorage: {
        get: (key) => get(key),
        set: (key, value) => set(key, value),
        keys: () => keys() as Promise<string[]>,
        delete: (key) => del(key),
      },
    }),
});
```

`localStorage` is synchronous and stores strings, so wrap it in such an object. On logout call `client.clear()`, which
also empties `lazyStorage`. See the [persistence guide](/docs/guides/core/advanced/persistence).

| Option        | Default         | Description                                                            |
| ------------- | --------------- | ---------------------------------------------------------------------- |
| `storage`     | in-memory `Map` | Sync storage with `get`, `set`, `keys`, `delete` and `clear`           |
| `lazyStorage` | none            | Async storage that mirrors every entry, such as IndexedDB              |
| `version`     | `"0.0.1"`       | Entries saved with another version are dropped                         |

## Structural sharing

When a new response is deeply equal in parts to the cached one, those parts keep their object references, and an equal
response keeps the same `data` object. That avoids needless re-renders. It is on by default, turn it off with
`structuralSharing: false` for very large payloads you never compare.

:::secondary Summary

- Successful responses are stored by `cacheKey`, fresh for `staleTime` and kept for `cacheTime`, 5 minutes each.
- `invalidate` marks entries stale and refetches readers. `update` edits an existing entry.
- On the server only scoped requests are cached. Persist with `lazyStorage` and bump `version` on shape changes.

:::
