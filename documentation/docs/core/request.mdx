A **Request** is an immutable, typed description of one endpoint call: its endpoint, method, types and options. You
create it once from the [client](/docs/core/client) and send it from components, servers, tests or scripts. It is plain
data, so it can be cloned, serialized, queued while offline and restored later.

:::tip Purpose

1. **Define an endpoint once** with its response, payload, query params and error types.
2. **Send it anywhere** with `send()`, which always resolves with a response object.
3. **Carry its behavior**: cache, retries, cancelation, queueing and offline options.

:::

```ts title="api/users.ts"
import { client } from "./client";

export const getUser = client.createRequest<{ response: User }>()({
  endpoint: "/users/:userId",
});
```

```tsx live title="Send a request" size="small"
const response = await getUser.send({
  params: { userId: 1 },
});

console.log(response);
```

`createRequest` is called twice: the first call takes the types, the second the options. The split lets TypeScript
read `:userId` from the endpoint string and require it when you send.

---

## Type the request

All generics are optional. Leave out what the endpoint does not have.

| Generic       | Types                                                                 |
| ------------- | --------------------------------------------------------------------- |
| `response`    | `data` of a successful response                                       |
| `payload`     | The body you send, set with `setPayload` or `send({ payload })`        |
| `queryParams` | Query params. `queryParams?:` makes them optional, `queryParams:` required |
| `error`       | Endpoint errors, merged with the client's global error                |

```ts title="api/users.ts"
export const updateUser = client.createRequest<{
  response: User;
  payload: { name: string };
  queryParams?: { notify?: boolean };
  error: { fields: Record<string, string[]> };
}>()({ endpoint: "/users/:userId", method: "PATCH" });
```

TypeScript does not reject unknown keys in an object generic, so `rsponse` would pass silently. The
[lint plugin](/docs/integrations/plugin-eslint) reports it. When the endpoint is a typed GraphQL document, `response`
and `payload` come from it, see [typed documents](/docs/integrations/adapter-graphql/queries#typed-documents).

## Pass params, query params and payload

Set values ahead of time with setters, or pass them to `send()`. Both are typed by the generics and the endpoint.

```ts
// Setters return a new request
const response = await updateUser
  .setParams({ userId: 1 })
  .setPayload({ name: "Ann" })
  .send();

// Or all at once
await updateUser.send({
  params: { userId: 1 },
  payload: { name: "Ann" },
  queryParams: { notify: true },
});
```

- **Params** come from `:name` segments of the endpoint. A missing one is a compile error.
- **Query params** are serialized by the adapter. The fetch adapter's array format and encoding are set with
  `client.adapter.setQueryParamsMapperConfig`.
- **Payload** can be JSON data or `FormData`. Falsy values like `0` or `""` are sent as they are, `null` removes the
  payload.

Guides: [parameters](/docs/guides/core/basics/parameters), [query params](/docs/guides/core/basics/query-params) and
[payload](/docs/guides/core/basics/payload).

---

## Setters return a clone

Every setter returns a new request and leaves the original untouched. Use the returned value. The mock setters
(`setMock`, `clearMock`, `setMockingEnabled`) are the only exception: they change the instance.

```ts
// error-next-line
getUser.setParams({ userId: 1 }); // result discarded
await getUser.send(); // compile error: params are still required

// highlight-next-line
await getUser.setParams({ userId: 1 }).send(); // correct
```

## Send it

`send()` goes through the [dispatcher](/docs/core/dispatcher), the adapter and the cache. It resolves with
`{ data, error, status, success, extra, requestTimestamp, responseTimestamp }` for every outcome, including HTTP errors,
timeouts and aborts, so you never need `try/catch`.

```ts
const { data, error, status } = await getUser.send({ params: { userId: 1 } });

if (data) console.log(data.name);
else console.error(status, error);
```

`send()` accepts every request option except `endpoint` and `method`, plus these:

| Option           | Default          | Description                                                                                   |
| ---------------- | ---------------- | --------------------------------------------------------------------------------------------- |
| `cachePolicy`    | `"network-only"` | `"cache-first"` returns a cached entry, fresh or stale, else fetches. `"revalidate"` returns the cached entry and refetches in the background. |
| `dispatcherType` | `"auto"`         | `"auto"` sends GET and QUERY through `fetchDispatcher`, the rest through `submitDispatcher`. Force one with `"fetch"` or `"submit"`. |
| `optimistic`     | none             | [Optimistic changes](#update-the-cache-optimistically) for this call only.                     |

Neither cache policy looks at `staleTime`. `request.read()` returns the cached response without a network call.

`exec()` sends straight through the adapter: interceptors and mappers run, but there is no deduplication, queue, retry,
offline handling or cache write. Use it for one-off server calls. See the [fetching guide](/docs/guides/core/basics/fetching).

## Control how it is sent

The dispatcher reads these options from the request. Each has a setter, such as `setCancelable(true)`.

| Option        | Default                    | What it does                                                         |
| ------------- | -------------------------- | -------------------------------------------------------------------- |
| `deduplicate` | `true` for GET and QUERY ¹ | Identical requests in flight share one call                          |
| `cancelable`  | `false`                    | A new send aborts the previous one with the same `queryKey`          |
| `queued`      | `false`                    | Requests with the same `queryKey` go one at a time, in order         |
| `offline`     | `true`                     | Requests wait for the connection instead of failing                  |
| `retry`       | `0`                        | Failed attempts to retry, delayed by `retryTime` (default 500 ms)    |

1. The fetch adapter turns deduplication on for GET and QUERY. Other methods and adapters default to `false`.

Abort in-flight requests with `request.abort()`, which aborts every request with the same `abortKey`.

```tsx live title="Cancel the previous call" size="small"
const cancelableRequest =
  getUser.setCancelable(true);

cancelableRequest.send({
  params: { userId: 1 },
});

setTimeout(() => {
  // Aborts the first call
  cancelableRequest.send({
    params: { userId: 1 },
  });
}, 500);
```

Decide per response whether to retry with `setRetryOnError`:

```ts
const getReport = client
  .createRequest()({ endpoint: "/reports", retry: 3, retryTime: 1000 })
  // skip retries for 4xx
  .setRetryOnError(({ status }) => !!status && status >= 500);
```

Guides: [cancellation](/docs/guides/core/advanced/cancellation), [deduplication](/docs/guides/core/advanced/deduplication),
[queueing](/docs/guides/core/advanced/queueing), [offline](/docs/guides/core/advanced/offline) and
[retries](/docs/guides/core/basics/retries).

## Keys

Three keys tie a request to the cache, the queues and aborting. They are derived from the request, so equal requests
share cache entries and deduplication automatically.

| Key        | Identifies                    | Default value                              | Example for `GET /users/1?page=2` | Setter        |
| ---------- | ----------------------------- | ------------------------------------------ | --------------------------------- | ------------- |
| `cacheKey` | The cached response           | method, filled endpoint, query params      | `GET_/users/1_{"page":2}`         | `setCacheKey` |
| `queryKey` | The dispatcher queue          | method, filled endpoint, query params      | `GET_/users/1_{"page":2}`         | `setQueryKey` |
| `abortKey` | Requests aborted together     | method, endpoint template, `cancelable`    | `GET_/users/:userId_false`        | `setAbortKey` |

Override a key to group requests on purpose. For search-as-you-type, give a cancelable request one `queryKey`, because
the default one changes with every query:

```ts
const searchUsers = getUsers.setCancelable(true).setQueryKey("users-search");
```

To change how keys are built for every request, use `client.setCacheKeyMapper`, `setQueryKeyMapper` or
`setAbortKeyMapper`. The mapper must return a key for every request, so fall back to `getRequestKey(request)`.

---

## Scope requests on the server

`setScope(id)` prefixes all three keys with the scope, so scoped requests never share cache, queues or aborts. On a
client in `"server"` mode a request is only cached when it has a scope. See [Cache](/docs/core/cache).

```ts
const { data } = await getUser
  .setParams({ userId: 1 })
  .setScope(session.id)
  .send();
```

## Map and validate

- `setResponseMapper` reshapes or validates the response and changes the type of `data`. A throw becomes an error
  response. The cache keeps the raw response.
- `setRequestMapper` changes the request right before it is sent. A throw stops the request and returns an error.
- `setPayloadMapper` transforms the payload, for example into `FormData`.

```ts
const getProfile = client
  .createRequest<{ response: { full_name: string } }>()({ endpoint: "/me" })
  .setResponseMapper((response) => {
    if (!response.data) return response;
    return { ...response, data: { name: response.data.full_name } };
  });
```

Guides: [data mapping](/docs/guides/core/basics/data-mapping), [mapping](/docs/guides/core/advanced/mapping) and
[validation](/docs/guides/core/advanced/validation).

## Update the cache optimistically

`setOptimistic` changes cached data before the server answers. Build each change with `optimistic()`. Core rolls it back
on failure, abort or removal from the queue, and refreshes the target once the last pending change on it settles.

```ts title="api/todos.ts"
import { optimistic } from "@hyper-fetch/core";

export const toggleTodo = client
  .createRequest<{ response: Todo; payload: { done: boolean } }>()({
    endpoint: "/todos/:todoId",
    method: "PATCH",
  })
  .setOptimistic(({ params, payload }) => [
    optimistic(getTodos).patch(params.todoId, payload),
  ]);
```

The callback can also return `{ updates, context, rollback, invalidate }`. The
[optimistic updates guide](/docs/guides/react/basics/optimistic-approach) covers every field.

## Listen to the lifecycle

`send()` takes callbacks for one call. `$hooks` registers listeners on the request instance, which run for every
`send()` and `exec()` of it and of clones made afterwards. Each `$hooks` method returns an unsubscribe function.

```ts
await getUser.send({
  params: { userId: 1 },
  onRequestStart: ({ requestId }) => console.log("started", requestId),
  onDownloadProgress: ({ progress }) => console.log(progress),
  onRetry: ({ retry, delay }) => console.log(`retry ${retry} in ${delay} ms`),
  onResponse: ({ response }) => console.log(response.status),
});

const unsubscribe = getUser.$hooks.onResponse(({ response }) =>
  track(response.status),
);
```

The callbacks are `onBeforeSent`, `onRequestStart`, `onResponseStart`, `onUploadProgress`, `onDownloadProgress`,
`onRetry`, `onResponse` and `onRemove`. A callback that throws does not break the request: `send()` still resolves and
the error is thrown from a timer, where `window.onerror` or `uncaughtException` handlers see it. `$hooks` are not part
of `toJSON()`.
