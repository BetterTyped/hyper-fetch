# Why HyperFetch?

HyperFetch is a typed request layer: you describe each endpoint once, and the same object is sent from components,
servers, tests and scripts, with cache, queues and offline handling attached. This page shows where that differs from
TanStack Query, SWR, RTK Query and Apollo Client, and where those are the better pick.

:::info How this page was written

Claims about other libraries come from their own docs, linked on the [head-to-head pages](/docs/guides/comparisons).
Libraries change fast. If something here is out of date, [open an issue](https://github.com/BetterTyped/hyper-fetch/issues)
and we will fix it.

:::

---

## When to choose which

- **HyperFetch** for a REST or mixed backend where you want typed requests, realtime, request queues and offline writes
  in one place, without Redux or GraphQL.
- **TanStack Query** when you want the most widely used option, full control over the fetch call, or a framework other
  than React.
- **SWR** for a small app that mostly reads data and needs a light hook with very little setup.
- **RTK Query** when your app already runs on Redux Toolkit.
- **Apollo Client** when your API is GraphQL and you need a normalized cache that updates one record across every view.

## Feature comparison

| Capability         | HyperFetch                    | TanStack Query            | SWR                    | RTK Query              | Apollo Client                 |
| ------------------ | ----------------------------- | ------------------------- | ---------------------- | ---------------------- | ----------------------------- |
| Sends requests     | Yes, built-in `fetch` adapter | No, you write `queryFn`   | No, you write fetchers | Yes, `fetchBaseQuery`  | Yes, GraphQL only             |
| Request definition | `createRequest` object        | Query key and function    | Key and fetcher        | One `createApi` slice  | GraphQL documents             |
| Cache              | Per request key               | Per query key             | Per key                | Per endpoint and args  | Normalized by type and id     |
| Invalidation       | Request, key or RegExp        | Query key                 | `mutate` with a key    | Tags                   | `refetchQueries`, cache edits |
| Realtime           | `@hyper-fetch/sockets`        | Your own socket           | `useSWRSubscription`   | `onCacheEntryAdded`    | GraphQL subscriptions         |
| Codegen            | OpenAPI, Swagger, [CLI](/docs/cli/overview) | OpenAPI, third-party ¹ | OpenAPI, third-party ¹ | OpenAPI, official      | GraphQL Code Generator        |
| Devtools           | HyperFlow desktop app         | In-app panel              | Community extension    | Redux DevTools         | Browser extension             |
| UI frameworks      | React                         | React, Solid, Svelte, Vue | React                  | Any, with React hooks  | React, community ports        |

1. Generators such as Orval, Hey API and Kubb write TanStack Query or SWR hooks from OpenAPI, see
   [OpenAPI to TypeScript](/docs/cli/openapi-typescript-client).

## What is built into HyperFetch

These are verified against the HyperFetch source. Each links to where it is documented.

- **URL params typed from the endpoint string.** `/users/:userId` makes `userId` a required param, and `send()` without
  it fails to compile. See [Request](/docs/core/request).
- **One response shape.** `send()` resolves with `{ data, error, status, success, extra }` for HTTP errors, timeouts,
  aborts and network failures. It never throws.
- **Request modes per queue.** `deduplicate` (on for GET and QUERY), `cancelable` and `queued`, plus pausing and stopping whole
  queues. See [Dispatcher](/docs/core/dispatcher).
- **Offline writes.** Requests sent while offline wait and go out when the connection returns. With the dispatcher's
  `lazyStorage` they also survive a reload. See [offline](/docs/guides/core/advanced/offline).
- **Progress events.** Download progress with the fetch adapter, upload progress with the
  [Axios adapter](/docs/integrations/adapter-axios/overview).
- **No normalized cache.** HyperFetch caches one entry per request. If you need entity normalization, see the
  [db package](/docs/db/overview) or pick Apollo Client.

## Side by side with TanStack Query

<Tabs>
<TabItem value="hf" label="HyperFetch">

```tsx title="todos.tsx"
import { createClient } from "@hyper-fetch/core";
import { useFetch, useSubmit } from "@hyper-fetch/react";

const client = createClient({ url: "https://api.example.com" });

const getTodos = client.createRequest<{ response: Todo[] }>()({
  endpoint: "/todos",
});
const createTodo = client.createRequest<{
  response: Todo;
  payload: { title: string };
}>()({
  endpoint: "/todos",
  method: "POST",
});

function Todos() {
  const { data, loading } = useFetch(getTodos);
  const { submit, onSubmitSuccess } = useSubmit(createTodo);

  // Mounted useFetch hooks for getTodos refetch
  onSubmitSuccess(() => client.cache.invalidate(getTodos));

  return (
    <button onClick={() => submit({ payload: { title: "Buy milk" } })}>
      Add
    </button>
  );
}
```

</TabItem>
<TabItem value="tq" label="TanStack Query">

```tsx title="todos.tsx"
import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";

function Todos() {
  const queryClient = useQueryClient();
  const { data, isPending } = useQuery({
    queryKey: ["todos"],
    queryFn: async () => {
      const response = await fetch("https://api.example.com/todos");
      if (!response.ok) throw new Error("Request failed");
      return response.json();
    },
  });
  const mutation = useMutation({
    mutationFn: addTodo,
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ["todos"] }),
  });

  return (
    <button onClick={() => mutation.mutate({ title: "Buy milk" })}>Add</button>
  );
}
```

</TabItem>

The HyperFetch requests also work outside React: `await getTodos.send()` in a loader, a test or a script.

## Where another library is the better choice

- **You need Vue, Svelte or Solid bindings.** HyperFetch ships React bindings only. TanStack Query covers those.
- **Your app is GraphQL with shared entities.** Apollo's normalized cache updates every view of a record after one
  mutation. HyperFetch invalidates or updates each request entry.
- **You are all-in on Redux.** RTK Query keeps server state in the same store and devtools as the rest of your state.
- **You only read a few endpoints.** SWR or plain `fetch` is less to learn.
- **You want the largest community.** TanStack Query has the most users, answers and integrations.
